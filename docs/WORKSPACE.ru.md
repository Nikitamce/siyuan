# Структура файловой системы рабочей области SiYuan

[English](WORKSPACE.md)

> Этот документ описывает организацию каталогов и файлов рабочей области SiYuan на диске.
> Он дополняет [`SY-FORMAT.zh-CN.md`](./SY-FORMAT.zh-CN.md): последний описывает JSON-структуру **внутри** файлов `.sy`, а данный документ — общую структуру рабочей области **в целом** в файловой системе.
> Все выводы проверены по реальной рабочей области и коду ядра.

## 0. Обзор

Рабочая область SiYuan представляет собой **самоописываемое** дерево каталогов: блокноты, документы и файлы ресурсов хранятся на диске в виде файлов или каталогов. **Имя файла — это ID, а структура каталогов — это иерархия документов**. Файловая система хранит авторитетное исходное содержимое, а базы данных SQLite в `temp/` являются перестраиваемыми индексами и кэшем. Содержимое обычных блокнотов можно читать напрямую, тогда как содержимое зашифрованных блокнотов хранится на диске в зашифрованном виде и должно читаться через разблокированное ядро.

## 1. Краткое дерево (обзор)

```
<Корень рабочей области>/   напр. F:\SiYuan\
├── .lock                       # Блокировка рабочей области во время работы
├── conf/
│   ├── conf.json              # ★Общая конфигурация рабочей области (appearance/system/sync/editor...)
│   ├── appearance/             # Встроенные ресурсы оформления
│   ├── ca.crt / ca.key / cert.pem / key.pem   # TLS-сертификаты и ключи
│   └── windowState.json        # Состояние окна настольной версии
├── data/                       # DataDir — корень всех данных блокнотов
│   ├── .siyuan/                # Скрытая конфигурация уровня рабочей области
│   │   ├── syncignore / searchignore / embeddingignore / indexignore / refsearchignore
│   │   └── data-crypto-backup.json # Опциональные глобальные метаданные восстановления зашифрованных данных
│   ├── assets/                 # ★Глобальные файлы ресурсов (изображения/аудио-видео/файлы)
│   ├── templates/              # Глобальные шаблоны (.md)
│   ├── widgets/                # Виджеты
│   ├── plugins/                # Плагины
│   ├── themes/                 # Сторонние темы, синхронизируются как обычные файлы
│   ├── icons/                  # Сторонние значки, синхронизируются как обычные файлы
│   ├── emojis/                 # Пользовательские emoji
│   ├── snippets/               # Фрагменты кода (CSS/JS)
│   ├── public/                 # Статические ресурсы
│   ├── storage/                # Постоянные структурированные данные (представления атрибутов, состояние плагинов и т. д.)
│   └── <boxID>/                # ★Блокнот (имя каталога = ID блокнота)
│       ├── .siyuan/
│       │   ├── conf.json       # ★Конфигурация блокнота (BoxConf: name/icon/closed...)
│       │   ├── sort.json       # Опциональное пользовательское отображение сортировки {docID: order}
│       │   ├── boxDoc.json     # Опциональный маркер документа верхнего уровня блокнота для импорта/экспорта .sy.zip
│       │   └── notebook-crypto-backup.json # Опциональная резервная копия обёрнутого ключа зашифрованного блокнота
│       ├── <boxID>.sy          # Опциональный документ верхнего уровня блокнота (rootID = ID блокнота)
│       ├── <docID>.sy          # Документ (JSON-дерево; имя файла = rootID документа)
│       ├── <docID>/            # ★Каталог дочерних документов этого документа (одноимённая пара)
│       │   ├── <childID>.sy
│       │   └── <childID>/ ...  # Вложенность произвольной глубины
│       ├── assets/             # Локальные файлы ресурсов блокнота (обязательны для зашифрованных блокнотов)
│       └── storage/av/         # Определения представлений атрибутов зашифрованного блокнота
├── repo/                       # Репозиторий данных (снимки/синхронизация)
├── history/                    # Архив истории редактирования
├── corrupted/                  # Опциональный каталог карантина повреждённых данных
└── temp/                       # Перестраиваемые индексы, очереди, кэш, журналы и файлы экспорта
    ├── siyuan.db / blocktree.db / asset_content.db / history.db
    ├── siyuan-encrypted-<boxID>.db / siyuan-encrypted-<boxID>-blocktree.db
    └── queue/ / export/ / os/ / siyuan.log
```

## 2. Корень рабочей области

Корень рабочей области выбирается пользователем (например, `F:\SiYuan\`). Признак корректной рабочей области: наличие файла `conf/conf.json` с полем `kernelVersion`.

Элементы корневого каталога рабочей области:

| Элемент | Назначение |
|---|---|
| `.lock` | Блокировка времени выполнения, предотвращающая одновременное открытие одной рабочей области двумя ядрами |
| `conf/` | Конфигурация уровня рабочей области, ресурсы оформления, а также TLS-сертификаты и ключи |
| `data/` | **Все данные блокнотов** (основная тема этого документа) |
| `repo/` | Репозиторий снимков данных (используется для синхронизации и истории) |
| `history/` | Архив истории редактирования |
| `temp/` | Перестраиваемые индексы, очереди, кэш, журналы и файлы экспорта |
| `corrupted/` | Опциональная зона карантина повреждённых данных (создаётся ядром автоматически при необходимости) |

## 3. Верхний уровень `data/`

На первом уровне `data/` находятся два вида элементов:

1. **Фиксированные каталоги данных**: `.siyuan/`, `assets/`, `templates/`, `widgets/`, `plugins/`, `themes/`, `icons/`, `emojis/`, `snippets/`, `public/`, `storage/`.
2. **Каталоги блокнотов**: каждый представляет собой папку, названную по ID блокнота.

### Список зарезервированных имён файлов

`IsReservedFilename`:

```go
func IsReservedFilename(baseName string) bool {
    return "assets" == baseName || "templates" == baseName || "widgets" == baseName ||
        "emojis" == baseName || ".siyuan" == baseName || strings.HasPrefix(baseName, ".")
}
```

То есть физические сегменты пути `assets` / `templates` / `widgets` / `emojis` / `.siyuan` и любые имена, начинающиеся с `.`, являются зарезервированными. Это ограничение относится к ID и сегментам пути на диске и не ограничивает отображаемые в интерфейсе названия блокнотов или заголовки документов.

### Постоянные данные и перестраиваемые индексы

Сторонние темы располагаются в `data/themes/<name>/`, наборы значков — в `data/icons/<name>/` и используют общую с плагинами, виджетами и шаблонами логику файловой синхронизации, удаления, обработки конфликтов и снимков. Каждое устройство независимо сохраняет выбор оформления в `conf/conf.json`, а встроенные ресурсы остаются ресурсами программы. Даже если для ресурсов блокнота включена загрузка по требованию, ресурсы пакетов загружаются полностью. При миграции исходный каталог перемещается в каталог данных без сохранения исходной копии. Если в восстанавливаемом снимке отсутствует какой-либо пакет, он удаляется. Подробнее см. в [Синхронизация внешнего вида](APPEARANCE-SYNC.zh-CN.md).

`data/storage/` хранит постоянные структурированные данные, такие как определения представлений атрибутов и состояние плагинов. Файлы SQLite в `temp/` являются производными индексами и кэшем: обычные блокноты используют глобальные `siyuan.db` и `blocktree.db`, а каждый разблокированный зашифрованный блокнот использует отдельную базу данных SQLCipher. Поэтому удаление или перестроение индекса нельзя путать с удалением исходных `.sy`, файлов ресурсов или файлов определений баз данных.

### Правила определения блокнота

При перечислении `data/` функция `ListNotebooks` проверяет каждый каталог:

1. Пропускает зарезервированные имена;
2. Элемент должен быть каталогом (не файлом);
3. Имя каталога должно соответствовать формату NodeID (`ast.IsNodeIDPattern`);
4. Если выполнены все три условия → имя каталога является `box.ID` (ID блокнота).

## 4. Внутренняя структура блокнота: пары «родитель–потомок»

Это важнейшее соглашение всей структуры:

> **Представление документа `A` на диске = файл `A.sy` + каталог `A/` (последний существует только если у A есть дочерние документы). Все дочерние документы A помещаются в каталог `A/`; если у дочернего документа есть свои дочерние документы, вкладывается каталог `A/B/` на произвольную глубину.**

Реальный пример (из вывода `find`):

```
20221126104620-m06prws/                         # Каталог родительского документа A
20221126104620-m06prws.sy                       # Сам родительский документ A
20221126104620-m06prws/20230928134805-z11t56h.sy   # Дочерний документ B документа A
20221126104620-m06prws/20230928134805-z11t56h/    # Подкаталог B (уровень внуков)
20221126104620-m06prws/20230928134805-z11t56h/20240304105333-v7g5j1s.sy
```

Подтверждение в коде:

- Раскрытие дочерних документов (`Ls`): передаётся путь `.sy`, отбрасывается суффикс `.sy`, проверяется существование одноимённого каталога и при наличии перечисляются его элементы.
- Глубина дочерних документов (`GetChildDocDepth`): аналогично выполняется обход одноимённого каталога.

> ⚠️ Это означает: **при перемещении или переименовании документа с дочерними документами необходимо синхронно перемещать его одноимённый каталог**, иначе дочерние документы невозможно будет найти.

### Исключение для документа верхнего уровня блокнота

При включённой функции документа верхнего уровня блокнота ядро создаёт `<boxID>.sy` непосредственно в каталоге блокнота. Его `rootID` совпадает с ID блокнота, поэтому блокнот и его документ верхнего уровня используют один и тот же ID.

Переключатель хранится в `fileTree.boxDocEnabled` файла `conf/conf.json`. В новых рабочих областях он включён по умолчанию; если в существующей конфигурации это поле отсутствует, оно инициализируется как выключенное.

Документ верхнего уровня блокнота является виртуальным родителем для всех обычных документов корневого уровня блокнота. В отличие от обычного родительского документа, его дочерние документы по-прежнему располагаются в каталоге блокнота и **не** перемещаются в `<boxID>/<boxID>/`. Например:

```
data/<boxID>/
├── <boxID>.sy       # Документ верхнего уровня блокнота
├── <docA>.sy        # Логический дочерний документ <boxID>.sy
├── <docA>/          # Физический каталог дочерних документов docA
│   └── <docB>.sy
└── <docC>.sy        # Другой логический дочерний документ <boxID>.sy
```

Ядро отображает виртуальные пути, начинающиеся с `/<boxID>/`, обратно в физический корневой путь блокнота. Документ верхнего уровня блокнота нельзя переместить или удалить. После создания этого документа отключение функции лишь скрывает его в обычном интерфейсе и результатах поиска, не удаляя соответствующий файл `.sy`.

## 5. Метаданные блокнота: `<boxID>/.siyuan/`

В каталоге каждого блокнота есть скрытый каталог `.siyuan/`, который может содержать:

| Файл | Назначение |
|---|---|
| `conf.json` | Конфигурация блокнота (BoxConf) |
| `sort.json` | Опциональное пользовательское отображение сортировки документов `{docID: order}` |
| `boxDoc.json` | Опциональный; идентифицирует документ верхнего уровня блокнота при импорте и экспорте `.sy.zip` |
| `notebook-crypto-backup.json` | Опциональная резервная копия обёрнутого ключа шифрования данных зашифрованного блокнота |

Структура `BoxConf`:

| Поле | Тип | Значение |
|---|---|---|
| `name` | string | Отображаемое имя блокнота |
| `sort` | int | Вес сортировки |
| `icon` | string | Значок (hex-код emoji, напр. `"1f3af"`; имя файла пользовательского значка; или URL изображения HTTP(S)) |
| `closed` | bool | Закрыт ли блокнот |
| `refCreateSaveBox` | string | Целевой блокнот для создания документа при ссылке на блок |
| `refCreateSavePath` | string | Целевой путь для создания документа при ссылке на блок |
| `docCreateSaveBox` | string | Целевой блокнот для создания нового документа |
| `docCreateSavePath` | string | Целевой путь для создания нового документа |
| `dailyNoteSavePath` | string | Путь сохранения новых ежедневных заметок (поддерживает шаблоны) |
| `dailyNoteTemplatePath` | string | Путь шаблона для новых ежедневных заметок |
| `sortMode` | int | Способ сортировки |
| `encrypted` | bool | Является ли блокнот зашифрованным |
| `boxCrypt` | object или null | Обёрнутый ключ шифрования данных блокнота и метаданные обёртки; не null в зашифрованном блокноте |

Зашифрованный блокнот по-прежнему сохраняет в открытом виде имя, состояние закрытия и обёртку ключа, необходимую для восстановления, но `icon`, `sort` и `sortMode` на верхнем уровне хранят только нейтральные значения, а реальные значения находятся в аутентифицированном шифротексте `boxCrypt.metadata`; `GetConf` восстанавливает эти значения в памяти только после разблокировки блокнота.

> ⚠️ **ID блокнота отсутствует в `conf.json`** — ID является самим именем каталога блокнота (см. правила определения в §3).

Место чтения и записи: `GetConf` / `SaveConf`. Путь жёстко задан как `<DataDir>/<boxID>/.siyuan/conf.json`.

`boxDoc.json` содержит версию спецификации метаданных и ID документа верхнего уровня. Во время работы ядро выводит этот ID документа напрямую из `box.ID`; файл метаданных сохраняется для того, чтобы процесс импорта `.sy.zip` мог распознать документ верхнего уровня исходного блокнота и переназначить его на ID целевого блокнота.

Зашифрованный блокнот сохраняет метаданные восстановления в `conf.json` и `notebook-crypto-backup.json`, но его файлы `.sy`, локальные ресурсы блокнота и определения представлений атрибутов хранятся на диске в зашифрованном виде. Подробности о границах шифрования, изоляции баз данных и восстановлении см. в [ENCRYPTED-NOTEBOOK.zh-CN.md](./ENCRYPTED-NOTEBOOK.zh-CN.md).

## 6. Общая конфигурация рабочей области: `<workspace>/conf/conf.json`

Важно различать два файла `conf.json`:

| Файл | Расположение | Область действия |
|---|---|---|
| `conf/conf.json` | **Корень рабочей области** | Общая конфигурация уровня рабочей области (глобальные секции appearance / langs / system / editor / sync / repo и т. д.) |
| `<boxID>/.siyuan/conf.json` | **Внутри блокнота** | Только данный блокнот (BoxConf) |

`conf/conf.json` содержит настройки уровня рабочей области: внешний вид UI, учётную запись, синхронизацию, ИИ, карточки повторения и т. д.

## 7. Скрытая конфигурация уровня рабочей области: `data/.siyuan/`

`data/.siyuan/` отличается от `.siyuan/` внутри блокнота тем, что содержит правила и состояния **уровня рабочей области**:

| Файл | Назначение |
|---|---|
| `syncignore` | Правила игнорирования синхронизации (в стиле gitignore) |
| `searchignore` | Игнорирование поиска |
| `embeddingignore` | Игнорирование AI embedding |
| `indexignore` | Игнорирование индексации |
| `refsearchignore` | Игнорирование поиска обратных ссылок |
| `publishAccess.json` | Контроль доступа при публикации |
| `filesys_status_check/` | Состояние проверки согласованности файловой системы |
| `data-crypto-backup.json` | Резервная копия глобального KDF зашифрованных данных и верификатора для синхронизации и восстановления |
| `master-password-migration.json` | Временное состояние аварийного восстановления, используемое при смене мастер-пароля |

Большинство этих элементов опциональны и создаются только при использовании соответствующих функций.

> Здесь **нет** `conf.json` — общая конфигурация рабочей области находится в `conf/conf.json` в корне рабочей области (см. §6).

## 8. Файлы ресурсов (`assets`)

Сосуществуют два набора:

1. **Глобальный уровня рабочей области `data/assets/`** — основной. Правило именования имеет вид `<исходное_имя>-<NodeID>.<ext>` (например, `640-20240927104411-0jh7x96.webp`). Внутри документа указывается относительный путь `assets/xxx`.
2. **Уровня блокнота `<notebook>/assets/`** — используется встроенным руководством пользователя и обязателен для зашифрованных блокнотов; в обычных незашифрованных пользовательских блокнотах обычно отсутствует.

Распознавание префиксов ссылок на ресурсы: допустимыми ссылками на файлы ресурсов считаются только префиксы `assets/`, `emojis/`, `plugins/`, `public/`, `widgets/`.

Зашифрованный блокнот обязан использовать локальные файлы ресурсов блокнота. Содержимое ресурса и его исходное имя хранятся в одном зашифрованном контейнере, а физическое имя файла использует обезличенный формат `<16 случайных символов>-<blockID>.<ext>`, поэтому прямое изучение диска не позволяет восстановить исходное имя файла ресурса. Подробнее см. в [Формат зашифрованных файлов](./ENCRYPTED-NOTEBOOK.zh-CN.md#sy--assets--数据库文件加解密).

## 9. Связь между ID и путями

### Формат ID

- **NodeID**: `YYYYMMDDHHMMSS-xxxxxxx` (14-значная временная метка + `-` + 7 случайных символов).
- ID блокнота и ID документа используют один и тот же формат NodeID; документ верхнего уровня блокнота напрямую использует NodeID своего блокнота.
- Первые 14 символов — это время создания (извлекается `TimeFromID`).
- Набор случайных символов: `[a-z0-9]`.

### Имя файла = ID (жёсткое ограничение)

- Имя файла `.sy` документа (без суффикса `.sy`) = `rootID` документа.
- Имя каталога блокнота = ID блокнота.
- Имя файла и `rootID` документа верхнего уровня блокнота равны ID блокнота, то есть `<boxID>.sy`.
- Ядро требует `ID имени файла == root.ID`; при несоответствии для незашифрованных документов оно автоматически исправляется, а зашифрованные документы отклоняются при загрузке.

Всё вышеперечисленное — физические идентификаторы. Отображаемое имя блокнота берётся из `BoxConf.name`, а отображаемый заголовок документа — из свойств корневого блока; ни то ни другое не обязано соответствовать формату NodeID.

### Абсолютный путь документа

Абсолютный путь документа на диске = `data/<boxID>/<относительный_путь>`, где `<относительный_путь>` имеет вид `/20221126104620-m06prws/20230928134805-z11t56h.sy` (начинается с `/`, в стиле POSIX).

Получение ID документа из пути (`GetTreeID`): `filepath.Base(путь)` без суффикса `.sy`.

## 10. Как выводится HPath (человекочитаемый путь)

HPath **не является авторитетными данными, хранящимися в исходном файле `.sy`**, а выводится при загрузке документа через `LoadTreeByData` и может кэшироваться в перестраиваемых индексах, таких как `blocktree.db`:

1. Собственный относительный путь документа разбивается по `/`, отбрасывается начальный пустой сегмент и конечный собственный сегмент, что даёт **сегменты ID всех родительских документов**.
2. Для каждого родительского ID составляется `<родительский_ID>.sy`, и с помощью `DocIAL()` (**потоковое чтение только `Properties`** без парсинга всего дерева) считывается `title` этого родительского документа. Зашифрованный файл `.sy` должен быть сначала полностью прочитан и расшифрован, прежде чем можно будет разобрать свойства.
3. Все `title` соединяются через `/`, а в конец добавляется `title` текущего документа → получается HPath вида `/Заголовок_родителя/Заголовок_потомка/Текущий_заголовок`.
4. Если какой-то родительский `.sy` отсутствует, ядро **автоматически создаёт** родительский документ `Untitled` (соответствует issue #7376).

> В этом состоит фундаментальная причина принципа «структура каталогов = данные»: **перемещение или переименование файла/каталога напрямую изменяет HPath документа и навигационную цепочку (хлебные крошки)** — потому что HPath полностью выводится из цепочки каталогов.

Документ верхнего уровня блокнота обрабатывается особым образом: его API HPath равен `/`, полный человекочитаемый путь — это имя блокнота; обычные документы корневого уровня логически отображаются как его подчинённые документы, но физически файлы по-прежнему хранятся непосредственно в каталоге блокнота.

## 11. Рекомендации при прямой работе с файловой системой

> В соответствии с [SY-FORMAT.zh-CN.md §0.5](./SY-FORMAT.zh-CN.md#05-何时直接读写-sy优先级): **изменение данных предпочтительно выполнять через HTTP API / MCP / CLI**, чтобы ядро отвечало за синхронизацию индексов. Прямая работа с файловой системой предназначена только для массовой офлайн-миграции, холодной инициализации и подобных сценариев.

Не изменяйте напрямую постоянные файлы зашифрованных блокнотов. Raw-API файлов отклоняет чтение, перечисление или изменение каталогов зашифрованных блокнотов. При офлайн-проверке защищённого содержимого виден только шифротекст, однако несодержимые метаданные вроде `conf.json` по-прежнему читаемы. После разблокировки блокнота следует использовать специализированные API для сохранения согласованности шифрования, аутентификации и изолированных индексов.

При прямой записи на диск обязательно проверьте:

1. ☐ Физические ID блокнотов и документов соответствуют формату NodeID и **избегают зарезервированных имён** (§3).
2. ☐ Имя файла `.sy` документа == `rootID` документа (§9).
3. ☐ Для документа с дочерними документами обязательно наличие **сопутствующего одноимённого каталога**; при перемещении родительского документа перемещайте одноимённый каталог вместе с ним (§4).
4. ☐ Не перемещайте документы корневого уровня в `<boxID>/<boxID>/`; документ верхнего уровня блокнота использует виртуальное отображение путей «родитель–потомок» (§4).
5. ☐ Имя, значок и состояние закрытия блокнота записываются в `<boxID>/.siyuan/conf.json`; при наличии `<boxID>.sy` имя и значок синхронизируются с ним (§5).
6. ☐ Рассматривайте `data/storage/` как постоянные исходные данные, а `temp/*.db` — как перестраиваемые индексы, не путая их жизненные циклы (§3).
7. ☐ После изменений обычно требуется **перестроить индекс**, иначе поиск, ссылки на блоки и хлебные крошки перестанут работать.
