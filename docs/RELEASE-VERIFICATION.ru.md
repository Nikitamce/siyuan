# Процесс выпуска, сборка и проверка установочных пакетов

<!-- release-version: 3.8.11 -->

> **Область применения: `scripts/build-release.py` — официальный скрипт упаковки SiYuan, предназначенный исключительно для официальной среды выпуска; не используйте его в других средах. Скрипт зависит от структуры каталогов, цепочки инструментов, конфигурации WSL и среды подписи официальной сборочной машины и не является универсальным инструментом упаковки.**

Требуется Python 3.11 или более новая версия. Проверка установочных пакетов не требует изменения процесса упаковки или переноса эталонных файлов с других машин. Для форматов EXE, DMG, AppImage, DEB, RPM и т.д. также требуется 7-Zip (путь можно указать через `--sevenzip`).

## Распределение задач при выпуске

- Стабильные версии собираются локально, агрегируются, проверяются и публикуются вручную в соответствии с инструкциями ниже
- Версии alpha, beta и rc автоматически публикуются через GitHub Actions: после подготовки и синхронизации версий основного репозитория и репозитория Android отправляется соответствующий тег предвыпуска; одноимённые артефакты релиза вручную не загружаются

## Шаги выпуска версии для разработки

Для alpha, beta и rc используются семантические номера версий предвыпуска, например `3.8.11-alpha.1`, `3.8.11-beta.1`, `3.8.11-rc.1`. Ниже в качестве примера используется `3.8.11-beta.1`; при выполнении замените его на текущую версию. Автоматический выпуск выполняется [рабочим процессом CD](../.github/workflows/cd.yml), запускать локальный скрипт сборки для четырёх платформ не требуется.

### 1. Подготовка версии и синхронизация кода

- Установите `Mode` в `kernel/util/working.go` в значение `prod`, обновите `Ver` и версию в `app/package.json` до одного и того же номера предвыпуска
- Обновите `siyuanVersionName` и `siyuanVersionCode` в `build.gradle` репозитория Android; имя версии должно совпадать с основным репозиторием
- Сначала отправьте коммит подготовки релиза Android в удалённую ветку `main`; рабочий процесс проверяет версию из этой ветки и фиксирует используемый коммит Android для данной сборки, не переключая репозиторий Android по тегу основного репозитория
- Зафиксируйте и отправьте подготовленный к релизу код основного репозитория, убедившись, что текущая рабочая копия находится на этом релизном коммите
- Убедитесь, что конфигурация подписи Android и учётные данные, необходимые для Actions репозитория, доступны; учётные данные управляются только через Secrets репозитория и не записываются в документацию или исходный код

### 2. Создание тега и запуск сборки

Выполните в корневом каталоге основного репозитория, отправив только текущий тег:

```powershell
git tag v3.8.11-beta.1
git push origin v3.8.11-beta.1
```

Отправка тега, содержащего `-alpha`, `-beta` или `-rc`, запускает `CD For SiYuan`, а также сборку предрелизного образа в [Release Docker Image](../.github/workflows/dockerimage.yml). Тег после удаления начальной `v` должен полностью совпадать с версией в `app/package.json`, а версия Android также должна совпадать, иначе этап подготовки завершится ошибкой. Для предрелизных образов публикуется только тег `v` с номером версии, тег `latest` не обновляется.

### 3. Ожидание автоматической сборки и публикации

Отслеживайте соответствующий запуск `CD For SiYuan` для данного тега в GitHub Actions. Рабочий процесс генерирует примечания к выпуску, выполняет проверки и собирает следующие восемь установочных пакетов:

| Платформа | Автоматически публикуемые артефакты |
| --- | --- |
| Windows | Установщик NSIS для AMD64 |
| Linux | AppImage, tar.gz, deb, rpm для AMD64 (всего четыре пакета) |
| macOS | Два DMG для Intel и Apple Silicon |
| Android | Официальный ARM64 APK |

Версии для разработки в настоящее время не публикуют автоматически Windows ARM64, Linux ARM64, Appx, HarmonyOS, iOS или другие канальные пакеты Android и не используют полный список всех платформ стабильной версии.

Рабочий процесс автоматически генерирует и проверяет `SHA256SUMS.txt`, создаёт черновик предвыпуска, загружает установочные пакеты и файл контрольных сумм, затем сверяет контрольные суммы удалённых ресурсов и при полном совпадении автоматически публикует предвыпуск. Здесь контрольные суммы генерируются GitHub Actions; локальный скрипт сборки стабильной версии по-прежнему не генерирует контрольные суммы — их в конце вручную создаёт публикатор своим инструментом.

### 4. Проверка результатов и обработка сбоев

- Убедитесь, что текущий рабочий процесс завершён, проверьте журналы тестов; для части тестов допускается продолжение после сбоя, поэтому успешный релиз не означает прохождение всех тестов
- Убедитесь, что GitHub Release для соответствующего тега опубликован и помечен как pre-release, версия верна, а все восемь установочных пакетов и `SHA256SUMS.txt` загружены
- Если сборка или загрузка завершились ошибкой, сначала проверьте упавший шаг и статус существующего Release; после устранения проблем среды можно перезапустить упавшие задания, а при изменении исходного кода или версии используйте новый номер предвыпуска и тег
- При загрузке рабочий процесс перезаписывает одноимённые ресурсы; не загружайте файлы вручную одновременно и не публикуйте черновик заранее; если существующий Release уже опубликован, проверка черновика заблокирует последующую автоматическую загрузку

## Шаги выпуска стабильной версии

Если не указано иное, все следующие команды выполняются в корневом каталоге репозитория `D:\88250\siyuan` на официальной сборочной машине Windows.

### 1. Подготовка к выпуску

Сгенерируйте список изменений (changelogs) для данной стабильной версии, завершите подготовку релиза в ветке `dev` основного репозитория, а в остальных репозиториях убедитесь, что они переключены на свои релизные ветки. Ветка `master` используется для официального выпуска и принимает код из `dev` через релизный PR.

Укажите текущую стабильную версию в корневом каталоге основного репозитория и сначала просмотрите план подготовки:

```powershell
python -X utf8 scripts/prepare-release.py 3.8.11
```

Скрипт обновляет примеры версий в этом документе (включая URL загрузки), а также версии ядра, фронтенда, Appx, Android, HarmonyOS и официального сайта `b3log-index`. Локально уже должен присутствовать репозиторий `b3log-index` (по умолчанию на одном уровне с основным репозиторием). Проверив версии и пути в плане, выберите один из следующих вариантов выполнения.

Только изменить файлы, оставив проверку и коммит человеку:

```powershell
python -X utf8 scripts/prepare-release.py 3.8.11 --execute
```

Убедившись, что все отслеживаемые изменения в основном репозитории, Android и HarmonyOS предназначены для релиза, а ветка `b3log-index` верна и не содержит конфликтов или посторонних правок, просмотрите план коммита и отправки, затем выполните:

```powershell
python -X utf8 scripts/prepare-release.py 3.8.11 --publish
python -X utf8 scripts/prepare-release.py 3.8.11 --publish --execute
```

`--publish --execute` сначала завершает подготовку версий, затем фиксирует и отправляет все отслеживаемые изменения основного репозитория, Android и HarmonyOS, создаёт и отправляет тег Android, а также собирает, проверяет, фиксирует и отправляет официальный сайт. Перед выполнением обработайте неотслеживаемые файлы и проверьте ветки в каждом репозитории; сервер официального сайта развёртывается после публикации и проверки установочных пакетов. Подробнее о параметрах и обработке ошибок см. в разделе [Описание скрипта подготовки к выпуску](#описание-скрипта-подготовки-к-выпуску).

Если репозитории уже зафиксированы и отправлены вручную, можно создать локальный тег только при совпадении версии текущего коммита Android и чистом рабочем дереве, а затем отправить его самостоятельно:

```powershell
python -X utf8 scripts/prepare-release.py 3.8.11 --tag-android --execute
```

Скрипт подготовки по умолчанию использует `siyuan-android`, `siyuan-harmony`, `b3log-index` на одном уровне с основным репозиторием; пути можно задать через `--android-dir`, `--harmony-dir`, `--index-dir`. Тег стабильной версии основного репозитория создаётся при публикации Release на GitHub, репозиторий iOS по-прежнему требует ручной подготовки и синхронизации.

После фиксации и отправки всех релизных изменений запишите полный SHA текущего сборочного коммита основного репозитория с помощью `git rev-parse HEAD`, а также соответствующие коммиты репозиториев других платформ. С начала сборки и до слияния релизного PR удерживайте `dev` на этом коммите; все сборочные машины должны использовать один и тот же коммит основного репозитория. Если в этот период добавляются изменения, которые нужно включить в данный релиз, сначала зафиксируйте и отправьте их, затем пересоберите всё заново начиная со сборки фронтенда, заново запишите сборочный коммит и проверьте артефакты; нельзя повторно использовать старые пакеты только на основании совпадения номера версии.

### 2. Проверка условий автоматической синхронизации WSL

Когда сборка включает Linux или HarmonyOS, `build-release.py --execute` на этапе предварительной проверки автоматически синхронизирует репозиторий WSL без ручного pull. По умолчанию используется пользователь `d` и `/home/d/88250/siyuan`; каталог должен уже содержать репозиторий и рабочий удалённый репозиторий `origin`.

Синхронизация WSL выполняется до проверки среды и проверки сертификата подписи. Если для SSH требуется парольная фраза закрытого ключа, введите её по запросу после запуска скрипта; проверки и сборка продолжатся только после завершения синхронизации, и при последующих этапах сборки репозиторий повторно не вытягивается. Если ключ разблокирован через SSH-агент или коммиты на обеих сторонах совпадают, запрос ввода не появится. Скрипт не сохраняет парольные фразы. В Windows при запуске по умолчанию один раз скрыто вводится PIN-код подписи, а после прохождения предварительной проверки подпись выполняется автоматически; если устройство требует касания или используется `--signing-ui`, по-прежнему требуется ручное взаимодействие.

Если коммиты на обеих сторонах различаются, скрипт требует отсутствия незафиксированных или неотслеживаемых файлов как в Windows, так и в WSL, получает текущую ветку Windows из `origin` в WSL, проверяет, что текущий коммит Windows уже присутствует в этой удалённой ветке и содержит текущий коммит WSL, и затем переключается на точный коммит Windows в состоянии detached HEAD. Он не следует за последующими новыми коммитами в удалённом репозитории и не выполняет принудительный сброс, очистку или stash локальных изменений; при наличии неотправленных коммитов, расхождения веток или опережения WSL скрипт останавливается для вмешательства публикатора. Если обе стороны уже на одном коммите, синхронизация пропускается и продолжается проверка согласованности входных данных сборки. При просмотре плана синхронизация не выполняется.

### 3. Подготовка среды сборки

- Подготовьте Go, Node, pnpm, компиляторы Windows для обеих архитектур, gomobile, Android SDK/NDK, DevEco Studio и 7-Zip; для Appx также требуется `electron-windows-store`
- Кэш архивов среды выполнения OCR находится в `.cache/ocr/` проекта; при ручной загрузке сохраняйте исходное имя файла без распаковки, скрипт проверит контрольную сумму и использует его повторно
- Остановите запущенные dev-сборки фронтенда
- Подключите YubiKey и при запуске сборки скрыто введите PIN-код подписи один раз
- Убедитесь в доступности конфигурации подписи Android и HarmonyOS
- Не оставляйте старые версии или одноимённые установочные пакеты в папке `siyuan` на рабочем столе; при поэтапной сборке сохраняйте уже проверенные артефакты других платформ текущей версии

### 4. Просмотр плана

```powershell
python -X utf8 scripts/build-release.py --appx
```

Эта команда только отображает план, не выполняет сборку, не изменяет файлы и не проверяет инструменты сборки или среду подписи.

### 5. Выполнение сборки

Одновременная сборка Windows, WSL Linux, Android и HarmonyOS. Для стабильной версии требуются два пакета Appx, сохраняйте `--appx`:

```powershell
python -X utf8 scripts/build-release.py --appx --execute
```

При одновременном выборе Windows и Linux WSL во время сборки Windows заранее проверяет цепочку инструментов и устанавливает зависимости фронтенда Linux. После установки зависимостей Linux ожидает успешной упаковки Windows, затем собирает фронтенд и ядро Linux. После завершения Windows упаковка приложения Android (если выбрана) выполняется параллельно со сборкой Linux. При выборе Windows сначала подготавливаются ресурсы Windows, затем одновременно компилируются ядра AMD64, ARM64 и выбранное ядро Android (по умолчанию до трёх задач параллельно). Как только ядро AMD64 готово и проверено, сразу начинается его упаковка без ожидания Android; когда готово ядро ARM64 и завершена упаковка AMD64, выполняется упаковка ARM64. Установщики Windows и подпись всегда выполняются последовательно, компиляция Android может продолжаться в это время, а этап Android повторно использует уже скомпилированный AAR. Можно передать `--kernel-jobs 2` для ограничения до двух задач или `--kernel-jobs 1` для возврата к последовательной компиляции этой части ядер.

Linux настраивает зеркало загрузки перед первым вызовом Go и проверяет необходимую цепочку инструментов перед сборкой фронтенда; загрузка цепочки инструментов по-прежнему включает проверку контрольных сумм и завершается досрочно при сбое сети или проверки. Фронтенд Linux собирается один раз, ядра AMD64 и ARM64 компилируются параллельно с использованием отдельных выходных каталогов; установочные пакеты Electron по-прежнему генерируются последовательно. При одновременном выборе Linux и HarmonyOS во время генерации установочных пакетов Linux параллельно компилируется ядро HarmonyOS ARM64; после успеха ядра отправляется маркер готовности текущей сборки, и этап HarmonyOS немедленно проверяет версию, архитектуру и заголовочные файлы и начинает упаковку приложения, не дожидаясь завершения пакетов Linux или Android. Если выбран только HarmonyOS, ядро по-прежнему компилируется на этапе HarmonyOS. При сбое любой параллельной задачи остальные отменяются; при прерывании завершаются дерево дочерних процессов Windows и группа процессов сборки WSL.

Параллельные этапы раздельно записывают статус и артефакты; поле `current_stages` в `progress.json` перечисляет все выполняющиеся этапы, а `current_stage` представляет собой совместимую сводку через запятую. Запись блокируется и обновляется атомарно; артефакты каждой платформы по-прежнему должны проходить прежние проверки свежести, версии и контрольной суммы при копировании.

Для команды упаковки обеих архитектур Linux жёстко задаётся `ELECTRON_BUILDER_COMPRESSION_LEVEL=5`, чтобы сократить время сжатия `tar.gz`; эта переменная действует только на дочерний процесс Linux Electron Builder. Архивы по-прежнему используют прежний формат, а артефакты должны пройти финальную проверку установочных пакетов.

Журналы параллельной компиляции раздельно сохраняются в `kernel-logs/` текущего временного каталога сборки, а основной журнал фиксирует запуск, завершение и сбои задач. При ошибке компиляции, упаковки или нажатии Ctrl+C очередь останавливается, а ещё работающие процессы компиляции завершаются; неначатые задачи не запускаются. Этап подготовки ресурсов Windows фиксирует только генерацию ресурсов, а этапы упаковки каждой архитектуры могут перекрываться с компиляцией оставшихся ядер.

Если включена сборка Windows, сначала один раз скрыто вводится PIN-код подписи; после прохождения предварительной проверки последующая подпись выполняется автоматически. При просмотре плана или сборке других платформ PIN не запрашивается. SSH-аутентификация WSL по-прежнему выполняется на этапе предварительной проверки — отходите от компьютера только после её прохождения.

При запуске с помощью агента откройте видимый интерактивный терминал на локальной машине для запуска скрипта, чтобы публикатор мог напрямую скрыто ввести PIN-код подписи и возможный последующий запрос парольной фразы SSH-ключа. Не передавайте пароли через чат и не запускайте сборку, требующую аутентификации, неинтерактивной фоновой командой. В корневом каталоге репозитория можно выполнить:

```powershell
Start-Process -FilePath "powershell.exe" -WorkingDirectory "D:\88250\siyuan" -ArgumentList '-NoExit', '-Command', 'python -u -X utf8 scripts/build-release.py --appx --execute'
```

По умолчанию сначала вводится PIN-код подписи Windows, затем на этапе синхронизации WSL по запросу вводится парольная фраза закрытого SSH-ключа. Если журнал остановился на `git fetch`, сначала проверьте, не ожидает ли интерактивный терминал аутентификации, и не запускайте сборку повторно; после завершения аутентификации скрипт продолжит выполнение. `--signing-ui` только переключает подпись Windows на системное диалоговое окно аутентификации и не заменяет терминальное взаимодействие SSH в WSL.

Дополнительно: если нужно собрать отдельную платформу или отладить проблему сборки, выберите соответствующую команду:

```powershell
python -X utf8 scripts/build-release.py --platforms windows --appx --execute
python -X utf8 scripts/build-release.py --platforms linux --execute
python -X utf8 scripts/build-release.py --platforms android --execute
python -X utf8 scripts/build-release.py --platforms harmony --execute
```

Скрипт автоматически собирает и копирует мобильные ядра и ресурсы; артефакты каждой платформы сразу после генерации собираются в папку `siyuan` на рабочем столе без ожидания завершения всех платформ; после окончания сборки всех выбранных платформ выводится только подсказка с командой ручной проверки, без автоматического вызова валидатора пакетов. При сбое сборки последующей платформы уже собранные пакеты сохраняются; успешная сборка не означает, что установочные пакеты прошли проверку. Официальная версия Android именуется `siyuan-версия.apk`, например `siyuan-3.8.11.apk`. Существующие одноимённые пакеты не перезаписываются. Скрипт не генерирует и не обновляет `SHA256SUMS.txt` и не вызывает `checksum.exe`.

При фактическом выполнении скрипт сохраняет записи текущего запуска в `release-records/версия/время-случайный_суффикс/` на одном уровне с основным репозиторием, например `D:\88250\release-records\3.8.11\20260929-093000-xxxxxxxx\`. Полный путь выводится при запуске и завершении и сохраняется даже при сбое сборки. Корневой каталог записей можно задать через `--records-dir`; записи должны храниться отдельно от репозитория исходного кода, каталога установочных пакетов и системного временного каталога. При простом просмотре плана записи не создаются.

| Файл | Содержимое |
| --- | --- |
| `build.log` | Вывод скрипта с временными метками, вывод команд сборки и сообщения об ошибках с одновременным отображением в терминале |
| `progress.json` | Общий статус, статус каждого этапа, время начала и окончания, длительность, пути собранных артефактов, последняя выполненная команда и причина сбоя |

Файл прогресса атомарно обновляется при начале, завершении этапа, выполнении команды и сборе артефактов; Windows AMD64 и ARM64 фиксируются раздельно. Статусы: `pending` (не начат), `running` (выполняется), `succeeded` (завершён), `failed` (ошибка) или `interrupted` (получено прерывание). Завершение общего и платформенных этапов означает только завершение сборки и сбора артефактов, не включает этап проверки пакетов и не генерирует отчёт проверки автоматически; если нужен отчёт, отдельно запустите `verify-release.py check` с флагом `--report`. При нажатии Ctrl+C записывается статус прерывания; при принудительном завершении процесса или отключении питания файл может остаться в состоянии `running`, что не означает продолжение работы. Текущие записи предназначены для просмотра и диагностики и не используются для автоматического возобновления или повторного использования артефактов.

При вытягивании через SSH сохраняется прямое терминальное взаимодействие, вывод терминала и клавиатурный ввод команд аутентификации не перехватываются; в журнал записываются только команды и коды выхода. Возвращаемые значения внутренних команд запросов не записываются напрямую в журнал, а переменные окружения, парольные фразы закрытых ключей и PIN-код YubiKey не сохраняются.

### 6. Сбор артефактов других платформ

Сборка и подпись для macOS и iOS выполняются на соответствующих сборочных машинах. На macOS выполняется нотаризация и собираются DMG для обеих архитектур; на iOS синхронизируются ядро, ресурсы и changelogs, подтверждается номер версии и выполняется сборка для публикации в App Store. Оркестрирующий скрипт Windows не выполняет сборку этих двух платформ.

Соберите распространяемые установочные пакеты с других машин в папку `siyuan` на рабочем столе перед финальной проверкой. iOS после приёмки на соответствующей платформе загружается напрямую в App Store; IPA не собирается в папку на рабочем столе и не проверяется этим скриптом.

Вручную убедитесь, что следующие установочные пакеты в наличии (при поэтапной сборке по платформам часть пакетов может временно отсутствовать, но перед финальным выпуском должны быть собраны все):

### 9. Ручная публикация и размещение в магазинах приложений

Создайте релизный PR на GitHub из ветки `dev` в ветку `master`, убедившись, что исходный коммит совпадает со сборочным коммитом, записанным на шаге 1. Для официального выпуска разрешено использовать `dev` напрямую как источник PR; обычные PR разработки по-прежнему используют отдельные ветки задач и вливаются в `dev`. [Рабочий процесс проверки ветки](../.github/workflows/target-branch.yml) поддерживает этот процесс через `exclude: dev`, а PR в `master` из других веток автоматически перенаправляются в `dev`.

После прохождения проверок выполните слияние релизного PR с помощью **Create a merge commit**, чтобы сохранить полную историю коммитов `dev` и избежать повторного перечисления старых коммитов в последующих PR из-за многократного squash долгоживущей ветки. В настройках репозитория должно быть включено **Allow merge commits**; если настройка запрещает это, сообщите об ограничении и остановите слияние — не используйте squash или rebase для релизного PR. Обновляйте `master` через PR, не отправляя изменения напрямую в `master`.

После слияния получите актуальный `master`, замените `<полный SHA сборочного коммита>` ниже на полный SHA, записанный на шаге 1, и сверьте совпадение дерева файлов со сборочным коммитом; проверка различий не должна выдавать вывод и должна завершиться с кодом `0`, при наличии различий остановите публикацию и выясните причину:

```powershell
git fetch origin master
$releaseCommit = "<полный SHA сборочного коммита>"
git diff --exit-code $releaseCommit origin/master
```

При создании Release на GitHub введите новый тег `v3.8.11`, выберите создание нового тега, целевую ветку `master` и сверьте целевой коммит. При публикации Release тег создаётся самим GitHub, вручную создавать или отправлять тег локально не нужно. Если одноимённый тег уже существует, сначала проверьте, куда он указывает, не перезаписывайте и не создавайте дубликат.

- Загрузите публично распространяемые установочные пакеты и финальный `SHA256SUMS.txt` в GitHub Release репозитория `siyuan-note/siyuan`, сверьте версию, целевой коммит и имена файлов, затем опубликуйте стабильную версию
- Убедитесь, что тег стабильной версии создан, и проверьте статус выполнения [Release Docker Image](../.github/workflows/dockerimage.yml); этот рабочий процесс отслеживает отправку тегов `v*`, для стабильной версии одновременно обновляет `latest`, для предвыпуска публикует только тег версии, а при простом слиянии веток не запускается
- Скачайте установочные пакеты через домен загрузки и сверьте контрольные суммы
- Загрузите на Baidu Netdisk
- Войдите в аккаунт `siyuan` на Liandi (链滴) и опубликуйте анонс
- Синхронизируйте с Gitee
- Измените и разверните Rhy, вставив финальный `SHA256SUMS.txt`
- Разверните Index (обновление версии, сборка и отправка уже выполнены через `--publish --execute` при подготовке к выпуску)
- Выполните публикацию в магазинах приложений: Xiaomi, Huawei, Honor, OPPO, vivo, App Store, Microsoft Store, Tencent MyApp, Google Play, 360 и Tencent PC Manager

Рабочий процесс Docker сначала разрешает или собирает отдельный образ среды выполнения ONNX, а затем передаёт в сборку приложения `ONNX_IMAGE=<репозиторий>@sha256:<дайджест>`. Ключ артефакта включает целевую платформу, базовый образ Alpine, исходный код и версию ONNX, ревизию цепочки инструментов, скрипт сборки и файлы цепочки инструментов; изменения исходного кода приложения, версии приложения и цепочки инструментов Go не инвалидируют артефакт ONNX. При обновлении системных пакетов компиляции необходимо увеличить `ONNX_TOOLCHAIN_REV`, фактические версии пакетов сохраняются в `onnx-toolchain.txt` артефакта. При сбое разрешения, ошибке аутентификации или несовпадении метаданных артефакта публикация останавливается без отката на другие версии.

Компиляция ONNX для ARM32 использует нативный Clang сборочной машины, целевые файлы разработки Alpine и нативный `protoc`, собранный из зафиксированных зависимостей, чтобы избежать запуска компилятора C++ под QEMU; финальные установочные пакеты по-прежнему должны пройти прежнюю поплатформенную приёмку реального OCR и чтения/записи блокнотов. Отдельный артефакт сохраняет лицензию ONNX и уведомления сторонних компонентов. Журналы сборки и отчёт разрешения артефактов загружаются вместе с записями платформы. Первичная проверка должна включать холодную сборку ARMv7, повторное использование при тех же входных данных, повторное использование после изменений приложения и инвалидацию при изменении входных данных ONNX; соответствующая регрессия скрипта запускается через `python -m unittest discover -s scripts -p test_docker_release.py`.

При завершении рабочий процесс Docker очищает теги-кандидаты `build-<runId>-<attempt>-<platform>` и `build-<runId>-<attempt>-verified`: при успешном текущем выпуске немедленно очищаются все теги-кандидаты в репозитории, включая оставшиеся от предыдущих неудачных или отменённых запусков. Если текущий запуск не завершился успешным выпуском, кандидаты сохраняются для повторных попыток и диагностики; они будут очищены при завершении следующего успешного выпуска. Теги `v*`, `latest`, `buildcache-*` и `onnx-*` не участвуют в очистке, а репозиторий кэша и параллельная сборка не изменяются. Очистка использует существующие Secrets `DOCKER_HUB_USER` и `DOCKER_HUB_PWD`, учётные данные должны иметь права на удаление тегов; сбой очистки не меняет результат выпуска, журнал можно проверить в задании `Clean up build candidate tags`. `scripts/cleanup-docker-tags.py` по умолчанию работает в режиме предпросмотра и удаляет теги только при передаче `--execute`; эта операция не гарантирует освобождение хранилища, занятого общими слоями образов.

### 10. Синхронизация истории выпуска обратно в dev

После официального выпуска и перед продолжением разработки получите актуальные удалённые коммиты в чистой рабочей области `dev`, влейте опубликованный `master` обратно в `dev` и отправьте изменения. При выполнении агентом слияние требует разрешения пользователя, а отправка (push) требует явного разрешения; сам процесс выпуска не даёт разрешения на незапрошенные слияния, теги, загрузки или публичную публикацию, а также на прямые коммиты или отправку в `master`. Используйте обычное слияние для сохранения истории обеих веток, не сбрасывайте и не делайте force push в `dev`. Если после выпуска с обеих сторон не было новых изменений кода, дерево файлов до и после синхронизации должно быть полностью идентичным; при наличии других изменений или конфликтов сначала проверьте и устраните их.

Для исторических выпусков, где использовался squash, эта синхронизация также необходима: она позволяет `dev` включить релизный коммит и обновить общего предка, хотя и не устраняет дублирование исходных коммитов в списке коммитов последующих PR. Для всех последующих выпусков единообразно используется обычное слияние, чтобы эти исходные коммиты попадали в историю `master`.

При выполнении операций с помощью агента слияние веток и отправка требуют соответствующего явного разрешения; запрос только на изменение документации или сборку установочных пакетов не включает коммит, отправку, создание тегов или публичную публикацию.

### 11. Очистка артефактов выпуска

После завершения выпуска, подтверждения сбора и прохождения проверки установочных пакетов в папке `siyuan` на рабочем столе остановите все задачи сборки и выполните в основном репозитории Windows:

```powershell
# Предпросмотр путей очистки
python -X utf8 scripts/clean-release.py

# Фактическая очистка
python -X utf8 scripts/clean-release.py --execute
```

Скрипт очищает системные временные каталоги сборки, оставленные скриптом выпуска, локальный и WSL `app/build`, каталоги ядра Linux, а также выходные каталоги сборки в проектах Android и HarmonyOS. Сохраняются `app/libs/kernel.aar` и `app/src/main/assets/app.zip` в проекте Android, библиотеки ядра и заголовочные файлы в `entry/libs/`, общие заголовочные файлы в `entry/src/main/cpp/include/` и `entry/src/main/resources/rawfile/app.zip` в проекте HarmonyOS, а также библиотеки ядра и заголовочные файлы в локальном и WSL `kernel/harmony/`. Папка `siyuan` на рабочем столе, файлы под управлением Git, исходный код, конфигурация подписи, кэши зависимостей и инструментов, а также dev-фронтенд `app/stage/build` сохраняются. Копии в системном временном каталоге сборки по-прежнему удаляются вместе с временным каталогом, не затрагивая уже скопированные в мобильные проекты файлы.

Если параметры сборки переопределялись, при очистке передайте те же `--android-dir`, `--harmony-dir`, `--wsl-distro`, `--wsl-user`, `--wsl-repo`; при использовании пользовательского каталога сбора обязательно передайте `--output` для его защиты, а при использовании пользовательского каталога записей — тот же `--records-dir`. Каталог записей выпуска по умолчанию `release-records` всегда сохраняется. `--skip-wsl` позволяет очистить только локальный Windows. Скрипт отклоняет выходящие за границы пути, цели, пересекающиеся с защищёнными каталогами, и точки очистки, являющиеся ссылками сами или имеющие ссылки в родителях; для символических ссылок и соединений каталогов (junctions) внутри каталога сборки удаляется только сама ссылка, без очистки целевого каталога. Артефакты сборки macOS или iOS на других компьютерах не очищаются.

### 12. Ожидание завершения GitHub Actions и развёртывание руководства пользователя

В завершение дождитесь выполнения связанных с данным выпуском GitHub Actions, убедитесь, что сборка для развёртывания руководства пользователя прошла успешно и её версия совпадает с текущим выпуском, и затем разверните руководство пользователя. При сбое рабочего процесса сначала устраните причину сбоя и развёртывайте только после успеха.

## Описание скрипта подготовки к выпуску

- Необходимо обязательно передать целевой номер стабильной версии; скрипт устанавливает `Mode` ядра в `prod`, синхронизирует версии всех платформ и обновляет примеры на основе маркера `release-version` в верхней части документа (сохраняйте этот маркер)
- При изменении имени версии Android и HarmonyOS их коды версий (versionCode) увеличиваются на 1, при повторном запуске для той же версии больше не увеличиваются; их можно задать явно через `--android-code`, `--harmony-code`
- `--publish` отправляет текущую ветку каждого репозитория без автоматического переключения веток; удалённая ветка должна быть предком локального HEAD, неотслеживаемые файлы должны быть предварительно обработаны вручную, force push и перезапись существующих тегов не выполняются
- `--execute` на этапе подготовки версии обновляет `src/siyuan/src/version.pug` официального сайта, но не собирает и не отправляет сайт; версия в `package.json` проекта сайта не изменяется
- `--publish --execute` после завершения подготовки версий выполняет `pnpm install --frozen-lockfile` и `pnpm run build` в `b3log-index/src/siyuan`, проверяет китайскую и английскую страницы, затем фиксирует и отправляет файлы версий и скомпилированные страницы
- На официальном сайте допускаются изменения только файлов версий и скомпилированных страниц, а также добавление новых скомпилированных страниц; при сбое сборки или проверки файлы сохраняются для диагностики, а при отсутствии изменений содержимого пустой коммит не создаётся
- Межрепозиторный выпуск не является атомарной операцией: после сбоя проверьте уже выполненные шаги и повторно запустите ту же команду; если содержимое уже опубликованной версии нужно изменить, используйте новый номер версии

## Прямая проверка установочных пакетов

Поместите установочные пакеты в папку `siyuan` на рабочем столе и выполните в корневом каталоге репозитория:

```text
python -X utf8 scripts/verify-release.py check
```

По умолчанию версия релиза определяется из имени пакета. Если версии смешаны, имя пакета не содержит версию или нужно явно проверить целевую версию, укажите её:

```text
python -X utf8 scripts/verify-release.py check --version 3.8.11
python -X utf8 scripts/verify-release.py check D:/releases/siyuan --version 3.8.11 --report D:/releases/verification.json
```

Путь к отчёту должен указывать на ещё не существующий файл `.json`. Код возврата `0` означает, что все пакеты прошли текущую проверку, `1` — ошибку или невозможность проверки. Проверка не запускает установщики, ядро или JavaScript внутри пакетов и не изменяет пакеты; для каждого пакета используется отдельный временный каталог, который очищается после проверки.

### Что проверяется

- Считывает версию из полного идентификатора `SiYuan v… (pdfcpu ` в ядре PE, ELF или Mach-O, скомпилированного из `util.Ver` в `kernel/model/export.go`; также перекрёстно проверяет распознаваемые полные идентификаторы версии десктопного CLI, не принимая произвольную подстроку версии за успешную проверку
- Проверяет совпадение версии ядра с версией релиза и выявляет определяемые ошибки архитектуры и формата ядра
- Проверяет обязательные точки входа фронтенда: десктопные пакеты должны содержать `app/index.html`, `app/window.html`, `desktop/index.html`, `mobile/index.html` и `export/protyle-method.js`, мобильные пакеты — `mobile/index.html` и `export/protyle-method.js` (все пути относительно `stage/build/`); отсутствие всего каталога фронтенда также приводит к ошибке
- Считывает `Constants.SIYUAN_VERSION` из JavaScript, на который фактически ссылается HTML, проверяет согласованность фронтенда и ядра, не позволяя новым неиспользуемым файлам маскировать старую точку входа
- Проверяет разрешимые локальные ссылки на ресурсы в HTML и CSS, а также карту хэшей числовых чанков текущего webpack, выявляя отсутствующие скрипты, стили, шрифты или динамические чанки
- Проверяет версию фронтенда экспорта, JSON языков, руководство пользователя и текущий список изменений стабильной версии; десктопные пакеты должны содержать `app/package.json` в корне ресурсов, версия в котором должна совпадать с версией релиза
- Распаковывает внутренние архивы NSIS, мобильный `app.zip`, AAB, APP и содержимое пакетов Linux; для HarmonyOS поддерживается только APP — из него извлекается внутренний HAP для проверки ядра и ресурсов, отдельная проверка файлов HAP не поддерживается
- macOS не требует наличия соответствующих артефактов сборки на текущей машине; при невозможности полной распаковки через 7-Zip проверка завершается явной ошибкой
- При распаковке символические ссылки пропускаются, чтобы избежать ошибок нехватки прав при создании ссылок в Windows для таких пакетов, как AppImage; ошибки распаковки обычных файлов по-прежнему вызывают сбой, а отсутствие обязательных точек входа, ядра или ссылаемых ресурсов не проходит проверку; сами ссылки в область проверки не входят

Текущие регрессионные тесты в основном используют макеты установочных пакетов, а тесты загрузки конфигурации используют установленный на машине Electron Builder. Поддерживаемых вместе с документацией проверяемых записей приёмки реальных установочных пакетов нет, поэтому на этом основании нельзя утверждать, что текущая версия для какой-либо платформы прошла проверку на реальном пакете. Перед официальным использованием следует провести приёмку по платформам и сохранить версию пакета, SHA256, версии инструментов и отчёт проверки; прохождение тестов не равнозначно успешной реальной сборке, подписи или установке.

### Границы проверки

По одному только установочному пакету нельзя доказать, что «среди нескольких сборок с одинаковым номером версии это последняя сборка», а также нельзя доказать побайтовую идентичность всех ресурсов текущему исходному коду. Скрипт способен выявить старую версию ядра, старую версию фронтенда и отсутствие разрешимых ссылок. Иконки без единого идентификатора релиза, версии сторонних библиотек и произвольные URL, формируемые во время выполнения, не могут быть полностью проверены автоматически.

Неизвестные файлы или каталоги, пустые каталоги, сбои распаковки и нераспознанные версии не проходят проверку. `checksum.exe`, `SHA256SUMS.txt`, `.blockmap`, YAML-метаданные обновлений и опциональный эталонный JSON не обрабатываются как установочные пакеты. Автономный скрипт проверки в настоящее время не проверяет списки контрольных сумм, подписи, сертификаты или функции нативной оболочки, а также не определяет, какие платформы должны быть выпущены в данном релизе.

## Параметры и поведение автоматической сборки

### Параметры и предварительная проверка

- Скрипт проверяет `Ver` и `Mode` ядра, версии Android и HarmonyOS, а также версию манифеста при включении Appx, но не изменяет автоматически номера версий или `versionCode`
- `--platforms` принимает список платформ через запятую: `windows`, `linux`, `android`, `harmony`; по умолчанию собираются все четыре платформы, для Appx необходимо дополнительно указать `--appx`
- `--output` задаёт каталог сбора артефактов (по умолчанию `siyuan` на рабочем столе); скрипт не перезаписывает существующие одноимённые пакеты
- `--records-dir` задаёт корневой каталог постоянных записей (по умолчанию `release-records` на одном уровне с основным репозиторием); при каждом запуске создаётся отдельный каталог для журналов и прогресса этапов, который сохраняется при очистке артефактов выпуска
- В Windows по умолчанию перед предварительной проверкой один раз скрыто вводится PIN-код подписи; в автоматизированной среде его можно передать через переменную окружения процесса `SIYUAN_SIGNING_PIN`, скрипт считывает её и удаляет из окружения родительского процесса, не записывая в аргументы командной строки, файлы конфигурации или записи выпуска; `--signing-ui` позволяет использовать системное диалоговое окно PIN
- Скрипт сохраняет существующую конфигурацию подписи Android и HarmonyOS и не считывает и не выводит пароли из этих конфигураций
- В WSL по умолчанию используются пользователь `d` и репозиторий `/home/d/88250/siyuan`, их можно изменить через `--wsl-user`, `--wsl-repo`, `--wsl-distro`; при предварительной проверке сборки Linux или HarmonyOS выполняется автоматическая синхронизация с точным коммитом Windows, проверяемые входные данные сборки должны совпадать, условия автоматической синхронизации см. на шаге 2
- Репозитории Android и HarmonyOS по умолчанию находятся на одном уровне с репозиторием SiYuan, их можно изменить через `--android-dir`, `--harmony-dir`; пути к инструментам сборки задаются через `--arm64-cc`, `--deveco`; `--sevenzip` передаётся только в команду ручной проверки, выводимую после завершения, и не проверяется и не вызывается во время сборки

### Процесс

- Локальный фронтенд для продакшена собирается один раз, фронтенд Linux собирается в WSL
- В Windows ядра обеих архитектур собираются в новом каталоге, генерируется временная конфигурация Electron Builder с включённой подписью сертификатом без изменения YAML репозитория и без повторного использования каталога ядра разработки; по умолчанию генерируются два пакета NSIS и проверяется подпись Authenticode
- Инструмент ресурсов Windows зафиксирован на `goversioninfo v1.7.0`: сначала проверяется наличие инструмента и версии его модуля Go в `GOBIN` (или `GOPATH/bin`, если не задана), при совпадении он переиспользуется, и только при отсутствии или несовпадении версии устанавливается эта зафиксированная версия с повторной проверкой; `latest` при каждой сборке не запрашивается
- Linux вызывает существующий `scripts/linux-build.sh --target=all` и собирает восемь пакетов: TAR, AppImage, DEB и RPM для обеих архитектур
- Android генерирует новый AAR в текущем временном каталоге, после проверки версии и архитектуры ядра копирует его в проект; генерирует и копирует новый `app.zip`, затем запускает `gradlew clean buildReleaseTask` для создания четырёх канальных пакетов; официальная версия собирается как `siyuan-версия.apk` (например, `siyuan-3.8.11.apk`) без суффикса `official` или `release`, остальные каналы сохраняют исходные имена файлов
- HarmonyOS собирает и копирует только ядро ARM64 для реальных устройств, не собирая ядро эмулятора x86_64; в release-проекте должны сохраняться фильтрация ABI ARM64 и исключение библиотек x86_64. С использованием того же нового `app.zip` через Hvigor в режиме release выполняется `assembleApp` (соответствует «Build - Build Hap(s)/APP(s) - Build APP(s)» в DevEco Studio), собирается только `build/outputs/default/siyuan-harmony-default-signed.app`; при отсутствии подписанного артефакта сборка завершается ошибкой, `unsigned.app` и отдельные HAP не собираются
- Ядро HarmonyOS собирается через `scripts/harmony-kernel-build.sh` с использованием адаптации отдельной цепочки инструментов Go из процесса разработки и развёртывания; этот вход используется как для фоновой компиляции во время упаковки Linux, так и для отдельной сборки HarmonyOS. Подробнее о копии цепочки инструментов и трёх адаптациях исходного кода см. в [руководстве по участию в разработке](../.github/CONTRIBUTING.zh-CN.md#harmony); системный Go и общий кэш модулей не изменяются
- При сбое любой команды выполнение немедленно останавливается; артефакты должны быть сгенерированы в текущем запуске, при копировании контрольные суммы сверяются повторно
- Каталог `entry/libs/arm64-v8a/` для HarmonyOS принимает только `libkernel.so`, заголовочные файлы синхронизируются из каталога сборки ARM64 в `entry/src/main/cpp/include/`; `libkernel.h` должен быть сгенерирован в текущем запуске, `lan_sync_bridge.h` синхронизируется при наличии в каталоге сборки, иначе сохраняется версия, поддерживаемая в проекте; при отсутствии обязательных заголовочных файлов сборка останавливается
- Артефакты каждой платформы сразу после генерации копируются в папку `siyuan` на рабочем столе без перезаписи одноимённых пакетов; после завершения сборки отдельно запускается `verify-release.py check` для проверки каталога сбора, а при сбое сборки уже скопированные пакеты сохраняются. Если нужно пересобрать одноимённый пакет, сначала вручную переместите старый пакет; после исправления ошибок проверки можно повторно запустить `verify-release.py check` для каталога на рабочем столе. Существующий `SHA256SUMS.txt` сохраняется, список контрольных сумм в конце вручную генерируется публикатором
- Каталоги сборки сохраняются в системном временном каталоге, фактический путь выводится в консоль, после сбоя их можно проверить и забрать артефакты; автоматический коммит, отправка, создание тегов, загрузка или публикация анонсов не выполняются

### PIN-код YubiKey

По умолчанию автоматическая подпись выполняется через драйвер смарт-карт Windows и интерфейс Authenticode с поддержкой ключей подписи RSA и ECDSA в CNG. При запуске один раз скрыто вводится PIN; на этапе предварительной проверки существующий AMD64 elevator EXE копируется во временный каталог, после проверки PIN для копии выполняются подпись SHA256, запрос метки времени и проверка подписи, и только после успеха начинается длительная сборка; исходный файл остаётся неизменным, а временная копия удаляется как при успехе, так и при ошибке. PIN временно хранится только в памяти процесса, передаётся через стандартный ввод дочернего процесса подписи и не записывается в файлы или журналы. Каждый публикуемый файл по-прежнему подписывается отдельно с проверкой сертификата и метки времени; прохождение предварительной проверки не гарантирует неизменность состояния сети или устройства в дальнейшем. При сбое выводятся только этап, код ошибки и статус подписи без вывода учётных данных или исходного текста исключений; автоматическая повторная попытка выполняется только один раз при обрыве связи с устройством, а при неверном PIN работа немедленно прекращается.

При автоматическом запуске вызывающая программа может передать PIN через переменную окружения процесса `SIYUAN_SIGNING_PIN`, не записывая пароль в команды или скрипты. Устройство подписи по-прежнему должно быть подключено; скрипт не меняет политику PIN или касания, поэтому ключи, требующие касания, не могут работать полностью без участия человека. Если драйвер не поддерживает автоматическую аутентификацию, можно добавить `--signing-ui` для использования системного диалогового окна.

Автоматическая подпись использует для каждого файла временную копию в том же каталоге: во время подписи запись в исходный файл запрещена, после подписи копии отдельно проверяются подпись, сертификат и метка времени, и только после подтверждения неизменности хэша исходного файла выполняется атомарная замена. При сбое исходный файл сохраняется, а временная копия удаляется; повторная подпись или игнорирование `HashMismatch` не используются вместо проверки. Перед сбором установочных пакетов по-прежнему выполняется финальная проверка подписи.

По умолчанию действующий сертификат подписи кода выбирается по существующей теме сертификата; при наличии нескольких сертификатов используйте `--certificate-sha1` для указания 40-символьного публичного отпечатка (это не пароль). Опция `/p` в SignTool предназначена для пароля файла сертификата и не может использоваться как универсальный параметр PIN для YubiKey. См. [документацию драйвера Yubico](https://www.yubico.com/support/download/smart-card-drivers-tools/) и [документацию SignTool](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool).

## Опциональный полный эталон контрольных сумм

Обычно не требуется. Если в будущем потребуется сравнить побайтовые различия для одного номера версии, можно сгенерировать эталон из доверенных артефактов сборки и явно включить его с помощью `check --baseline`. Сравнение с эталоном выполняется после прохождения обычных проверок и не пропускает проверки имени пакета, версии и архитектуры ядра, версии фронтенда, ссылок на ресурсы или метаданных оболочки десктопа. Нельзя генерировать эталон в обратную сторону из проверяемого пакета.

На примере Android: сначала получите «текущий каталог сборки» из журнала текущей сборки и замените `$releaseWork` ниже. Новый собранный AAR находится в `android/kernel.aar` этого каталога, а архив ресурсов для упаковки — в `mobile/app.zip`. Не используйте `kernel/kernel.aar` из основного репозитория или неотфильтрованный `app/`: они могут быть устаревшими артефактами или содержать неупакованные исторические журналы изменений.

```powershell
$releaseWork = "C:\Users\DL882\AppData\Local\Temp\siyuan-release-3.8.11-фактический_суффикс_каталога"
$resources = Join-Path $releaseWork "baseline-resources"
$baseline = Join-Path $releaseWork "android-arm64.release-baseline.json"
Expand-Archive -LiteralPath (Join-Path $releaseWork "mobile/app.zip") -DestinationPath $resources
python -X utf8 scripts/verify-release.py baseline --version 3.8.11 --target android-arm64 --kernel (Join-Path $releaseWork "android/kernel.aar") --resources $resources --output $baseline
python -X utf8 scripts/verify-release.py check ../siyuan-android/app/build-release/siyuan-3.8.11-all --version 3.8.11 --baseline $baseline
```

Указанные выше каталог распаковки ресурсов и файл эталона должны использовать ещё не существующие пути, а проверяемый каталог Android должен соответствовать текущему пути проекта и версии. Этот пример проверяет только четыре канальных пакета Android; при проверке каталога со смешанными платформами необходимо повторно передать `--baseline` для каждого требуемого эталона платформы.

Каталог ресурсов должен соответствовать фактически упакованному набору. Десктопные пакеты фильтруют файлы тем оформления и обрезают журналы изменений, поэтому нельзя напрямую сравнивать неотфильтрованный `app/`; подпись или обработка нативных библиотек также могут изменить контрольную сумму ядра. При возникновении расхождений контрольных сумм следует проверить доверенный процесс сборки и выбрать доверенный артефакт соответствующего этапа обработки, а не генерировать эталон из проверяемого пакета для устранения различий.
