# Контракты типов API ядра

[English](API-CONTRACTS.md)

## Область применения

Настоящий документ определяет требования к типизации, совместимости, генерируемым артефактам и процессу проверки HTTP API ядра. Определения транспортных типов и эндпоинтов расположены в модульных файлах каталога `kernel/apicontract/`, а `contracts.go` объединяет их в реестр эндпоинтов; миграция завершена — все интерфейсы обязаны иметь контракт типов и быть привязаны к типизированным обработчикам.

## Процесс сопровождения интерфейсов

1. Определите или обновите транспортные типы и эндпоинты в пакете контрактов, явно указав публичный или авторизованный доступ, требования администратора и записи, а также правила для тела запроса, кодов ошибок, null-значений, значений по умолчанию и обратной совместимости входных данных.
2. Привяжите бизнес-вход через `contractHandler` и зарегистрируйте обработчик через `contractRouteHandlers`, сохраняя порядок middleware маршрутизации и область действия аренды (lease).
3. При удалении интерфейса синхронно удалите регистрацию маршрута и определение контракта.
4. Обновите тесты реальных ответов, совместимости входных данных и строгой типизации, запустите генератор, затем исправьте ошибки вызовов, указанные компилятором.
5. Синхронизируйте генерируемые объявления в `petal` и связанные публичные объявления. Поведение интерфейса, значения по умолчанию, ограничения и совместимость описываются в комментариях исходного кода контракта и соответствующих объявлениях сопровождения Petal. При изменении существующего интерфейса проверьте и синхронизируйте затронутые разделы в `docs/API.md`, `docs/API.zh-CN.md` и `docs/API.ja.md`, не предполагая, что все языки покрывают одинаковый набор интерфейсов; добавляйте новые интерфейсы в эти справочники только по явному запросу пользователя.

Настоящий документ и его переводы являются руководством по сопровождению; они обновляются только при изменении механизма контрактов, политики совместимости, процесса генерации, обнаружения тестов или правил проверки, либо по явному запросу пользователя. Обычные изменения интерфейсов или функций не должны добавлять сюда описание поведения конкретных эндпоинтов, сводки функций, результаты проверок или команды таргетированных тестов. Пользовательские инструкции помещаются во встроенное руководство пользователя, исполняемые примеры плагинов — в `plugin-sample`, а проверки конкретных задач и их результаты — в ответ на задачу или описание PR. В README Petal оставляются только название проекта и ссылка на `plugin-sample`. Область документации следует [AGENTS.md](../AGENTS.md).

Проверка генерации считывает фактические объявления маршрутов и обработчиков, проверяя соответствие метода, пути, обработчика, адаптера контракта и middleware аутентификации. `define` требует явной передачи политики доступа: публичные эндпоинты используют `PublicAccess`, а авторизованные могут добавлять `AdminAccess` и `WritableAccess`. Доменные функции регистрации сохраняют литеральные метод и путь, а `contractRouteHandlers` выводит middleware из привязанного эндпоинта. Проверка генерации отклоняет отсутствующие политики, несовпадение привязки эндпоинта, а также пропуск или изменение порядка явных middleware. Метаданные аутентификации не заменяют проверку прав на ресурсы или глобальный middleware аренды блокнота. Генератор и CI отклоняют маршруты без контракта и проверяют полное покрытие маршрутов. Запрещено обходить проверку контрактов через `any` или приведение типов.

## Контракты и реализация

Для JSON-интерфейсов под управлением `ControlConcurrency` запрос сначала проходит аутентификацию и проверку допуска, затем `contractHandler` завершает декодирование и чтение оставшегося тела запроса, и только после этого захватывается бизнес-блокировка по пути, чтобы запросы в очереди не исчерпали окно приёма HTTP/2-соединения. Внешний middleware освобождает блокировку после завершения обработки ответа и очистки аренды блокнота. Новые адаптеры обязаны сохранять этот порядок; потоки сырых данных и загрузка форм сохраняют прежние пути управления конкурентностью.

Модульные файлы в `kernel/apicontract/` определяют запросы, ответы и эндпоинты, а `contracts.go` собирает их в реестр эндпоинтов. Пакет контрактов не зависит от запуска ядра, базы данных и моделей персистентности, поэтому генератор может запускаться автономно. Входы API привязывают эндпоинты через `contractHandler`; параметры запроса и успешные возвращаемые значения ограничены generic-сигнатурами Go; полезная нагрузка ответа задаётся через конструкторы, прямое присваивание общему `ret.Data` запрещено. Вспомогательные функции валидации возвращают ошибки; `FailureFrom` сохраняет код ошибки и сообщение `Rejection`, остальные ошибки используют `-1`. Поддерживаемые полезные нагрузки ошибок задаются через конструкторы эндпоинтов, а успешные ответы с `null` в `data` используют `SuccessWithoutData`.

Генератор из одного набора Go-типов создаёт `app/src/types/api/index.d.ts` и `kernel/apicontract/schema.json`. Последний содержит общие `$defs` и схемы запросов и ответов для каждого эндпоинта; тесты используют ту же схему для проверки реальных HTTP-ответов. Объявления типов не валидируют JSON во время выполнения — за проверку сериализации отвечают тесты обработчиков в CI.

Входные и выходные данные обрабатываются раздельно. Тег `json` управляет именем поля в сетевом протоколе; поля запроса по умолчанию обязательны, `api:"optional"` означает необязательность, `nullable` — допустимость `null`, а указатели сохраняют семантику nullable. Тег `omitempty` у выходных полей управляет только пропуском при выводе и не определяет обязательность в запросе. Встроенные структуры разворачиваются, рекурсивные типы представляются ссылками; объединения интерфейсов, константные поля и пользовательская сериализация требуют явного моделирования. Неподдерживаемые типы, конфликты полей и неизвестные JSON-теги приводят к ошибке генерации и не деградируют в `any`.

Массивы, словари и вложенные структуры рекурсивно проверяют ограничения запроса; `null` в массивах строк не преобразуется в пустую строку, а `null` в пакетных атрибутах по-прежнему означает удаление атрибута. Дерево тегов определяет отдельную рекурсивную транспортную структуру; поля пути блокнота и документа в общих узлах дерева на фронтенде необязательны, что отражает фактическое поведение узлов тегов, не возвращающих эти поля.

`Notebook` является полезной нагрузкой интерфейса; бизнес-модель преобразуется в неё через явную конвертацию, а регрессионные тесты сравнивают полный JSON, включая все состояния шифрования. Изменение контракта не меняет форматы `.sy`, базы данных, истории, синхронизации или шифрования.

Создание, переименование, удаление, закрытие, обновление иконки и сортировка блокнотов включены в контракты типов. Переименование, удаление и обновление иконки обрезают пробелы по краям ID блокнота; закрытие сохраняет пробелы и обрабатывается проверкой ID. Пустые имена и пустые иконки по-прежнему обрабатываются бизнес-слоем, а ошибка переименования сохраняет длительность показа уведомления.

Интерфейсы жизненного цикла зашифрованных блокнотов используют типизированные запросы и ответы, сохраняя обрезку пробелов пароля, усечение минут с приведением отрицательных значений к нулю, права администратора, захват аренды и откат при ошибке монтирования. Вывод ключей, формат шифротекста и материалы восстановления по-прежнему сопровождаются уровнем моделей.

## Требования к совместимости

Мобильные сборки могут вызывать `DisableFeature("ai")` до запуска ядра. Все интерфейсы `/api/ai/` и `/api/setting/setAI` отклоняют запросы до декодирования тела, сохраняя аутентификацию и авторизацию маршрута. JSON-интерфейсы возвращают код ошибки `-1` и пустые данные; OAuth-коллбэк MCP возвращает HTTP 403 в виде обычного текста. Сохранённая конфигурация AI остаётся неизменной. Индексация эмбеддингов, переранжирование и исходящие MCP-подключения также подчиняются этому флагу.

Интерфейс блокировки экрана системы зашифрованных блокнотов сохраняет аутентификацию администратора и проверку режима «только чтение». Булев переключатель хранится в конфигурации системы и не попадает в аутентифицированные данные резервного копирования ключей.

На момент завершения миграции 14 сентября 2026 года все 629 регистраций методов и путей в `kernel/api/router.go` включены в контракты, а список старых маршрутов пуст. 4 регистрации `ANY` из этого базового набора разворачиваются в 661 конкретный метод и путь в генерируемых объявлениях. При добавлении новых интерфейсов ориентируйтесь на статистику генератора и проверки покрытия маршрутов. Статические ресурсы, главный WebSocket приложения и прочие транспортные сервисы, регистрируемые `kernel/server/serve.go`, не входят в этот реестр API-маршрутов.

Системный контракт сохраняет полную конфигурацию, управление рабочим пространством, загрузку файлов, аутентификацию, ветки ответов OIDC, поток событий запуска, а также пустые и бинарные ответы. Фронтенд сужает типы в местах чтения сохранённой раскладки и горячих клавиш, сохраняя прежнюю логику восстановления значений по умолчанию, очистки устаревших ключей и фильтрации привязок. Импорт, экспорт и выход из конфигурации сохраняют прежний жизненный цикл и поведение шифрования.

Контракт транзакций различает по действию все 98 известных операций и исключает их имена в явной ветке совместимости для неизвестных операций. Фронтенд использует тот же ограниченный набор операций. Приватный сырой ввод сохраняет исторические поля, игнорируемые значения, асинхронные ошибки модели и возвращаемую полезную нагрузку; объявления типов не переносят валидацию модели на этап HTTP-допуска. Отмена, повтор, операции с заголовками, аренда ответа и формат персистентности транзакций сохраняют прежнее поведение.

Расширение веб-клиппера сохраняет обработку первого значения в multipart-форме, динамические имена загружаемых файлов, частичные результаты, прежние сообщения и допуск к зашифрованным блокнотам. Динамические иконки сохраняют байты SVG, заголовки безопасности и кэширования, а также пустые ответы об ошибках. Широковещательные потоки объявляют сырые байты SSE, динамические имена событий, ID и значения retry, а также сырые кадры WebSocket и ошибки обновления соединения; полезная нагрузка не конвертируется в JSON или Base64, а очистка каналов сохраняет прежнюю область действия.

Приватные сервисы плагинов объявляют существующие режимы сериализации, сырые файлы, перенаправления, прокси-ответы, события SSE и кадры WebSocket. Пользовательская полезная нагрузка плагина сохраняется как данные расширения протокола и валидируется раздельно по фактическим веткам как сериализованный формат или произвольные байты. Тело запроса, явные заголовки ответа, ошибки допуска и обработка отмены сохраняют прежний жизненный цикл сервисов плагинов.

Сетевой контракт сохраняет байты запроса, поля формы, заголовки запроса, URL и диагностику TLS, включая полную структуру открытого ключа сертификата и большие целые числа. Параметры forward-прокси сохраняют порядок валидации, усечение чисел, кодировку ответа и JSON-нагрузку, определённую протоколом. Прокси HTTP, EventSource и WebSocket сохраняют статус и байты апстрима, поведение повторяющихся заголовков, заголовки безопасности, отмену потока и очистку соединений. Wildcard-путь echo привязывает отдельный адаптер и использует ту же бизнес-обработку.

Контракт баз данных раздельно объявляет структуры результатов для таблицы, галереи и канбана, сохраняя отсутствие базовых полей, частичное изменение ячеек и значения `null`. Отдельный макет `list` переиспользует нагрузку таблицы `columns`/`rows`/`rowCount`, конфигурация макета хранится в `list`, а `viewType` имеет значение `list`. Известные изменённые поля сохраняют переданное состояние без заполнения нулевыми значениями отсутствующих полей. Текущий, исторический и снимочный рендеринг используют соответствующие типы запросов; вызывающая сторона сначала обрабатывает нагрузку ошибки и только потом обновляет представление. Сортировка строк, допуск публикации, аренда зашифрованных блокнотов и быстрый рендеринг JSON сохраняют прежнее поведение. Общие объявления фронтенда и плагинов синхронизируются по фактическим полям представлений и ячеек.

Интерфейс рендеринга баз данных использует для читателей публикации путь без записи на диск. Запрос сохраняет текущий режим, авторизацию носителя, фильтрацию содержимого и аренду блокнота; даже при передаче `createIfNotExist: true` отсутствующая база данных для читателя не создаётся. Нормализация совместимости, генерация групп и исправление отсутствующих полей выполняются только в памяти.

Контракт AI сохраняет конфигурацию провайдеров, обнаружение и сопоставление моделей, результаты подтверждения, поля расширения сессии, а также числовую семантику и семантику пропуска полей. Потоки редактора и агента объявляют фактические события SSE, закрывают исходящий запрос при разрыве соединения, а жизненный цикл потока остаётся внутри запроса. Страницы OAuth сохраняют тип медиа, HTTP-статус и заголовки безопасности. Уведомления о правах сессии используют `WithAfterWrite`, сохраняя порядок «сначала ответ, затем рассылка». Произвольный JSON используется только для полей расширения протокола и результатов инструментов.

Провайдеры AI помимо `openai` и `openai-responses` поддерживают `anthropic-messages`; при пропуске протокола сохраняется значение по умолчанию Chat Completions. Нативные вызовы Messages покрывают обнаружение моделей, тестирование моделей, генерацию в редакторе, инструменты агента, заголовки и сжатие сводок. Поскольку Messages требует `max_tokens`, автоматический лимит вывода составляет 4096 токенов. Записи ассистента могут содержать `nativeContent` с протоколом, версией и непрозрачными блоками содержимого; версия 1 сохраняет подпись размышлений Anthropic и порядок блоков при восстановлении во время выполнения и фиксации сессии. Другие протоколы проецируют только видимый диалог и не отправляют эти нативные блоки. Неизвестная нативная версия завершается ошибкой до отправки запроса Messages и сохраняет исходную сессию. Использование токенов в потоке отправляется один раз после `message_stop`, а неполные ответы инструментов не передаются на выполнение. Существующие правила обнаружения тестов фронтенда уже включают `aiProviderPresets.test.ts`.

Контракт настроек сохраняет частичное слияние конфигурации, прежние значения по умолчанию, совместимость регистра полей структур, явный `null`, нормализацию чисел JSON и сообщения об ошибках парсинга. Горячие клавиши и результаты облачной аутентификации объявляют фиксированные поля, сохраняя определённые протоколом расширения JSON. При запросе облачного пользователя не-администратором проверка допуска по-прежнему выполняется до чтения тела запроса; двухфакторная аутентификация сохраняет облачные коды ошибок и поля расширения. Фронтенд продолжает нормализовать сохранённые настройки отображения на прежних границах.

Контракт дерева документов сохраняет условную валидацию параметров, семантику путей и сортировки, правила пропуска коллбэков, значения пагинации по умолчанию и варианты ответов документа. Аутентификация публикации сохраняет HTTP 429 и `Retry-After` через явно объявленный дополнительный статус ошибки. Допуск публикации и зашифрованных блокнотов по-прежнему предшествует отложенной валидации полей, а аренда документа покрывает этап сериализации ответа.

Контракт вложений сохраняет `null`-значения в списке результатов, порядок загрузки по файлам и дублирующиеся имена файлов, уведомления при частичном успехе загрузки и полезную нагрузку при ошибке локальной вставки. Столбец OCR сохраняет строковое значение. Проверка аннотаций, допуск опубликованных файлов, чтение/запись при шифровании, отложенная загрузка и выбор цели загрузки сохраняют прежнее поведение. Точки загрузки вне API переиспользуют ту же типизированную операцию модели.

Получение списка и очистка неиспользуемых ресурсов при ошибке загрузки документа или обхода каталога ссылок возвращают стандартную ошибку `code: -1`, `data: null`, включая неподдерживаемые спецификации документов. Очистка одного ресурса использует то же полное сканирование; пакетная очистка не создаёт историю и не начинает удаление до успешного завершения сканирования. Структура успешного ответа и правила исключения зашифрованных блокнотов остаются неизменными.

Сканирование ссылок на ресурсы записывает базы данных с отсутствующим файлом определения или недействительным ID определения в необязательный список `unavailableAttributeViews`, не блокируя запрос, пробный прогон или замену. Каждый элемент содержит ID и имя блокнота, ID, путь и человекочитаемый путь документа, ID блока, ID базы данных и причину. Существующие, но нечитаемые или повреждённые определения по-прежнему возвращают ошибку. Перед сохранением снимок отсутствующих файлов перепроверяется, чтобы не пропустить определения, восстановленные во время сканирования. Текущие правила загрузки по требованию не включают определения баз данных; регрессионные тесты проверяют эту предпосылку. Регрессия отсутствующих определений покрывает модель и реальный HTTP-контракт, включая закрытые блокноты и общие определения.

Контракт запроса и замены ссылок на ресурсы сохраняет запрос одного ресурса и одновременно поддерживает пакетные параметры. Пакетный результат возвращает по порядку ввода статус каждого элемента, причину, ссылки и число изменённых файлов; верхнеуровневый счётчик дедуплицирует общие файлы. Пустые пакеты, дублирующиеся исходные пути, цепочки и циклические сопоставления отклоняются. Независимые сопоставления могут завершиться при ошибке других элементов, а ошибка записи общего файла относится ко всем затронутым сопоставлениям. Во время сканирования разрешено редактирование, перед сохранением проверяется снимок рабочего пространства; отмена и повтор без изменений сохраняют исходные данные.

Контракт экспорта сохраняет значения по умолчанию для параметров Markdown и усечение чисел, фильтрацию списка блокнотов, правила игнорирования типов параметров заголовков, необязательное поле HTML-оглавления и правила выбора поля загрузки. Ответы об ошибках сохраняют длительность показа сообщения и пустую строковую нагрузку в ошибках ресурсов. Фильтрация публикации, допуск зашифрованных блокнотов, аренда на время ответа и очистка временного экспорта сохраняют прежний жизненный цикл.

Контракт репозитория сохраняет кодировку ключей, метаданные снимков, усечение чисел и значения срока хранения по умолчанию, облачную пагинацию и аренду доступа к файлам. Чтение файла репозитория сохраняет тип медиа и сырые байты, а пустой файл сохраняет конверт успеха. Как файловый успех, так и JSON-ошибка возвращают HTTP 200. Для явно объявленного общего статуса `ValidateHTTPResponse` принимает сырые байты файла, а `ValidateErrorResponse` отдельно проверяет известную нагрузку ошибки. Ключевой материал, формат зашифрованных файлов и поведение восстановления снимков остаются неизменными.

Контракт карточек памяти сохраняет усечение чисел, значения пагинации по умолчанию, необязательный список повторенных карточек, `null`-значения результатов блоков и непустой список колод. Допуск блокнота и документа по-прежнему предшествует отложенным ошибкам пагинации. Изменение карточек и колод сохраняет валидацию уровня моделей и поведение персистентности, а ограничения зашифрованных блокнотов остаются неизменными.

Контракт синхронизации сохраняет усечение чисел, условную валидацию направления в ручном режиме, сопоставление полей конфигурации и нормализацию чисел JSON, а также длительность показа сообщений. Импорт конфигурации синхронизации требует ровно один файл и сохраняет содержимое зашифрованного пакета и путь восстановления. Аутентификация и проверка режима «только чтение» по-прежнему предшествуют декодированию тела запроса; синхронизация и шифрование блокнотов продолжают обрабатываться уровнем моделей.

Контракт маркетплейса сохраняет порядок валидации обязательных полей, обработку пробелов, привязку к режиму темы, доступность оценок и нагрузку ограничения частоты, а также ошибки загрузки локальных пакетов. Ответы пакетов и тем оформления объявляют полную вложенную структуру, включая фиксированное распределение оценок из пяти элементов. Запрос загрузки сохраняет выбор первого файла и разбор параметра перезаписи. Установка, удаление, аутентификация и ограничения публикации по-прежнему выполняются существующими бизнес-обработчиками и middleware.

Запрос информации о плагине сохраняет приоритет имени из параметра пути, параметра запроса и JSON-тела запроса, включая пробелы и бизнес-коды ошибок от 1 до 4. При совпадении параметра URL тело запроса не парсится, а списочный запрос игнорирует тело запроса. Списки плагинов и RPC-методов сохраняют семантику `null` для массивов и элементов массива. HTTP JSON-RPC использует отдельный контракт для одиночных и пакетных запросов, успешных и ошибочных ответов, а также ответа HTTP 204 для чистых уведомлений. Допуск плагина предшествует чтению тела запроса, пакетные ошибки сохраняют исходный порядок, а произвольный JSON используется только для параметров RPC, возвращаемых значений и деталей ошибок. Маршрут RPC WebSocket объявляет обновление до HTTP 101, ошибку допуска плагина HTTP 404, текстовый отказ HTTP 400, а также раздельные входящие вызовы и исходящие ответы или уведомления. Авторизация Origin и очистка соединений сохраняются в прежнем жизненном цикле обновления соединения.

Контракт публикации плагинов разделяет авторизацию и запись снимков (доступные только администратору) и публичное чтение для аутентифицированных посетителей. Публичные данные содержат только объявленные скалярные поля, а авторизация и снимки используют локальные версионированные файлы, отделённые от синхронизируемого приватного хранилища плагина. Статические маршруты и файловый интерфейс разделяют состояние плагина и правила безопасного открытия файлов; ответ загрузки публикации исключает код ядра. Фильтр CI для тестов путей также включает регрессии моделей, статических маршрутов и границ файлов. Описание интерфейсов и примеров миграции см. в [Публикация плагинов](PLUGIN-PUBLISH.zh-CN.md).

Контракт поиска сохраняет значения пагинации по умолчанию и усечение десятичных дробей, валидацию и дедупликацию путей, правила игнорирования фильтрации подтипов истории, а также различие между `null` и пустым массивом. Поиск ссылок различает возврат только идентификатора запроса и полных результатов блоков, сохраняя порядок допуска блокнота до отложенной валидации параметров. Права SQL-поиска, фильтрация публикации, аренда зашифрованных блокнотов, ответы на отменённые запросы и пустая операция обновления встроенных блоков только для чтения сохраняют прежний порядок. Вызовы на десктопе и мобильных устройствах используют сгенерированные типы запросов.

Поиск пользовательских блоков использует необязательное поле фильтрации типа `customBlock`. При явной передаче карты типов в API выполняется поиск только по включённым в неё типам; при пропуске карты типов используются настройки поиска, где пользовательские блоки включены по умолчанию. Сохранённые условия поиска различают отсутствие поля и `false`, чтобы старая конфигурация поиска на фронтенде могла наследовать настройку.

Контракт истории сохраняет обрезку пробелов в путях, значения по умолчанию для необязательной подсветки, усечение десятичных дробей типа истории, а также различие между `null` и пустым массивом. Сравнение версий сначала проверяет два объекта ссылок, затем поля объектов и захватывает аренду по отсортированным ID блокнотов. Чтение содержимого и откат документов, ресурсов и баз данных сохраняют проверку аренды исторического пути, а откат блокнотов следует поведению восстановления уровня моделей.

Контракт импорта сохраняет очистку архивов, выбор первого загруженного файла, пробелы в пути Markdown, а также обрезку пробелов и срок действия временного токена. Автоматический импорт SiYuan объявляет результаты для документа, токена, блокнота и коллекции блокнотов, сохраняя нагрузку документа при ошибке монтирования. Задача Obsidian при ошибке отмены сохраняет снимок задачи. Монтирование блокнота, обработка зашифрованного импорта и уведомления о создании по-прежнему выполняются существующими бизнес-операциями.

Контракт обратных ссылок сохраняет пробелы в полях запроса, значения по умолчанию для необязательных переключателей, нормализацию фильтра источника и хеш версии. При отсутствии ID в списочном запросе по-прежнему возвращается `null`; при неизменной версии сохраняются прежние поля и `null`-массивы. При ошибке запроса определений-кандидатов сохраняется пустой массив `refDefs`. Фильтрация публикации, допуск зашифрованных блокнотов и аренда на время запроса по-прежнему поддерживаются обработчиком, а полезная нагрузка контекста сохраняет рекурсивный путь блоков и позиции ссылок в базах данных.

Контракт графа сохраняет значения по умолчанию для локальной конфигурации, нечувствительность к регистру полей конфигурации и поведение нормализации чисел. Ответ запроса различает полные данные графа и результаты только с идентификатором запроса — последние включают ошибки и локальные запросы без ID; массивы узлов и связей сохраняют прежнюю семантику `null`. Сохранение конфигурации по-прежнему требует прав администратора и отсутствия режима «только чтение». Порядок выполнения между фильтрацией публикации, отказом в доступе к зашифрованным блокнотам и декодированием конфигурации остаётся неизменным.

Контракт шаблонов сохраняет валидацию пути до режима и исходного содержимого, приоритет явного режима над старым переключателем предпросмотра, значение по умолчанию для режима базы данных и подсказку перезаписи с кодом `1`. Управление файлами сохраняет JSON-привязку Go-структур и её фиксированные сообщения об ошибках парсинга, раздельно объявляя список, исходное содержимое, номер версии и пустую нагрузку. Проверка версии, ограничения символических ссылок и обработка инвалидации синхронизации по-прежнему выполняются существующими операциями моделей.

Контракт SQL-запросов сохраняет `limit` и `truncated` на верхнем уровне конверта успеха. `SuccessSQL` добавляет эти поля, а ответы об ошибках их не содержат. Имена столбцов результата определяются запросом, каждое значение является JSON-скаляром с сохранением разрядности целых чисел и Base64-сериализацией бинарных значений. Обрезка пробелов по краям запроса, необязательная схема, проверка одного запроса и режима «только чтение», а также код ошибки запроса `1` остаются неизменными.

Сопровождение контрактов обязано сохранять наблюдаемое поведение интерфейсов; нельзя изменять семантику вызовов только из-за рефакторинга определений типов или обработчиков:

- Семантика запросов: сохраняйте обязательность тела запроса, необязательность полей, а также различие между пустым телом, отсутствующим полем, `null`, пустой строкой, пустым объектом и пустым массивом.
- Обработка параметров: сохраняйте значения по умолчанию, обработку пробелов, преобразование чисел и поддерживаемые исторические правила ввода; нельзя неявно расширять или сужать диапазон принимаемых значений.
- Структура ответов: сохраняйте имена полей, типы, допустимость `null` и правила пропуска, различайте `{}`, `[]` и `null`, полностью объявляйте ветки успеха, подсказок и ошибок.
- Поведение при ошибках: сохраняйте HTTP-статус, бизнес-код ошибки, сообщение, дополнительную нагрузку ошибки и длительность показа уведомления; не переинтерпретируйте существующие бизнес-ошибки как успех.
- Права и жизненный цикл: сохраняйте проверку аутентификации, ролей, режима «только чтение» и прав публикации, а также допуск операций с зашифрованными блокнотами, область аренды и момент её освобождения; обработка совместимости не должна обходить авторизацию или аутентифицированное дешифрование.

Особое поведение конкретных интерфейсов совместно фиксируется определением контракта, декодированием совместимости и регрессионными тестами. Тесты должны покрывать фактическую HTTP-сериализацию, граничные входные данные и сценарии прав доступа, а не только проверять компиляцию типов.

`ignoretype` и `filterstrings` используются только для объявленного поведения совместимости со старыми параметрами. Сгенерированные типы запросов описывают каноническую форму вызова; декодирование совместимости может принимать и игнорировать более широкий старый ввод, а тесты совместимости явно покрывают эти исключения. Глобального переключателя «откат к старому парсеру при ошибке привязки» не существует.

Middleware режима «только чтение» по-прежнему может возвращать объект подсказки с `closeTimeout`. Обычный коллбэк `fetchPost` получает только неотрицательные коды ошибок, оставшиеся после обработки сообщений, а код `3` в интерфейсе информации о блоке по-прежнему должен обрабатываться; `fetchSyncPost` и `fetchGet` сохраняют полный ответ. Динамические URL сохраняют существующие сигнатуры; статические POST-пути должны браться из контракта, а ошибочные параметры не могут откатываться через перегрузки. При сборке URL-шаблона открытого диапазона используйте явную переменную `string`.

Когда бизнес-ошибке необходимо сохранить длительность показа уведомления, используйте `FailureWithTimeout`. Запросы блоков с контрактом сохраняют явный блокнот и проверку аренды прикреплённого ID через `holdContractBlockRequest`; поведение запросов статуса, допускающее удалённые ID, по-прежнему явно задаётся соответствующим входом.

`StructJSONBody` используется для интерфейсов, уже применяющих привязку Go JSON-структур, сохраняя совместимость регистра имён полей, обработку `null` и ошибки парсинга; обязательные бизнес-поля продолжают проверяться обработчиком. Запрещено использовать его для ослабления правил запросов существующих интерфейсов. Эндпоинты, возвращающие бизнес-результат при ошибке, явно устанавливают `DataOnError` и вызывают собственный типизированный метод `FailureWithData`.

Обновление конфигурации блокнота использует типизированный частичный объект. Параметр поля `legacyobject` сохраняет нормализацию чисел и совместимость регистра имён полей структур из прежнего JSON round-trip; необязательные поля-указатели при отсутствии или `null` сохраняют прежнее значение. Поля шифрования декодируются только для совместимости ввода и не применяются патчем конфигурации. `Base64Bytes` явно описывает ввод среза байтов в виде строки Base64 или массива байтов.

`JSONValue` используется только для полей, где сетевой протокол явно принимает произвольный JSON, например для возвращаемого как есть идентификатора запроса. Его схема представляет собой рекурсивное объединение `null`, булева значения, числа, строки, массива и объекта и не может заменять запросы или ответы с определённой структурой. Фиксированные поля результата подсчёта слов и идентификатор запроса моделируются раздельно.

Запрос транзакций заголовков использует `BlockTransaction` для возврата типизированных операций, сохраняя пустой массив, `null` и нагрузку отмены операции. `BlockOperationResult` явно объявляет ограниченный тип объединения текста, массива ID блоков и `null`. При конвертации полиморфных полей из бизнес-модели неподдерживаемые типы отклоняются, а полезная нагрузка операций представления атрибутов использует контракты соответствующих действий. Тип операций редактора также принимает пустое поле типа столбца, возвращаемое операциями вне представления атрибутов.

Все маршруты `/api/block/` уже используют контракты. Запрос уровня заголовков сохраняет приоритет пакетных ID, дедупликацию, усечение дробных уровней, привязку структуры документа и длительность показа сообщения. Результат конвертации документа содержит счётчики шести уровней заголовков и типизированные транзакции. Проверка ссылок валидирует только поля, используемые выбранной областью, сохраняет правила игнорируемых полей и обрезки пробелов параметров блокнота, а также булеву нагрузку ошибки, фильтрацию публикации и аренду блокнота до завершения сериализации ответа. Эти особые правила ввода используют приватные функции декодирования, специфичные для входа, тогда как обычные интерфейсы продолжают декодироваться через объявления полей. Результаты недавних обновлений используют рекурсивную нагрузку `SearchBlock`, включающую nullable-ссылки, дочерние блоки и метаданные карточек.

Преобразование HTML-буфера обмена сохраняет литеральные обратные слеши и символы разметки, а при отключённом синтаксисе Markdown сохраняет HTML-формат. После изменения исходного кода Lute необходимо запустить `go test ./...` в репозитории Lute и перегенерировать встроенный JavaScript.

`swapBlockRef` принимает необязательное булево значение `originalToEmbed`. При пропуске или передаче `false` ссылка сохраняется на исходной позиции определения; при передаче `true` она заменяется на встроенный блок с запросом ID перемещённого определения. `includeChildren` сохраняет поведение для заголовков и списков.

Контракт хранилища разрешает произвольный JSON только в значении хранилища; ключи, недавние документы, условия поиска, строчные стили и палитра представления атрибутов используют структурированные типы. Интерфейс записи недавних документов сохраняет поведение немедленного возврата успеха для роли «только чтение» до парсинга тела запроса. Необязательный типизированный коллбэк `beforeDecode` в `contractHandler` используется для сохранения этого порядка выполнения, позволяя вернуть ответ до декодирования; проверка маршрутов по-прежнему требует явной привязки эндпоинта. Обновление строчных стилей версии 1 сохраняет существующую встроенную конфигурацию, а запросы версии 2 и палитры сохраняют совместимость декодирования структур.

`DirectJSONOutput` сохраняет отдельный протокол прямого возврата JSON-объекта или массива без добавления конверта ядра; такая полезная нагрузка возвращается через `SuccessDirectJSON`. Эндпоинты, поддерживающие пустой ответ уведомления, явно объявляют `NoContent` и возвращают `SuccessNoContent`; HTTP-проверка требует код статуса 204 и пустое тело ответа. Ошибки аутентификации и режима «только чтение» по-прежнему сохраняют конверт ошибок ядра. Сгенерированные объявления фиксируют режим прямого вывода и необязательную поддержку пустого ответа.

Интерфейс глобальных обратных ссылок использует отдельный плоский список. `/api/ref/getGlobalBacklinks` требует `id`, `sort` (`1` — естественная сортировка по возрастанию, `2` — по убыванию) и `containChildren`, поддерживая необязательные `notebook`, `keyword` и `sourceFilter`. Каждый реальный ссылающийся блок появляется один раз, берётся анкорный текст его первого совпадающего строчного упоминания с обрезкой пробелов по краям; пустой анкорный текст в обоих направлениях помещается в конец, а одинаковый анкорный текст сортируется по ID исходного документа, позиции в тексте и ID блока. Первый запрос возвращает непрозрачный токен снимка и до 50 записей метаданных; последующие запросы переиспользуют `snapshot` и `offset`, где смещение ограничено границами существующих страниц. Необязательный `anchorID` используется для позиционирования на странице исходного места чтения. Порядок снимка при изменении текста остаётся неизменным, а результаты редактирования включаются только при обновлении без токена. При истечении срока токена, несовпадении запроса, исчезновении исходного документа либо удалении или перемещении элементов текущей страницы возвращается `expired: true`. Кэш хранит не более 16 снимков сроком на 5 минут с общим бюджетом метаданных 64 MiB и не кэширует основной текст; при блокировке блокнота соответствующие снимки очищаются.

`/api/ref/getGlobalBacklinkContexts` использует тот же запрос, обязательный `snapshot` и до 20 `ids` блоков, принадлежащих этому снимку, возвращая независимо редактируемые тела блоков с сохранением хлебных крошек и информации о ссылках в базах данных. Оба интерфейса перед возвратом метаданных или тела перепроверяют права источника и сохраняют аренду запроса зашифрованного блокнота; читатели публикации не могут читать зашифрованные блокноты. Фронтенд загружает по 50 записей на страницу, сохраняя 5 страниц вокруг области просмотра и редактируемую страницу, создавая по требованию не более 16 редакторов. Переработка ожидает незавершённых транзакций, сохраняя композицию IME, фокус, перетаскивание и сессию редактирования базы данных. Автообновление ожидает окончания редактирования и восстанавливает позицию видимых блоков. Значение `0` (по умолчанию) настройки `backlinkGlobalSort` означает группировку по документам, а `1` и `2` — глобальную сортировку анкорного текста по возрастанию и убыванию. В `/api/ref/getBacklink2` добавлен необязательный `includeBacklinks` (по умолчанию `true`); при значении `false` возвращается пустой список обратных ссылок и нулевой счётчик с сохранением поведения упоминаний, что позволяет избежать повторной загрузки группировки по документам. Прежнее поведение существующих вызывающих сторон и внутридокументного `blockSort` остаётся неизменным.

## Файловые и потоковые протоколы

`RawSSEOptions` и `RawWebSocketOptions` объявляют широковещательные протоколы с байтовой полезной нагрузкой и раздельно проверяют события и метаданные кадров через `ValidateRawSSEEvent` и `ValidateRawWebSocketFrame`; JSON-события и RPC-сообщения сохраняют свои прежние проверки. Ошибки сырого WebSocket записываются апгрейдером без использования `RejectWebSocket`.

JSON SSE-интерфейсы объявляют имена событий и полезную нагрузку через `SSEOptions` и `SSEEvent`. `StreamSSE` выполняет прежний жизненный цикл потока в контексте запроса, где также завершаются отмена и очистка. HTTP-проверка различает `text/event-stream` и объявленные JSON-ошибки до установления потока, а `ValidateSSEEvent` раздельно проверяет JSON-нагрузку каждого события. Сгенерированные объявления включают типы событий. `fetchPost` и `fetchGet` буферизуют весь поток в текст, а `fetchSyncPost` по-прежнему парсит JSON, поэтому не используется для чтения потока событий.

Эндпоинты, допускающие пустые HTTP-ответы, перечисляют разрешённые статусы в `EmptyResponseStatuses` и возвращают `EmptyHTTPResponse`; остальные ответы продолжают использовать свои объявленные структуры. `RedirectHTTPContent` сохраняет стандартный статус перенаправления, заголовок ответа Location и экранированное тело HTML. `RawBody` оставляет непрочитанный сырой поток запроса обработчику протокола. `ProxyOptions` различает байты HTTP, байты EventSource и кадры WebSocket, сохраняя статус апстрима и не интерпретируя его как бизнес-код ошибки ядра. Ошибки допуска прокси и конверт middleware проверяются раздельно. Регистрация `ANY` по-прежнему проверяется по покрытию как одна запись, а при генерации метаданных разворачивается в девять HTTP-методов маршрутизатора. Проверка ответов сохраняет точность чисел JSON, включая целые числа за пределами диапазона чисел с плавающей точкой, не изменяя преобразование чисел на стороне запроса.

Страничные ответы объявляют допустимые комбинации HTTP-статуса и типа медиа через `HTTPContentOptions` и сохраняют сырые байты через `SuccessHTTPContent`, переиспользуя существующую бинарную передачу и раздельно обрабатывая JSON-ошибки middleware. `FastJSON` сохраняет быстрое кодирование JSON для указанных объёмных ответов без изменения типизированной полезной нагрузки и конверта ответа; при ошибке кодирования по-прежнему выполняется откат к стандартному кодировщику.

`WebSocketOutput` объявляет типы входящих и исходящих сообщений и статус ошибки допуска плагина через `WebSocketOptions`. `UpgradeWebSocket` на этапе ответа `contractHandler` передаёт writer в жизненный цикл соединения; `RejectWebSocket` сериализует объявленную нагрузку отказа. Сгенерированные метаданные маршрута включают двунаправленную схему сообщений, а `ValidateWebSocketMessage` раздельно проверяет сообщения внутри соединения, избегая смешения с ответом рукопожатия или конвертом middleware. Проверка рукопожатия проверяет HTTP-статус и тело ответа, а сетевые регрессии проверяют заголовки обновления соединения, отказ по Origin, обмен сообщениями и закрытие соединения после отмены.

Необязательные поля формы `*string` различают непереданное поле и явную пустую строку и используют `nonnullable`, поскольку текст формы не может содержать JSON `null`. Обработчики импорта благодаря этому сохраняют значения по умолчанию и отложенную валидацию. Прогресс загрузки запускается до парсинга формы, а при ошибке парсинга сначала очищается прогресс, затем возвращается ответ; привязка типов переиспользует кэшированную форму Gin.

`BinaryOutput` объявляет сырые файловые ответы через `BinaryContent` и `SuccessBinary`. Адаптер сохраняет байты и тип медиа, а `ErrorStatus` объявляет отдельный HTTP-статус для JSON-ответа об ошибке (`getFile` использует 202). Схема фиксирует бинарный успешный ответ и типизированную JSON-ошибку; `ValidateHTTPResponse` сначала проверяет статус и тип медиа, а затем валидирует конверт ошибки. Сгенерированные ответы маршрутов используют `Blob`, тогда как существующие fetch-функции используют `JSONValue`, поскольку они сохраняют поведение парсинга содержимого файла в текст или JSON. Содержимое JSON-файла может быть произвольным JSON, но структурированный контракт ошибок из-за этого не ослабляется.

`FormBody` используется для интерфейсов вроде `putFile`, принимающих как URL-кодированные, так и multipart-формы. Он сохраняет поведение парсинга Gin `PostForm`, включая взятие первого значения для повторяющихся полей и уже полученные поля при ошибке парсинга. Условная обязательность и отложенная валидация по-прежнему возлагаются на обработчик: создание каталога не требует загрузки файла, а время модификации проверяется после записи. Сгенерированные типы вызовов используют тот же типизированный интерфейс формы, что и multipart-загрузка.

Загрузка файлов использует `MultipartBody`. Структура запроса объявляет строковые поля и поля `*multipart.FileHeader` с именами полей сетевого протокола; схема файла использует `type: string` и `format: binary`, генерируя тип `Blob`. Адаптер сохраняет способ парсинга форм Gin, беря первое значение для повторяющихся полей; содержимое файла продолжает читаться через `Open`, а обработчик сохраняет логику чтения и восстановления. Неподдерживаемые типы полей и параметры привязки приводят к ошибке генерации.

Фиксированное поле, объявленное как `[]*multipart.FileHeader`, принимает все файлы в исходном порядке и генерирует `Array<Blob>`. Необязательный список файлов при пропуске сохраняет `nil`; текстовые и однофайловые поля по-прежнему берут первое значение. `SuccessWithMessage` сохраняет непустые уведомления в успешном ответе, включая частичный успех пакетной загрузки.

Фронтенд конструирует `ContractFormData` из типизированных полей и передаёт его в существующие функции запросов. Сгенерированная сигнатура проверяет обязательные поля эндпоинта и различает файлы и строки; обычный `FormData` не удовлетворяет контракту интерфейса загрузки. Необязательные поля не записываются в форму, а пробелы в строках не обрезаются. Вызывающие стороны в плагинах при конструировании формы могут реализовывать сгенерированный интерфейс `APIFormData<Request>`.

Динамическая загрузка использует `MultipartFields` для сохранения всех текстовых значений и файлов, соответствующих каждому имени поля. Схема запроса отображает имя поля в массив текстовых или бинарных значений, а `ContractFormData` добавляет каждый элемент массива как одноимённое поле формы. Загрузка с фиксированными полями по-прежнему привязывает первое значение. Широковещательная публикация сохраняет порядок «сначала текст, затем файлы» и результаты ошибок по каждому сообщению. Специфичная для эндпоинта обработка `DecodeFailure` сохраняет прежний код ошибки парсинга и полезную нагрузку.

## Генерация и проверка

Генератор считывает предшествующие комментарии объявлений интерфейсов в `kernel/apicontract/contracts.go` и выводит их во фронтенд- и Petal-объявлениях как JSDoc соответствующих записей `APIGETRoutes` и `APIPOSTRoutes`. Поведение интерфейса, значения по умолчанию, ограничения и совместимость сопровождаются в этом объявлении; при использовании группового объявления `var` помещайте комментарий перед конкретным интерфейсом — групповой комментарий не копируется в каждую запись. Комментарии к вспомогательным функциям запросов описывают только транспортное поведение и ссылаются на детали интерфейса через типы маршрутов; не редактируйте сгенерированные объявления вручную.

После изменения контрактов запустите генерацию и проверки в `app/`. Следующие команды также включают полное тестирование фронтенда; выбирайте область регрессии в зависимости от затронутого поведения и рисков, не требуется запускать полные тесты для каждой задачи:

```text
pnpm run api:generate --petal ../../petal
pnpm run api:check --petal ../../petal
pnpm run lint
pnpm test
```

Приведённая команда генерации одновременно обновляет текущий репозиторий и `petal`, запускать отдельно генерацию без `--petal` не нужно. Путь `--petal` задаётся относительно рабочего каталога генератора `kernel/`, пример соответствует соседнему репозиторию. Перед запуском сверьте путь, идентичность, ветку, базовую линию и существующие изменения целевого репозитория; если фактическое расположение отличается, используйте проверенный путь. Если целевой репозиторий недоступен, выполните максимальный объём независимой работы и сообщите о блокировке межрепозиторной синхронизации; не создавайте и не скачивайте другие репозитории автоматически и не заявляйте о завершении синхронизации. CI проверяет только артефакты текущего репозитория, поэтому при локальной межрепозиторной синхронизации используйте этот параметр для сверки объявлений плагина.

`pnpm run lint` включает проверку типов и статический анализ, а также может автоматически исправлять файлы через ESLint; после запуска проверьте дифф, ограничьте изменения рамками задачи и не перезаписывайте чужую работу. Поведенческие тесты он не запускает. При проверке только для чтения используйте применимые немодифицирующие проверки и не запускайте эту команду. Раздельно сообщайте о пройденных, проваленных и незапущенных проверках.

Тот же генератор считывает объявления возможностей полей из `kernel/av/capabilities.go` и выводит `app/src/protyle/render/av/capabilities.generated.ts`, `app/src/types/av/index.d.ts` и соответствующий `petal/types/av/index.d.ts`. Списки возможностей полей и операторов фильтрации сопровождаются в ядре; после изменений перегенерируйте артефакты и не редактируйте вручную сгенерированные типы полей или объединения операторов. Тесты перечисляют Go-константы типов, отклоняют пропущенные объявления и сверяют сгенерированные артефакты через существующую команду проверки генерации и полные тесты ядра.

В `kernel/` запустите `go test ./apicontract/...` и применимые тесты совместимости API и покрытия маршрутов. Когда область влияния требует более широкой проверки, можно запустить полные тесты ядра:

```text
go test -tags "fts5 sqlcipher" ./... -count=1
```

`tsconfig.api.json` отдельно включает строгую проверку и проверяет файлы объявлений, покрывая ошибки параметров, опечатки полей, обязательные тела запросов, ветки успеха и ошибок, nullable-значения и несовпадение методов. Основное приложение продолжает использовать существующую конфигурацию и не предполагает включённой строгой проверки null во всех вызовах. Тесты обработчиков используют временное рабочее пространство и отдельный тестовый процесс, не запуская и не перезапуская работающее ядро.

Тестовые данные для импорта и статических файлов используют `internal/testutil.PublicDataDir` для создания и очистки явно проверенного нечувствительного каталога, не зависящего от `TMPDIR` и `GOTMPDIR`. Эта вспомогательная функция последовательно пробует домашний каталог пользователя, текущий каталог и корень файловой системы; если безопасного и доступного для записи места нет, сообщается об ошибке подготовки тестовых данных. CI также устанавливает `TMPDIR` в `/tmp` и перезапускает затронутые тесты путей с отдельным `GOTMPDIR` для покрытия переопределения переменных окружения.

Предрелизный рабочий процесс `.github/workflows/cd.yml` выполняет проверку языков, контрактов и типов, запускает тесты всех пакетов ядра на Linux и тесты фронтенда, Electron и скриптов сборки на Windows. Он запускается только по пушу предрелизных тегов (`*-alpha*`, `*-beta*`, `*-rc*`) или вручную; обычные пуши веток и PR этот рабочий процесс не запускают. Часть шагов тестирования, включая полные тесты ядра на Linux и тесты фронтенда, имеет `continue-on-error: true`. Поэтому успех задачи или выпуск версии не означает прохождения всех тестов; перед отчётом о результатах проверки следует изучить фактические результаты шагов, логи и отчёты тестов. Данное пояснение не меняет релизные ворота рабочего процесса.

Область обнаружения тестов фронтенда ограничена `src/**/*.test.ts`, `tests/**/*.test.js`, `electron/**/*.test.ts` и `scripts/**/*.test.js`, что исключает упакованные копии в `app/build`. Тестовые файлы запускаются в отдельных процессах с параллелизмом по доступному числу ядер CPU, но не более 4, чтобы ограничить конкуренцию запуска процессов Electron. Последовательное выполнение возможно через `pnpm test --test-concurrency=1`. Новые регрессионные тесты в этих местах подхватываются автоматически; при добавлении новых мест или соглашений об именовании тестовых файлов необходимо синхронно обновить команду тестирования и настоящий документ. В именах регрессионных тестов контрактов Go следует сохранять `Contract` для возможности отдельного запуска.

`pnpm test` остаётся точкой входа для полного прогона, передача файлов не сужает область. Для указания конкретных файлов используйте `pnpm run test:focused scripts/test-changed.test.js`: можно передать один или несколько существующих файлов `.test.ts`, `.test.js` или `.test.mjs`, параметры запуска или неразвёрнутые glob не принимаются; пустой список или неверный путь завершатся ошибкой до запуска тестов. Сначала сделайте предпросмотр через `pnpm run test:changed --explain`, затем запустите `pnpm run test:affected`: стандартный вывод остаётся списком файлов, а стандартный поток ошибок показывает базу, количество и репрезентативные цепочки зависимостей. База по умолчанию — `HEAD`, для проверки закоммиченных изменений ветки используйте `--base <версия>`. Режим `--explain` не усекает область выбранных тестов. Отсутствие найденных связанных тестов означает, что база покрытия ещё не сформирована, а не то, что изменения не имеют влияния; динамические зависимости по-прежнему требуют ручной оценки.
