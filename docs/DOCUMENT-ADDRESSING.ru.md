# Заголовки документов и адресация

[English](DOCUMENT-ADDRESSING.md)

Связанные задачи: [Support `/` in document titles](https://github.com/siyuan-note/siyuan/issues/19938), [Improve content preservation when converting headings to documents](https://github.com/siyuan-note/siyuan/issues/19235), [Improve document titles, notebook names, and plugin compatibility](https://github.com/siyuan-note/siyuan/issues/20837)

Настоящий документ определяет целевое поведение заголовков документов, иерархического позиционирования, человекочитаемых путей, интерфейсов и миграции. Текущая реализация в ветке разработки и условия релиза описаны раздельно; возможности ветки разработки нельзя считать уже выпущенными. Текущий механизм переименования и обновления индекса путей см. в [Переименование документов и индексация путей](DOCUMENT-HPATH.md).

### Текущая область реализации

В ветке разработки уже реализованы единое чтение обычных и форматированных заголовков, метаданные документов, организованные по идентификаторам, и маркеры восстановления фиксации исходников; предоставлены контракты `getDocPaths`, `resolveDocPath`, `getDocCreateTarget`, `planDocCreate`, `createDocByParent` и `getDocTitle`, а также транзакция `setDocTitle`, работающая с полным исходником. Встроенное создание, создание по ссылке, ежедневные заметки, создание из базы данных и быстрые заметки используют создание по ID или общий план создания; экспорт сначала назначает имена файлов по ID документа, а затем использует то же сопоставление для генерации внутренних ссылок. Существующие ID документов и представление обычных заголовков не изменяются, массовая перезапись исходных документов при обновлении не выполняется.

План создания использует фиксированные ID: уже подтверждённые и зафиксированные предки повторно не создаются. Десктоп и мобильное приложение используют общую обработку ошибок: при неясном ответе или сбое последующей обработки план сохраняется, и продолжение возможно только после подтверждения пользователем и сверки по ID; закрытие или блокировка блокнота очищает соответствующие кэши заголовков и шаблонов. Локальные быстрые заметки используют записи восстановления только с ID и сводкой, очищая ввод только после проверки ID блока в фактическом исходнике; неподтверждённые результаты сохраняют исходную быструю заметку и останавливают автоматический повтор.

Администратор при чтении конфигурации блокнота может получить `documentCapabilities` для отчёта о поддержке структурированных интерфейсов, возможностях заголовков и состоянии индекса; доступность по-прежнему ограничена существующими границами авторизации. Нативный импорт всего блокнота продолжает переназначать ID блокнота и якорей, частичный импорт сохраняет целевую конфигурацию; зашифрованная целевая полезная нагрузка сохраняет границы аутентификации, смены пароля и резервного копирования/восстановления.

Все блокноты унифицированно используют правила структурированных заголовков, переключатель режима не предоставляется, миграция режима 1 и поддержание нижней границы возможностей больше не выполняются. Новые записываемые заголовки с ASCII `/` используют как минимум Spec 6, а исходник форматированного заголовка в корневом узле — как минимум Spec 7; совместимость определяется по фактической спецификации исходника и представлению заголовка каждого документа. Старые строковые интерфейсы определяют совместимость по цепочке предков кандидатов. Поддержка по умолчанию не заменяет приёмку релизных сборок, старых данных, производительности и кроссплатформенности.

## Цели и область охвата

Документ использует ID для определения идентичности и принадлежности к иерархии, заголовок — для выражения содержимого, а человекочитаемый путь — для отображения. Создание, перемещение и цитирование не должны зависеть от обратного парсинга идентичности документа из отображаемого текста. После завершения миграции соответствующих точек входа и проверки совместимости заголовок документа сможет содержать полуширинный слеш `/`, сохраняя отличие от прежнего полноширинного слеша `／`.

Заголовок документа поддерживает существующую нативную модель строчного содержимого, включая изображения, гиперссылки, подчёркивание и другие стили текста, ссылки на блоки, теги, строчные формулы, строчные заметки, ссылки на аннотации файлов, эмодзи, сущности и экранирование. Сырые HTML-узлы (`NodeInlineHTML`) отклоняются. Адресация, отображение заголовка, извлечение обычного текста и представление хранения остаются разделёнными. Задача #20837 покрывает полный исходник заголовка, редактирование, обратные ссылки заголовков, двустороннее преобразование, сохранение `/` в именах блокнотов и адаптацию плагинов. Приёмка реальных версий сторонних плагинов требует отдельных доказательств — нельзя считать все плагины совместимыми лишь на основании наличия заменяющих контрактов.

Решение охватывает десктоп, браузер, мобильное приложение, интерфейсы ядра и данные, видимые плагинам, соблюдая соответствующие границы доступа обычных и зашифрованных блокнотов. Имя блокнота остаётся обычным текстом конфигурации; создание, переименование и выравнивание документа блокнота как для обычных, так и для зашифрованных блокнотов различают и сохраняют `/` и `／`. Документ блокнота принимает те же транзакции форматированного заголовка, что и обычный документ: после редактирования полного исходника приоритет имеет заголовок документа, а имя блокнота следует за его текстовой сводкой (при пустой сводке используется текст-заполнитель «Без названия»). Существующие документы блокнота, ещё не перешедшие на редактирование полного исходника, продолжают следовать имени блокнота из конфигурации.

### Принятые решения

| Элемент | Выбранное решение |
| --- | --- |
| Позиционирование документа | ID блокнота и ID документа; для создания используются независимый ID родительского документа и заголовок |
| Правила адресации | Все блокноты унифицированно используют структурированные заголовки; версия `2` в конфигурации служит только диагностическим маркером |
| Совместимость плагинов | Принимается адаптация плагинов, зависящих от старых правил `hPath`; сначала поставляются заменяющие интерфейсы и инструкции по миграции, затем включается новый символ |
| Старая строковая адресация | Определяется по реальной цепочке предков кандидатов; чистые пути сохраняют совместимость, конфликты со слешем или пустым заголовком явно отклоняются |
| Человекочитаемый путь | Сохраняет исходный текст заголовка и склеивает его по иерархии для отображения; `/` не кодируется, `／` и `%2F` не декодируются |
| Индекс | Сохраняется существующий столбец `hpath`, добавляются внутренние метаданные уровня документа; массив сегментов заголовка не дублируется для каждого блока содержимого |
| Исходник заголовка | Сохраняются существующие обычные заголовки; форматированный заголовок использует версионированное корневое поле и однонаправленно порождает текстовую сводку |
| Совместимость версий | Поддержка определяется по фактической спецификации исходника и представлению заголовка документа, без массовой миграции блокнотов; безопасность смешанного использования со старыми клиентами не гарантируется |

`/A/B` может означать как двухуровневый документ, так и один заголовок. Старый запрос возвращает результат только тогда, когда все заголовки предков данного кандидата непусты и не содержат `/`; при конфликте возвращается явная ошибка. Операции по ID и структурированные заменяющие интерфейсы продолжают работать — отображаемый путь нельзя использовать как стабильный идентификатор.

Базовая декомпозиция не требует новых сторонних сервисов, сетевых передач или зависимостей. Реализация продолжает соблюдать лицензионные требования репозитория и существующих зависимостей; при выборе новых зависимостей в будущем их лицензии необходимо проверять отдельно. Основные затраты — миграция вызывающих сторон, перестроение индекса и кросс-версионная проверка. Кэши, логи и ответы об ошибках для заголовков и цепочек предков по-прежнему ограничены границами зашифрованных блокнотов — добавление структурированных полей не должно расширять область видимости данных.

## Заголовки, идентичность и пути

### Текущие источники данных

Обычный заголовок документа хранится в IAL `title` корневого узла; форматированный заголовок использует корневой исходник `DocumentTitle`, а IAL `title` и `custom-sy-title-empty` являются производными полями совместимости. Файлы `.sy` и каталоги используют ID в качестве имён; `tree.HPath`, `blocks.hpath` и `blocktrees.hpath` порождают отображаемый текст из заголовков. Запись заголовков во всех блокнотах сохраняет `/`, без применения разных правил нормализации по режимам.

Часть текущей логики использует `hPath` для поиска по имени, создания документов, вычисления уровня или извлечения заголовка. Эти сценарии необходимо мигрировать по одному, а не просто переименовать `hPath` в отображаемое поле. Обратимое кодирование может решить неоднозначность разделителей в конкретном строковом протоколе, но всё равно требует версионирования формата и правил совместимости; данное решение снижает внутреннюю зависимость от этого протокола за счёт разделения обязанностей.

### Целевая модель

Названия в таблице ниже обозначают концепции и не задают напрямую имена новых полей интерфейсов или хранения.

| Концепция | Содержание и назначение | Ограничения |
| --- | --- | --- |
| Идентичность документа | ID блокнота и ID документа | Область доступа проверяется по фактической принадлежности; нельзя заменять заголовком |
| Идентичность родителя | Целевой блокнот и ID родительского документа либо явный корень блокнота | При создании и перемещении проверяется, что родитель существует и принадлежит целевому блокноту |
| Путь данных ID | Путь каталогов из ID и имя файла `.sy` | Используется для хранения и запросов поддерева; может меняться при перемещении, не является постоянным ID |
| Содержимое исходника заголовка | IAL `title` для обычного заголовка, корневой `DocumentTitle` для форматированного | Записывается только авторитетный исходник; нельзя перезаписывать форматированный исходник сводкой |
| Текстовый заголовок | Обычный текст, извлечённый из содержимого исходника заголовка | Используется для текстового поиска, сортировки и совместимого вывода; без HTML и маркеров подсветки поиска |
| Структурированная цепочка предков | Упорядоченный по иерархии список ID документов и сведений о заголовках | Сохраняет границы сегментов; имя блокнота хранится отдельно и не восстанавливается из отображаемой строки |
| Массив сегментов заголовка | Входные данные для поуровневого сопоставления или создания документов от явной позиции | Устраняет только неоднозначность разделителей, не гарантирует уникальность имени |
| Человекочитаемый путь | Отображаемое содержимое для хлебных крошек, подсказок или копирования пути | Может использовать разные формы отображения; не отвечает за адресацию или восстановление исходных данных |
| Старый протокол путей | Строки `hPath`, `hpath` в существующих интерфейсах и плагинах | Совместимость сохраняется только для чистых кандидатов, прошедших проверку цепочки предков |
| Относительный путь экспорта | Расположение файла, назначенное документу задачей экспорта | Определяется картой экспорта, отдельно от заголовка и отображаемого пути интерфейса |

Текущий параметр `idPath` в конфигурации поиска фронтенда представляет собой массив строк областей поиска, где каждый элемент может содержать ID блокнота и путь ID документов; это не поуровневый массив ID одного пути. При миграции необходимо сохранить прежнюю интерпретацию конфигурации. `parent_id` в дереве блоков обозначает родительский узел блока и также не может напрямую использоваться как ID родительского документа.

Следующие две структуры могут отображаться одинаково как `/A/B`, но обязаны сохранять разные идентификаторы документов и цепочки предков:

| Сегменты заголовка | Структура документов |
| --- | --- |
| `["A/B"]` | Один документ с заголовком `A/B` в корневом каталоге |
| `["A", "B"]` | Документ с заголовком `A` и его дочерний документ с заголовком `B` |

Хлебные крошки должны отображать границы с использованием структурированной иерархии. Скопированный текстовый путь предназначен только для чтения; ссылки и цитаты, используемые для навигации, обязаны содержать ID. Одноимённые документы под одним родителем допустимы — нельзя объединять идентичности из-за совпадения сегментов заголовка.

### Чтение заголовков и метаданные документов

Единое чтение заголовка возвращает сводку `{format, text, empty}`, а метаданные документа отдельно фиксируют спецификацию исходника. `format: "plain"` читает прежний IAL-заголовок и флаг пустоты; `format: "inline-ast"` порождается из прошедшего проверку полного исходника. Текст-заполнитель старых документов массово не перезаписывается, а подсказка пустого заголовка в интерфейсе не является основанием для сопоставления по имени. Пустой исходник отличается от пустой видимой сводки: исходник только с изображением или сохраняющий строчные метаданные может не иметь текста сводки, но при этом не является пустым исходником.

В обычной `blocktree.db` и в базах данных дерева блоков каждого зашифрованного блокнота добавляется внутренняя таблица `document_metadata` по одной строке на документ. Порядок столбцов существующей `blocktrees` остаётся неизменным, чтобы не нарушать раскладку столбцов для существующих сканирований и запросов плагинов.

| Поле | Значение |
| --- | --- |
| `box_id`, `id` | Составной первичный ключ: ID блокнота и ID документа соответственно |
| `parent_id` | ID родительского документа; для логического корня — SQL `NULL`, в отличие от `parent_id` узла дерева блоков |
| `title_text`, `title_empty` | Текст, извлечённый из исходного заголовка, и флаг пустого заголовка |
| `title_format`, `source_spec` | Представление заголовка и версия исходного документа |
| `revision` | Сводка версии идентичности, позиции, содержимого исходника заголовка и статуса пустоты |

Создаётся индекс `(box_id, parent_id, title_text, id)` для точного поиска по имени под текущим родительским документом. Сопоставление имён использует регистрозависимое сравнение исходного текста Unicode без преобразования ширины символов, процентного кодирования или нормализации Unicode; поиск может продолжать использовать собственные правила токенизации и регистра. Пустой заголовок не может служить условием автоматического сопоставления при неизвестном родителе — необходимо указывать ID родителя.

`document_metadata` является перестраиваемым внутренним индексом и не вводит обязательств по новой публичной SQL-таблице. Позиционирование использует текущие метаданные в БД дерева блоков, а плагины могут получать ID родителя, заголовок и глубину через структурированный интерфейс чтения. Столбец `content` строки документа в существующей базе содержимого продолжает хранить текстовое представление заголовка, а `hpath` остаётся копией человекочитаемого пути.

Метаданные документа и строка документа дерева блоков обновляются в одной транзакции базы данных. Добавление, переименование, перемещение, удаление, копирование, импорт и перестроение при синхронизации обязаны обновлять или очищать соответствующую строку. Кэш заголовков индексируется по идентичности блокнота и документа и проверяется по сводке версии; нельзя заимствовать данные одноимённого документа из другого блокнота.

### Вывод структурированных путей

`DocumentPath` содержит `notebook`, `id`, `parentID`, `path`, `title`, `segments`, `depth`, `displayPath`, `revision`. `title` имеет вид `{format, text, empty}`, а `segments` в порядке от корня к текущему документу содержат `{id, text, empty}`. `displayPath` начинается с `/` и соединяет сегменты через `/`, пустой массив сегментов отображается как `/` и служит только для показа; имя блокнота возвращается отдельно или получается вызывающей стороной и не смешивается с массивом сегментов. Здесь `title` — это сводка заголовка, которую нельзя записывать обратно как полную копию форматированного исходника.

Для обычного корневого документа `depth` равен `1`, а `parentID` равен `null`. При включённой функции документа блокнота сам документ блокнота имеет `depth` равный `0` и пустой `segments`, а обычные корневые документы остаются на первом уровне; он не добавляет дополнительный физический каталог. Передача ID документа блокнота при создании эквивалентна явному корню и следует существующему сопоставлению логического корня. Запрос дочерних документов по имени в корне исключает сам документ блокнота, чтобы не принять его за обычный корневой документ.

Сводка версии пути использует версионированную сериализацию с чёткими границами полей, охватывающую ID предков, версию заголовка и текущую позицию; нельзя использовать только секундное время обновления. Прямое создание по ID родителя может следовать за актуальной позицией родительского документа; когда требуется сохранить результат предпросмотра, передаётся `expectedParentRevision` — переименование предка или изменение позиции сделают это значение недействительным. Сводка используется только для проверки согласованности и не является учётными данными доступа через границы прав.

## Строчный исходник заголовка и операции

Форматированный заголовок хранит единственный авторитетный исходник `DocumentTitle` в корневом узле: `{spec: 1, format: "inline-ast", content: string}`. `content` представляет собой прошедший проверку канонический JSON-массив нативных строчных узлов, а не Markdown или отрендеренный HTML. Документ требует `.sy` Spec `7`; версия конверта заголовка, спецификация документа и режим адресации блокнота интерпретируются раздельно. Строчные узлы не имеют независимых ID блоков. Неизвестная версия конверта, неизвестные поля или типы узлов, некорректная структура и блочное содержимое отклоняются до записи с сохранением исходного текста. Правила сериализации см. в [Формат файла `.sy`](SY-FORMAT.zh-CN.md).

Набор элементов определяется существующей нативной строчной моделью и рендерером. Синтаксис `**текст**`, обратные апострофы и ссылки в старых заголовках сохраняют буквальное значение до тех пор, пока пользователь явно не изменит их через операцию с исходником; простое открытие или сохранение без изменений не интерпретирует и не обновляет их автоматически. При записи заголовка содержимое, которое можно без потерь свести к обычному тексту (включая пустой заголовок), сохраняется только как обычный заголовок без добавления `DocumentTitle`; стили, ресурсы, ссылки и строчные переносы строк сохраняют полный исходник. Существующие строчные исходники по-прежнему читаются и восстанавливаются; чтение не вызывает перезапись, а удаление исходника не понижает спецификацию документа. Форматированная запись сохраняет полный исходник без усечения по правилу 512 символов обычного заголовка или длине анкорного текста ссылки. Валидация исходника ограничивает строчный JSON размером 1 MiB, 8 192 узлами и 64 уровнями вложенности; верхний предел ввода BlockDOM составляет 4 MiB. Обычные интерфейсы создания продолжают соблюдать отдельные правила валидации заголовков, описанные ниже.

IAL `title` форматированного заголовка является лишь производным обычным текстом, содержащим видимый текст, текст ссылок, альтернативный текст изображений и содержимое строчных формул, с заменой переносов строк на пробелы, без адресов ресурсов и скрытого текста заметок. Стили не определяют идентичность. Пустой исходник, заголовок только с изображением и заголовок, сохраняющий узел метаданных с пустым текстом, различаются между собой. Заголовок в тексте документа, верхняя панель на мобильных устройствах, дерево документов и вкладки рендерят форматированный исходник; сохраняемое отображаемое имя, заголовок системного окна, хлебные крошки, сортировка и поиск используют текстовую сводку. Обычный текст по-прежнему экранируется, а форматированный текст переиспользует нативную валидацию и рендеринг. При прямом редактировании заголовка выполняется автосохранение, а черновик в диалоге переименования отправляется только после подтверждения и отменяется при закрытии.

`/api/filetree/getDocTitle` читает документ по `id` и необязательному `notebook`, возвращая идентичность, `format`, `text`, `empty`, `blockDOM`, `source` и `revision`; для обычного заголовка `source` равен `null`. BlockDOM является лишь проекцией для редактирования и предпросмотра и не создаёт блок абзаца под документом. Публичная сводка заголовка и возвращаемое значение `getDocPaths` не могут напрямую использоваться как запрос на запись исходника.

Изменение заголовка отправляется через отдельную однооперационную транзакцию `/api/transactions`: операция `setDocTitle` с ID документа, где `data` содержит `expectedRevision` и ровно одно из полей `blockDOM` или `source`. BlockDOM может содержать строчное содержимое только одного абзаца; снимок отмены генерируется ядром. Версия охватывает изменения текста, стилей, идентичности ссылок и других изменений исходника, исключая обновление кэша динамического анкорного текста. Устаревшая версия возвращает ответ `code: -409`; вызывающая сторона обязана сохранить черновик и перечитать данные, не перезаписывая и не повторяя отправку со сводкой. Отмена и повтор заголовка восстанавливают только состояние заголовка и не перезаписывают одновременные правки основного текста. Документ блокнота использует ID блокнота, следует тем же проверкам принадлежности ссылок и шифрованного доступа, а отмена/повтор также обновляют имя блокнота. Старое переименование блокнота и запись имени в конфигурацию следуют прежним правилам защиты форматированного заголовка при старом переименовании документа.

Старое переименование и интерфейсы корневых атрибутов не могут перезаписывать форматированный заголовок через текстовую сводку. Запись неподдерживаемого исходника завершается ошибкой, а операции с основным текстом обязаны сохранять корневой исходник заголовка. Аутентификация, статус доступности для записи, принадлежность блокноту и аренда шифрованного ответа продолжают применяться; возможности формата не дают прав доступа.

Ссылки и ресурсы в заголовке относятся к корневому ID документа. Сохраняется существующее правило подсчёта `(block_id, def_id)`: повторные ссылки на одну и ту же цель в заголовке считаются один раз, а ссылки из блоков основного текста на ту же цель остаются независимыми источниками. Группировка, сортировка и глобальные обратные ссылки отображают размеченный фрагмент заголовка только для чтения без разворачивания всего основного текста; открытие источника переходит к настоящему редактору заголовка документа, а временный предпросмотр нельзя отправлять как обновление абзаца основного текста.

Динамический анкорный текст обновляется из текущих зависимостей исходника, статический анкорный текст сохраняет исходный текст. Самоссылки и циклические ссылки внутри компоненты цикла используют локальный текст цели, а при отсутствии локального текста откатываются к ID, не разворачивая рекурсивно кэшированный анкорный текст. Переназначение ID при копировании и импорте, обход ресурсов, история, синхронизация и экспорт включают исходник заголовка. Ссылки через границы шифрования по-прежнему отклоняются, а защищённые заголовки всегда остаются в пределах аутентифицированного чтения, кэширования и восстановления соответствующего блокнота.

### Преобразование блоков заголовков и документов

`Heading2Doc` сначала проверяет и копирует полный нативный строчный исходник блока заголовка, используя ID исходного блока заголовка в качестве ID нового документа; содержимое раздела под исходным заголовком переносится в основной текст без создания дополнительного дублирующего абзаца заголовка, а уровни нижележащих заголовков корректируются по существующим правилам преобразования. `Doc2Heading` восстанавливает полное строчное содержимое заголовка в блок заголовка с тем же ID, сохраняя каждый исходный блок основного текста, включая абзацы, текст которых полностью совпадает с заголовком. Обычный заголовок преобразуется в блок заголовка по буквальному тексту; существующие документы не повышают первый абзац до заголовка автоматически.

Неподдерживаемые исторические исходники заголовков отклоняются до изменения любого из документов. Оба направления проверяют границы шифрования, сначала сохраняют цель, затем удаляют содержимое из источника, публикуя ссылки и принадлежность блоков только после полного успеха операций с источником. При ошибке записи или удаления используется условная компенсация по аутентифицированному исходному снимку без перезаписи конкурентных правок и без удаления заранее существовавшей цели. Это восстановление при сбое ограничено операцией преобразования и не является универсальной межфайловой атомарной транзакцией, изолирующей произвольные файлы или внешние изменения.

Приёмка round-trip для #19235 теперь охватывает всё поддерживаемое строчное содержимое, идентичность исходника, метаданные изображений и ссылок, сохранение основного текста и восстановление после сбоев. Совпадение обычного текста никогда не является основанием для удаления основного текста пользователя.

## Создание и шаблоны путей

### Создание по идентичности

Когда родительский документ известен, запрос на создание выражает целевой блокнот, ID родительского документа или корень, отдельный заголовок и основной текст. Ядро перед фактической записью разрешает путь данных ID по текущей идентичности и заново проверяет принадлежность, статус доступности для записи, действительность родительского документа и аренду операции зашифрованного блокнота. Межблокнотное перемещение могло изменить принадлежность, поэтому устаревший параметр блокнота обязан возвращать ошибку без отката к поиску в других блокнотах или среди одноимённых документов.

При прямом создании без версии предпросмотра после переименования родительского документа или его перемещения внутри того же блокнота создание всё равно происходит по текущей позиции этого ID. Запросы с `expectedParentRevision`, предпросмотр создания и планы дерева документов шаблона обязаны проверять соответствующие версии заголовка и позиции и возвращать `planChanged` при изменении, чтобы вызывающая сторона выполнила повторный предпросмотр. Эти два поведения явно различаются запросом — нельзя считать предпросмотр действительным только потому, что ID документа не изменился.

Разрешение идентичности родителя, финальная проверка и фиксация исходного документа должны находиться в общей области координации изменений с переименованием, перемещением и удалением, чтобы позиция родителя не изменилась после проверки. Сохраняется существующий порядок очереди транзакций и блокировок; нельзя ожидать завершения очереди, удерживая блокировку, необходимую для выполнения самой очереди. Отмена запроса, закрытие блокнота или его блокировка не должны оставлять пригодную к использованию устаревшую аренду.

Текущий `createDocWithMd` при передаче `parentID` всё ещё может откатываться к разрешению по имени при несовпадении `hPath`, и существующие регрессионные тесты требуют сохранения этого поведения. В новом протоколе предусмотрен отдельный вход для строгого создания по ID родителя, без изменения смысла старых параметров. Мигрированные внутренние вызовы напрямую передают структурированную цель; запрещено сначала склеивать `hPath`, а затем вызывать старый резолвер.

Обычное создание, переиспользование ежедневной заметки и добавление содержимого в существующий документ — разные операции. Вызывающая сторона обязана явно указать, допустимо ли переиспользование цели, а не определять объект записи неявно через однократный поиск по заголовку. Миграция должна сохранять прежние требования к применению шаблонов, записи атрибутов, сортировке, отправке сообщений и синхронной записи на диск; например, сценарий быстрых заметок, очищающий исходные данные после успеха, обязан сначала подтвердить успешную запись цели.

### Валидация заголовка в новом протоколе

Новый интерфейс создания требует явной передачи `title: {format: "plain", text: string}`. Пропуск `title`, передача `null` или неизвестного `format` являются ошибкой; `text: ""` означает пустой заголовок, следуя `custom-sy-title-empty` и существующему механизму хранения заполнителя. При чтении одновременно возвращаются фактический обычный текст и `empty`, редактор восстанавливает пустой ввод по флагу, не принимая локализованный текст-заполнитель за пользовательский заголовок.

Заголовок сохраняет верхний предел в 512 кодовых точек Unicode и существующие ограничения на невидимые символы и область частного использования, сохраняя ZWJ, необходимый для составных эмодзи. Новый интерфейс отклоняет превышение длины, запрещённые символы, пробелы по краям и отдельные `.` и `..`, возвращая `invalidTitle`; `/` внутри заголовка разрешён, входные данные не усекаются и не заменяются незаметно при сохранении.

Режим структурированных заголовков не выполняет очистку файловых путей, преобразование ширины символов, процентное декодирование или нормализацию Unicode. `/`, `／`, `%2F`, подряд идущие слеши и `A/../B` сохраняются в исходном виде, а иерархия определяется только идентичностью родителя. Обычное создание допускает одинаковые имена под одним родителем и возвращает новый ID без неявной перезаписи или переиспользования существующего документа.

### Разрешение по сегментам заголовка

Когда требуется поуровневое создание по имени, входные данные содержат явную отправную точку и массив сегментов заголовка. Если ID предка известен, используется непосредственно эта идентичность; неизвестные предки сопоставляются поуровнево под текущим родительским документом. При отсутствии совпадения создание выполняется по правилам операции, а при наличии нескольких совпадений возвращается неоднозначность и кандидаты в пределах авторизованной области — нельзя произвольно брать первый элемент. Общий резолвер не ищет потомков через одноимённых родителей, чтобы угадать намерение пользователя.

`/` в структурированном сегменте заголовка не разбивает иерархию, а `.` и `..` не выполняют навигацию. Переход на уровень вверх, старт от корня блокнота и старт от текущего документа должны выражаться раздельно. Пустой массив сегментов означает саму отправную точку, а пустая строка не может использоваться для автоматического сопоставления родительского документа с пустым заголовком; итоговый создаваемый пустой заголовок по-прежнему можно передать явно. Допустимость создания отсутствующих предков определяется политикой `onMissingParent` вызывающей стороны.

Результат сопоставления имён и версия пути родителя являются разными условиями фиксации. `nameConditions` фиксирует `{parentID, title, expectedID}`: `parentID` — это ID родительского документа или `null` для логического корня, непустой `title` точно сопоставляется по единым правилам обычного текста; `expectedID: null` означает, что одноимённый дочерний документ по-прежнему отсутствует, а ID документа означает, что единственным совпадением по-прежнему является этот документ. Пропуск `expectedID` недействителен. Максимум 128 условий, которые могут затрагивать только блокнот текущей цели, его реальную цепочку предков и конечного родителя — нельзя использовать их для перечисления посторонних позиций. ID документа блокнота предварительно нормализуется к логическому корню, а запрос исключает сам документ блокнота и значения-заполнители пустого заголовка.

При создании отсутствующих предков необходимо передать соответствующие условия отсутствия и сохранить условия уникальной идентичности предков, ранее сопоставленных по имени. Ядро выполняет повторный запрос в общей области координации с созданием, переименованием, перемещением и удалением и удерживает её до завершения фиксации исходного документа и метаданных; при невыполнении любого условия возвращается `planChanged`, вызывающая сторона выполняет повторное разрешение и не переиспользует автоматически только что появившийся одноимённый документ. Когда две вызывающие стороны одновременно создают одноимённого предка, условие отсутствия выполняется максимум у одной. Обычное создание конечного документа может опускать условия имени, продолжая допускать одинаковые имена под одним родителем и не добавляя уникальный индекс на заголовок. `expectedParentRevision` не может заменять эти условия.

### Фиксация, частичный сбой и повторная попытка

Первая версия не предоставляет межфайлового атомарного создания. План создания перед записью проверяет предсказуемые ошибки заголовка, глубины, неоднозначности, шаблона и прав, назначает фиксированный ID и фиксирует идентичность и версии предков; при фиксации выполняется повторная проверка. Конкурентное изменение одноимённых документов требует повторного планирования, нельзя незаметно переключиться на другой документ.

Общее многоуровневое создание фиксируется по одному документу за раз; существующее дерево документов шаблона по-прежнему сохраняет общую транзакцию и группу отмены для правки родительского документа и создания дочерних документов — нельзя разбивать их на несвязанные пользовательские операции из-за миграции логики позиционирования. Успешный ответ требует, чтобы исходный документ и необходимые для данной операции изменения основного текста и атрибутов были синхронно сохранены на диск, а метаданные документа стали доступны для чтения; полнотекстовый индекс поиска может обновляться асинхронно по существующему механизму. Шаблоны, сноски, математическое содержимое, источник клиппинга, теги, сортировка и уведомления об обновлении выполняются по прежней бизнес-семантике и не должны теряться при разделении логики позиционирования.

При сбое во время записи уже сохранённые на диск документы сохраняются. Данные ошибки различают `commitState: "none"`, `"committed"`, `"unknown"` и возвращают подтверждаемый ID документа, этап сбоя и выполненные шаги; `committed` означает только фиксацию исходного документа, а не успех всех последующих действий. Если состояние записи на диск невозможно подтвердить, необходимо вернуть `unknown` — нельзя утверждать, что запись не выполнялась. Многоуровневая операция одновременно сохраняет исходный план и выполненные ID, предоставляя пользователю точку продолжения.

Вызывающая сторона сохраняет назначенный ID перед отправкой. При потере ответа или неизвестном результате сначала выполняется необходимое восстановление индекса, затем сверка исходного документа и цели по исходному ID без переназначения ID. Повторная отправка существующего ID возвращает `documentIDConflict` без перезаписи документа и не трактует «ID уже существует» напрямую как тот же успешный запрос. Первая версия не обещает автоматического идемпотентного повтора; шаги с побочными эффектами, такие как шаблоны или добавление текста, нельзя выполнять повторно без сверки.

Восстановление обрабатывает только незавершённые шаги и не удаляет автоматически уже успешно созданный родительский документ. Неповторяемые последующие операции, такие как очистка исходных данных, выполняются только после полного успеха всех шагов, необходимых для бизнес-операции; частичного успеха и простого получения ID документа недостаточно для запуска удаления исходных данных быстрой заметки.

После штатного завершения дерева документов шаблона отмена и повтор сохраняют прежнюю семантику группировки и переназначения ID для изменения родительского документа и созданных документов. При частичном сбое записи восстановления и отмены должны опираться на фактически выполненные шаги и не затрагивать незафиксированные документы; повтор использует сохранённый снимок плана без повторного выполнения чувствительных ко времени шаблонов. При последующем изменении существующего или созданного документа применяется проверка конфликта транзакций — нельзя удалять эти правки под предлогом очистки неудачного плана. Если невозможно подтвердить выполнение побочных эффектов, автоматическое продолжение останавливается и показываются подтверждённые результаты; маркер восстановления индекса не считается доказательством успеха бизнес-операции.

### Версии шаблонов

Старые строковые пути сохранения продолжают использовать прежние правила интерпретации, включая абсолютные и относительные пути, `..`, завершающий `/`, пустые шаблоны, межблокнотный контекст и замену последнего сегмента явным именем. Новый синтаксис обязан иметь распознаваемую версию — нельзя автоматически переинтерпретировать существующую конфигурацию по новым правилам.

Старый шаблон вычисляется компилятором совместимости по прежнему синтаксису и порождает структурированный план; новый заголовок передаётся отдельно. Относительная навигация использует ID документа и родительские связи. `/` внутри переменных в старом синтаксисе по-прежнему делит уровни и сохраняется как один сегмент только после явного перехода на новый шаблон.

Все встроенные операции создания используют строгий структурированный план и не выбирают произвольно одноимённого предка. Публичный старый интерфейс создания сохраняет устранение неоднозначности по действительному и совпадающему `parentID` и прежний откат при отсутствии конфликта; когда набор одноимённых документов не позволяет однозначно определить позицию, возвращается `pathAmbiguous`.

`docCreateTarget`, `refCreateTarget` и `dailyNoteTarget` сосуществуют со старыми полями шаблонов и доступны во всех блокнотах. Объект имеет `version: 2` и задаёт блокнот, отправную точку, число шагов вверх, сегменты предков, итоговый заголовок и политику при отсутствии; глобальные старые шаблоны и правила наследования сохраняются, а синтаксис пути сохранения и синтаксис шаблона основного текста интерпретируются раздельно.

```json
{
  "version": 2,
  "notebook": "20210808180117-6v0mkxr",
  "anchor": {"kind": "notebookRoot"},
  "up": 0,
  "parents": ["Daily notes", "{{now | date \"2006-01\"}}"],
  "title": "{{now | date \"2006-01-02\"}}",
  "onMissingParent": "create"
}
```

`anchor` также поддерживает `{kind: "context"}` и `{kind: "document", id: string}`. `context` обязан разрешаться в текущий документ внутри целевого блокнота и не может угадывать отправную точку при межблокнотности; при отсутствии контекста возвращается ошибка. `up` — неотрицательное целое число; выход за пределы логического корня завершается ошибкой. `parents` может быть пустым, `onMissingParent` обязан быть `create` или `error`; если вызывающая сторона явно передаёт заголовок, он напрямую заменяет результат вычисления `title`. Политика переиспользования конечного документа определяется такими операциями, как ежедневная заметка, и не включается в общий шаблон пути.

Новый шаблон определяет границы сегментов до рендеринга, и каждый сегмент заголовка вычисляется независимо. При значении переменной `A/B` она остаётся одним сегментом заголовка; предварительный рендеринг в одну строку с последующим `split("/")` не соответствует протоколу. Все сегменты одного создания используют единый снимок контекста и времени, а ежедневная заметка передаёт `now` по указанной календарной дате во избежание смены даты или контекста.

Когда действует новый объект, он является единственным авторитетным параметром конфигурации для соответствующей операции; возврат старых полей без изменений допускается, но изменение их на конфликтующие значения должно отклоняться. После удаления нового объекта возвращается вычисление старого шаблона при неизменных правилах адресации. При отсутствии нового объекта сохраняется существующий порядок наследования; межблокнотные цели продолжают проверять формат исходника и права доступа.

Предпросмотр, сформированный из конфигурации, сохраняет исходный блокнот конфигурации, бизнес-назначение, действующую версию конфигурации и вычисленный контекст. При фиксации конфигурация проверяется с помощью `expectedTarget: {notebook, purpose, revision}`, где `notebook` — это блокнот-источник чтения конфигурации, который может отличаться от целевого блокнота запроса на создание. Версия охватывает действующую цель, участвующую в наследовании конфигурацию и выбранный путь шаблона основного текста; посторонние настройки не делают предпросмотр недействительным. Ядро в области координации, общей для обновления конфигурации и изменения документов, заново разрешает действующую конфигурацию, проверяет версию и целевой блокнот и затем фиксирует; при изменении конфигурации возвращается `planChanged`, и продолжение невозможно даже при неизменном пути родителя. Предпросмотр основного текста шаблона отдельно сохраняет отрендеренное содержимое и снимок зависимостей — нельзя заменять проверку снимка основного текста версией конфигурации.

### Миграция бизнес-входов

| Точка входа | Сохраняемое бизнес-поведение и фокус миграции |
| --- | --- |
| Обычное создание и создание по ссылке на блок | Прямое создание по известному ID родителя; новый заголовок передаётся отдельно, созданная ссылка сохраняет ID документа |
| Кнопка и горячая клавиша ежедневной заметки | Дата не указана — переиспользование цели по вычисленному на сегодня шаблону имени и пути; после переименования или перемещения прежней ежедневной заметки она перестаёт соответствовать цели, и может быть создана новая |
| Ссылка на дату и интерфейс указанной даты | Сначала переиспользование по атрибуту даты ежедневной заметки в целевом блокноте; при нескольких совпадениях приоритет у цели шаблона, иначе выбор по возрастанию ID; при отсутствии совпадения по дате — переиспользование или создание цели шаблона |
| Быстрая заметка | Явное указание цели добавления или новой цели; очистка источника только после успешной записи цели на диск |
| Новая запись базы данных | Сохранение значений атрибутов, связей привязки и сортировки; план создания сохраняет итоговый ID документа |
| Дерево документов шаблона | Сохранение предпросмотра, переназначения ID, порядка вставки и групповой отмены/повтора; при фиксации проверяются условия пути, имени и конфигурации и отображается частичный результат |
| MCP и встроенный Agent | Инструменты документов в первую очередь используют блокнот и `parentID`, пустая строка означает корень; старый путь переиспользует проверку цепочки предков, неоднозначность одноимённой цели возвращает ошибку |
| Десктоп, браузер и мобильное приложение | Раздельная проверка меню, горячих клавиш, диалогов и обработки событий; миграция общих утилит не заменяет проверку на каждой платформе |

Ежедневная заметка сохраняет бизнес-границы двух точек входа: `createDailyNote` при пропуске `date`, передаче пустой строки или `null` следует политике цели шаблона обычной кнопки; явная передача даты (включая сегодняшнюю) и `getDailyNoteInfo` ищут по атрибуту даты. Переименованная или перемещённая прежняя ежедневная заметка всё ещё может переиспользоваться входом по дате, но обычная кнопка может создать новую цель шаблона; после того как эта цель также получит атрибут сегодняшней даты, вход по дате выберет её в приоритете. Оба входа при переиспользовании существующей ежедневной заметки не применяют повторно шаблон основного текста. Несколько совпадений по одной дате сохраняют указанный порядок выбора, не превращаясь в безусловную ошибку; сопоставление цели шаблона использует сравнение структурированной цепочки идентичности.

## Поиск и производные индексы

Замена в заголовке документа управляется параметром `docTitle`. Форматированный заголовок выполняет сопоставление по видимому тексту сквозь строчные узлы, поддерживает разворачивание групп захвата регулярных выражений, сохраняет текст замены буквально и наследует стиль носителя в начале совпадения. Адрес ссылки, путь изображения, текст заметки и ID ссылки сохраняются как метаданные исходника; после изменения видимого анкорного текста динамической ссылки она превращается в статическую, что соответствует правилам замены в основном тексте. Фиксация использует аутентифицированные исходные байты в качестве условия конкурентности; отклонённая замена не должна перезаписывать последующие правки или очищать их историю отмены.

Структурированная цепочка предков предоставляет единый источник данных; отображение в интерфейсе, вывод старого протокола, текстовый поиск и экспорт используют правила преобразования, подходящие для каждого назначения. Унифицируется источник заголовков и иерархии — не требуется, чтобы все потребители использовали один и тот же результат строковой сериализации.

Глубина документа, отношения «родитель-потомок» и область поддерева вычисляются по пути данных ID или явным связям документов. Запрещено выводить структуру по числу слешей в `hPath`, `path.Base(hPath)`, `path.Clean(hPath)` или обрезке отображаемой строки по глубине. Заголовок документа в индексе извлекается из содержимого исходника заголовка; восстановительное чтение обязано использовать те же границы данных.

Фильтрация области поиска и текстовое сопоставление пути разделены. Первая использует идентичность документа или путь данных ID, вторая сопоставляет текстовое представление заголовка и текст предков без замены между `/` и `／`. Маркеры подсветки поиска и HTML в возвращаемом содержимом являются результатом отображения — их нельзя записывать обратно в содержимое исходника заголовка и нельзя перезаписывать ими уже имеющуюся подсветку совпадений при дополнении заголовка документа.

Первая версия сохраняет `blocks.hpath`, `blocktrees.hpath` и существующий механизм пакетного обновления, добавляя описанные выше метаданные уровня документа как источник структурированных запросов. Полная цепочка предков собирается подокументно и может использовать ограниченный кэш, без копирования полного массива сегментов заголовка для каждого блока содержимого. Плагины по-прежнему могут читать строковые столбцы, но должны рассматривать их только как данные отображения и текстового поиска.

`RefreshDocHPaths` перестраивает заголовки предков по поддереву ID и метаданным, больше не разрезая старый `hPath` по глубине. `updateRootContent` получает заголовок документа из единого результата чтения заголовка без использования `path.Base`. В установившемся режиме переименование родительского документа не читает полный `.sy` каждого потомка ради получения заголовка; отсутствующие или устаревшие метаданные передаются в процесс восстановления и не дополняются старым отображаемым путём.

Переименование по-прежнему делает недействительными отображаемый путь, текстовый поиск по предкам и связанные кэши. Сохранение исходного документа, обновление метаданных документа, фоновая пакетная проверка и восстановление после прерывания должны сохранять порядок — старые деревья в очереди не должны записывать обратно устаревшие заголовки или пути. Адресация по ID устраняет влияние заголовка на идентичность, но не означает, что можно удалить все задачи обновления при переименовании.

## Импорт и экспорт

### Межблокнотное перемещение и восстановление

Перемещение, копирование, нативный импорт и восстановление из истории перед первой записью проверяют полный набор операций, включая всех потомков, формат исходника, представление заголовка, целевую глубину и границы шифрования. Нечитаемый формат обязан отклоняться без перезаписи заголовка и без удаления источника; конфликты Spec защищаются версией исходника — нельзя заменять проверку отменённой записью режима.

Поддерживаемые исторические исходники по-прежнему читаются и восстанавливаются; новая запись, требующая новых возможностей заголовка, использует соответствующую Spec. Документы не переписываются массово при обновлении клиента, а существующие версии не понижаются ради прохождения проверки.

Готовые метаданные могут использоваться для проверки полного поддерева, а импорт и история используют соответствующие аутентифицированные снимки исходников; отсутствующий или устаревший индекс сначала восстанавливается, без вывода возможностей из старого `hPath`. Предварительная проверка фиксирует идентичность, состав и версии заголовков и позиций всего набора операций, а фиксация перепроверяет их в области координации изменений во избежание переименования или добавления потомков после предпроверки. Предсказуемая несовместимость должна отклоняться до любой записи; фактические ошибки ввода-вывода следуют правилам записи частичной фиксации и восстановления без обещания межфайлового атомарного перемещения. Прежние правила изоляции между обычными и зашифрованными блокнотами, а также между разными зашифрованными блокнотами остаются неизменными.

### Карта имён файлов и ссылок

Экспорт сначала назначает каждому ID документа уникальное относительное имя пути файла, а затем использует ту же карту для записи файлов и генерации междокументных ссылок. Карта должна обрабатывать слеши в заголовках, недопустимые символы имён файлов, одноимённые документы, регистронезависимые конфликты, ограничения длины и одноимённые блокноты; проверка перезаписи файлов и генерация ссылок не должны принимать решения об именах независимо друг от друга.

Распределитель сначала определяет каталог экспорта по отношениям ID, а затем независимо преобразует полное имя документа или блокнота. Совместимость с существующими бесконфликтными именами файлов сохраняется; при встрече зарезервированных имён, пустых имён, `.`, `..`, завершающих пробелов или точек используются безопасные имена, при конфликте добавляется стабильный ID, сравнение выполняется по правилам регистра и нормализации Unicode файловой системы, а при генерации путей документов и ссылок сохраняется уже назначенный уникальный суффикс. Имена блокнотов вроде `A/B` и `A_B` не должны конфликтовать или случайно создавать каталоги, а `／` сохраняет исходный символ. После распределения проверяются уникальность и целевые границы; `/` внутри заголовка или имени блокнота участвует только в преобразовании имени файла.

`.`, `..` и разделители путей в заголовках могут участвовать только в преобразовании имени файла и не могут выходить за пределы каталога экспорта. Текстовый заголовок и форматированный заголовок, поддерживаемый целевым форматом, используются для содержимого документа; экспортируемое имя файла может проходить необходимое преобразование, но не может служить единственным источником восстановления заголовка. Форматы, требующие повторного импорта без потерь, обязаны сохранять исходный заголовок и метаданные соответствующей идентичности; имя обычного файла Markdown не может в одиночку нести такую гарантию.

Нативный экспорт и резервное копирование сохраняют полный исходник заголовка и версию. Преобразование Markdown, HTML и форматов документов сначала вставляет в экспортируемую копию настоящий блок заголовка, затем преобразует ссылки, вложения и сноски; при отключённом `AddTitle` заголовок опускается, а явный пользовательский заголовок сохраняет обычное текстовое переопределение. Заголовки объединённых дочерних документов и заголовки сносок цитируемых документов также используют полный исходник, а специальные узлы экспорта не записываются обратно через валидатор постоянных заголовков. Обычный Markdown по-прежнему не обещает восстановление всех метаданных исходника без потерь; форматы round-trip с манифестом требуют отдельного определения правил версии и импорта.

Импорт строит сопоставление от исходного пути файла и идентификатора источника к новому ID документа, и разрешение ссылок использует эту карту, а не `hPath` в качестве уникального ключа. Одноимённые источники, относительные ссылки, якоря заголовков и ссылки, которые невозможно однозначно определить, следуют явной обработке конфликтов. Существующие процессы импорта вроде Obsidian должны продолжать использовать карту исходных путей, мигрируя только часть генерации заголовков и человекочитаемых путей.

## Контракты структурированных интерфейсов

Нижеприведённые пути и поля являются предлагаемыми новыми контрактами данного решения; все они используют `POST` и JSON-запросы. Новые интерфейсы чтения первой версии требуют прав администратора рабочего пространства, а интерфейсы записи дополнительно требуют состояния доступности для записи; способность перечисления предков не открывается автоматически посетителям публикации. Существующие страницы публикации продолжают соблюдать прежнюю подокументную проверку видимости, а при добавлении структурированных отображаемых данных они также обязаны проходить аналогичную фильтрацию. Зашифрованные блокноты сохраняют действующую аренду операции от разрешения и запроса до записи ответа.

### Пакетное чтение по ID

`/api/filetree/getDocPaths` принимает `notebook` и `ids`, где `ids` — от 1 до 128 ID документов; превышение лимита завершается ошибкой без тихого усечения. Дедупликация выполняется в порядке первого появления, возвращается `{documents: DocumentPath[], missingIDs: string[]}`. ID, которые не существуют, не принадлежат целевому блокноту или не могут быть прочитаны как документ, помещаются в `missingIDs` без дозапроса в других блокнотах; при отсутствии прав доступа ко всему блокноту запрос сразу завершается ошибкой.

Заголовок и цепочка предков каждого `DocumentPath` берутся из одной проверяемой версии. Порядок ответа соответствует дедуплицированному порядку ввода, а отсутствующие элементы перечисляются отдельно. Неготовность индекса, неподдерживаемый формат исходника и ошибка аутентификации являются ошибками и не маскируются под отсутствие документа. Пакетное чтение не обещает глобального снимка между разными документами; вызывающая сторона сохраняет `revision` каждого элемента и перепроверяет его при фиксации предпросмотра.

### Разрешение по сегментам заголовка

`/api/filetree/resolveDocPath` принимает `notebook`, `start` и `segments`. `start` имеет вид `{kind: "root"}` или `{kind: "document", id: string}`, а `segments` — массив отдельных строк заголовков. Интерфейс только разрешает путь, но не создаёт документы. Пустой массив возвращает отправную точку; непустой массив ищет по точному имени поуровнево, не интерпретируя символы навигации внутри строк.

Результат содержит `status`, `start`, `resolved`, `nextIndex`, `candidates`, `candidatesTruncated` и `nameConditions`. `start` возвращает идентичность и версию отправной точки, `resolved` и `candidates` используют `DocumentPath`; `nextIndex` — индекс следующего обрабатываемого сегмента с нуля. `status: "resolved"` означает полное совпадение, `"missing"` — отсутствие документа начиная с этого сегмента, `"ambiguous"` — наличие нескольких кандидатов на этом сегменте. Кандидаты сортируются по ID, возвращается максимум 128 элементов, а `candidatesTruncated` указывает на наличие дополнительных результатов; при достижении лимита всё равно должна сообщаться неоднозначность — вызывающая сторона переходит к явному ID родителя и не может по умолчанию выбирать первый элемент из усечённого списка.

`nameConditions` содержит условия для уже однозначно сопоставленных сегментов; результат `missing` дополнительно включает условие отсутствия для первого отсутствующего сегмента, а результат `ambiguous` не генерирует условие успеха для неоднозначного сегмента. Пустой массив сегментов возвращает пустой массив условий. Разрешённая цепочка и условия берутся из одного проверяемого снимка, но при фиксации всё равно требуют перепроверки. После создания первого отсутствующего предка плагин выполняет повторное разрешение от исходной отправной точки с полным исходным массивом сегментов, чтобы последующие условия ссылались на уже подтверждённый ID родителя; нельзя рассматривать один результат `missing` как бронирование всего ещё не существующего пути.

Разрешение принимает максимум 128 сегментов, каждый сегмент соблюдает ограничение длины заголовка, а фактическое создание по-прежнему применяет пользовательское ограничение глубины документов. Сегмент с пустой строкой завершается ошибкой, существующий родительский документ с пустым именем должен выбираться по ID. Когда результатом разрешения является корень блокнота, используется явная позиция корня без подделки ID документа; версия корня охватывает идентичность блокнота и связанную конфигурацию и не становится недействительной из-за изменений посторонних дочерних документов. ID документа блокнота, служащий псевдонимом корня, также проверяется по версии корня. Ошибки и кандидаты не должны раскрывать заголовки других блокнотов.

### Создание по ID родителя

Минимальный запрос `/api/filetree/createDocByParent` приведён ниже; целевой индекс обязан быть готов, а прежние требования авторизации должны выполняться.

```json
{
  "notebook": "20210808180117-6v0mkxr",
  "parentID": "20261015090000-abcdefg",
  "id": "20261015100000-hijklmn",
  "title": {"format": "plain", "text": "Том 01·Глава 1/Раздел 2"},
  "markdown": ""
}
```

| Поле | Ограничения |
| --- | --- |
| `notebook` | Обязательно, ID целевого блокнота |
| `parentID` | Обязательно; ID документа или `null` для корня блокнота, пустая строка как корень не принимается |
| `id` | Обязательно, действительный новый ID документа, заранее сгенерированный и сохранённый вызывающей стороной; если уже существует, не перезаписывается |
| `title` | Обязательно, первая версия принимает только объект обычного заголовка; пустая строка отличается от отсутствующего значения |
| `markdown` | Обязательно, допускается пустая строка |
| `expectedParentRevision` | Необязательно, используется для проверки версии пути родителя при фиксации предпросмотра; для корня используется версия корня, возвращённая интерфейсом разрешения |
| `nameConditions` | Необязательно, до 128 условий сопоставления имён; обязательно при создании отсутствующих предков, условие отсутствия соответствует непустому заголовку и родителю текущего создания |
| `expectedTarget` | Необязательно, содержит исходный `notebook`, `purpose` и `revision` конфигурации; обязательно при фиксации предпросмотра, сгенерированного из конфигурации пути сохранения |
| `tags`, `withMath`, `clippingHref` | Необязательно, переиспользуют соответствующие правила обработки существующего процесса создания из Markdown |
| `sorts`, `sortTargetID`, `sortPosition` | Необязательно, сохраняют валидацию сортировки; цель относительной сортировки должна оставаться документом под тем же родителем, конфликтующие способы сортировки вызывают ошибку |
| `docCreateTemplatePath`, `listDocTree` | Необязательно, следуют существующей семантике шаблона основного текста и обновления дерева документов |

Интерфейс отклоняет дополнительно переданные поля цели вроде `path` и `hPath`, чтобы два источника позиции не перезаписывали друг друга. При несовпадении родительского документа происходит немедленный сбой без отката к адресации по имени. При успехе возвращается `{id, document: DocumentPath}`; клиент напрямую использует возвращённый ID для открытия, цитирования или добавления содержимого.

Условия имени, версия пути родителя и версия конфигурации проверяются раздельно и не заменяют друг друга; отсутствие условий означает прямое создание по известной идентичности без гарантии сохранения прежнего предпросмотра, полученного по имени или конфигурации. Ни одно из условий не является учётными данными авторизации — ядро по-прежнему проверяет права, принадлежность и аренду. Многоуровневый план перед каждой фиксацией проверяет применимые условия, а при сбое возвращает реальный статус фиксации текущего и предыдущих шагов без перевыбора родительского документа.

Бизнес-ошибки используют `code: -1`, где `data.reason` предоставляет стабильную причину; `msg` предназначен для чтения человеком и не служит условием ветвления плагина. В таблице ниже приведены причины, относящиеся к данному решению; каждый интерфейс создания, перемещения, импорта или восстановления объявляет только применимые варианты ошибок и сохраняет соответствующие статус фиксации и информацию восстановления. Ошибки аутентификации, ролей, блокировки и общей валидации запросов продолжают использовать контракты соответствующих middleware без принудительной переделки всех существующих форматов ошибок.

| Причина | Значение и обработка вызывающей стороной |
| --- | --- |
| `invalidTitle` | Неверный формат, символы или длина заголовка; измените ввод и отправьте снова |
| `parentUnavailable` | Родительский документ не существует или не принадлежит целевому блокноту; не искать в других блокнотах |
| `planChanged` | Изменились зависимости предпросмотра, такие как позиция, версия заголовка, сопоставление имён или конфигурация; выполните повторное разрешение и подтвердите цель |
| `documentIDConflict` | ID уже существует; сверьте результат исходного запроса, не перезаписывайте и не повторяйте сразу с новым ID |
| `legacyPathUnsupported` | Имеются только кандидаты, предки которых содержат слеш или пустой заголовок; перейдите на структурированный интерфейс |
| `pathAmbiguous` | Конфликт чистых и несовместимых кандидатов либо наличие нескольких чистых кандидатов для одной цели; явно укажите идентичность |
| `indexUnavailable` | Структурированные метаданные не готовы; дождитесь восстановления, не откатывайтесь к отображаемому пути |
| `unsupportedTitleFormat` | Клиент или интерфейс не может обработать формат заголовка; обновитесь или используйте интерфейс соответствующего формата |
| `targetModeUnsupported` | Ошибка проверки формата исходного документа; сохраните источник, проверьте спецификацию или представление по деталям ошибки, исправьте или обновитесь и перепланируйте перемещение |
| `writeFailed` | Ошибка записи или последующей обработки; выполните восстановление согласно `commitState` и этапу |

### Чтение действующей цели создания

`/api/filetree/getDocCreateTarget` принимает текущий `notebook` и `purpose: "document" | "reference" | "dailyNote"`, переиспользуя существующий приоритет конфигурации каждой операции, и возвращает действующий `target`, `docCreateTemplatePath` и `revision` конфигурации. `target` является типом объединения с `version`: старый шаблон возвращает `{version: 1, notebook, path}`, а новый шаблон — полный объект версии `2`, описанный выше. Возвращаемое поле `docCreateTemplatePath` обозначает действующий шаблон основного текста для данной операции: для обычного создания выбирается по существующим правилам наследования, для ежедневной заметки берётся `DailyNoteTemplatePath`, а для создания по ссылке на блок сохраняется текущее поведение без автоматического применения шаблона основного текста и возвращается пустая строка. Интерфейс только читает конфигурацию, не выполняет шаблон и не угадывает текущий документ или текущую дату; вызывающая сторона затем предоставляет контекст для генерации плана и помещает источник, назначение и `revision` в условия фиксации.

Старые `getDocCreateSavePath` и `getRefCreateSavePath` сохраняют прежний ответ, когда действующей конфигурацией является старый шаблон; когда действует соответствующий новый объект, они возвращают `code: -1`, `data: {reason: "structuredTemplateRequired"}`. Критерием является источник конфигурации и операция, без угадывания конфигурации из отображаемого пути и без чтения отменённого режима адресации.

### Планирование цели создания в конфигурации

`/api/filetree/planDocCreate` принимает `notebook`, `purpose` и фиксированный `id` итогового документа; необязательный `contextID` задаёт текущий документ (пропуск или `null` означает отсутствие текущего документа); необязательный `title` переопределяет итоговый заголовок, `placement` принимает `configured` или `child`, а `reuse` управляет допустимостью переиспользования существующего итогового документа. Он только вычисляет и проверяет, не записывая документы. Шаблоны времени в рамках одного плана используют единый снимок времени; возвращаются итоговый заголовок, целевой блокнот, необязательный `existingID` и упорядоченный список `steps`, содержащий фиксированные ID, идентичность родителя, условия имени и версию конфигурации.

Вызывающая сторона последовательно отправляет каждый запрос `createDocByParent`, обновляя версию родителя следующего шага по версии пути из успешного ответа предыдущего. После фиксации ориентируются на возвращённый ID; ошибки обрабатываются по статусу фиксации — нельзя заново генерировать набор ID и слепо повторять. Единый план не является межфайловой транзакцией, а успешная проверка при планировании не заменяет перепроверку при каждой фиксации.

### Обнаружение возможностей

Администратор при чтении `getNotebookConf` получает доступный только для чтения объект `documentCapabilities`, содержащий `structuredPaths`, `literalSlash`, `titleFormats`, `indexState` и `revision`. `structuredPaths` объявляет поддержку интерфейсов ID и сегментов заголовков; `literalSlash` равен `true` только при готовности индекса. `indexState` сообщает `missing`, `building`, `ready` или `error`. Все блокноты используют одинаковые структурированные правила. Текущее значение `titleFormats` — `["plain", "inline-ast"]`; это возможность формата заголовка, которая не меняет правило запроса `createDocByParent`, принимающего только обычные заголовки.

Чтение возможностей не записывает маркеры миграции или нижней границы; `revision` — это сводка версии объявления возможностей, а не версия пути какого-либо документа. Ввод на десктопе, в браузере и на мобильных устройствах использует одинаковые правила заголовков и не зависит от переключателя режима адресации во время выполнения. Закрытие, блокировка, доступ к публикации и аренда запроса продолжают соблюдать прежние правила — информация о возможностях не даёт дополнительных прав.

### Сопровождение контрактов и объявлений

Реализация следует [Контракты типов API ядра](API-CONTRACTS.zh-CN.md): объявления определяются в `kernel/apicontract/`, привязываются через `contractHandler`, генерируются типы и синхронизируются объявления сопровождения Petal и журнал изменений. Подробные правила новых интерфейсов размещаются в комментариях соответствующих контрактов. Когда затрагивается поведение существующих интерфейсов, проверяются и синхронизируются существующие записи в китайской, английской и японской документации API; новые интерфейсы не добавляются автоматически в справочник API, а описание интерфейсов данной функции не добавляется в руководство по сопровождению контрактов.

## Совместимость интерфейсов и плагинов

Старый `getIDsByHPath` сначала проверяет состояние готовности и pending в том же снимке метаданных, затем запрашивает кандидатов текущего отображаемого пути и классифицирует их по реальной цепочке предков. Когда заголовки каждого уровня непусты, не имеют флага пустого заголовка и не содержат ASCII `/`, кандидат является чистым; любой слеш в цепочке, фактический пустой текст или заполнитель пустого заголовка делают кандидата несовместимым. Сущности атрибутов декодируются только один раз при чтении исходника — нельзя повторно декодировать метаданные. Отсутствие строки предка, цикл, несоответствие идентичности или версии пути, а также ошибка SQL возвращают `indexUnavailable`; даже пустой результат должен сначала доказать готовность индекса.

| Чистые кандидаты | Несовместимые кандидаты | Результат запроса |
| --- | --- | --- |
| Есть | Нет | Возвращаются все чистые ID |
| Есть | Есть | `pathAmbiguous` |
| Нет | Есть | `legacyPathUnsupported` |
| Нет | Нет | Пустой массив |

Полный исходник заголовка читается через `getDocTitle` и редактируется через транзакцию `setDocTitle` с текущей версией; при получении `code: -409` необходимо сохранить черновик и нельзя отправлять сводку заголовка в качестве форматированного исходника. Имя блокнота остаётся обычным текстом конфигурации с различением `/` и `／`; имена файлов экспорта назначаются независимо.

Ошибки используют `code: -1` и стабильный `data.reason`, поля кандидатов — `cleanIDs` и `unsupportedIDs`, пустые списки могут опускаться. ID кандидатов по-прежнему защищены фильтрацией доступа к публикации и арендой шифрованного ответа. Прежний успешный результат сохраняет тип массива или ID документа — нельзя требовать от вызывающей стороны сопоставления текста ошибки.

`createDocWithMd` перед первой записью исходника проверяет все префиксы родительского пути, не пропуская последующие конфликты из-за отсутствующего раннего префикса; кандидаты со слешем или пустым заголовком всегда возвращают `pathAmbiguous`. Несколько чистых родителей также возвращают эту ошибку; действительный и совпадающий `parentID` может устранить неоднозначность по реальной цепочке предков, но не может обойти несовместимых кандидатов. Позиционирование одной цели в CLI и MCP использует ту же проверку; при отсутствии явной идентичности нельзя произвольно выбирать чистого кандидата. Позиция корня сохраняет прежнее значение.

Для неизвестной позиции предпочтительно использовать отдельные сегменты заголовка в `resolveDocPath`, для создания — ID родителя и отдельный заголовок в `createDocByParent`, а для многоуровневого создания — `planDocCreate`. Во время перестроения индекса старые интерфейсы также возвращают `indexUnavailable`; вызывающая сторона ожидает восстановления и не откатывается к недоказанной отображаемой строке или выводу по префиксу SQL.

## Версии, шифрование и восстановление

### Спецификация документов и риск смешанного использования со старыми версиями

Режим 1 отменён, все блокноты интерпретируются по структурированным правилам, существующие документы, ID, шифротексты и ключи не требуют миграции или массовой перезаписи. Сохранение конфигурации больше не генерирует маркер версии адресации, существующий маркер игнорируется и опускается при следующем обычном сохранении конфигурации; отсутствие конфигурации и каталога блокнота не должно вызывать системных ошибок при чтении возможностей или пересоздавать данные.

Новые записываемые заголовки с ASCII `/` обязаны объявлять как минимум Spec 6. Сохраняются независимое определение спецификации, проверка декодирования дублирующихся атрибутов и сущностей, а также отклонение неизвестных представлений заголовков и будущих Spec. Поддерживаемые исторические исходники с низким Spec и слешем по-прежнему читаются и восстанавливаются, а новая запись исходника обязана удовлетворять требованиям спецификации; обычные документы сохраняют спецификацию, требуемую основным текстом, не переходя массово на Spec 6 при обновлении и не понижая прежнюю версию.

Спецификация исходника действует на уровне документа; миграции режима заголовков на уровне блокнота или защиты формата, покрывающей весь блокнот, не существует. Старые клиенты, не поддерживающие соответствующую спецификацию, откажутся читать документы с этой спецификацией, но документы в том же блокноте, сохраняющие старый формат, всё ещё могут читаться и записываться старой версией. Кэш редактирования в уже открытых страницах старой версии также может записаться обратно, перезаписав новый заголовок или содержимое и распространив это через синхронизацию. Отказ в чтении части документов не доказывает, что весь блокнот защищён, и не является обещанием безопасного смешанного использования нового и старого клиентов.

Имеющаяся изолированная проверка исходного кода `v3.8.9-alpha.4` доказывает только отказ прямого чтения Spec 6, сохранение чтения старых Spec и возможность перезаписи источника старым снимком редактирования, не покрывая все операции старых клиентов или полную смешанную синхронизацию. При необходимости использования старого клиента следует применять проверенную отдельную экспортную копию или резервную копию до обновления, восстановленную в отдельном рабочем пространстве, чтобы результаты записи старого клиента не синхронизировались с исходными данными.

Обычный заголовок с полуширинным `/` требует как минимум `DocumentTitleSpec = "6"`; корневой узел с форматированным исходником требует как минимум `RichDocumentTitleSpec = "7"`, даже если в сводке нет слеша. Обычная запись дерева повышает спецификацию по мере необходимости, не понижая более высокую спецификацию, требуемую другими функциями основного текста. Обновление клиента, чтение заголовка без изменений и обычное форматирование не повышают неизменённый обычный заголовок до форматированного. Конверт заголовка имеет отдельную версию; неизвестное представление не может быть толерантно разобрано и перезаписано.

### Отменённые записи и очистка при запуске

Чтение возможностей, импорт, синхронизация, снимки и резервное копирование настроек больше не читают и не генерируют нижнюю границу возможностей, записи миграции режима и поле `documentAddressing` в настройках; это поле в старых настройках игнорируется. Синхронизация передаёт обычные и зашифрованные документы как непрозрачные сырые байты, включая неподдерживаемые спецификации исходников и представления заголовков, сохраняя канонические пути, миграцию паролей и проверки аутентификации репозитория. Восстановление снимков продолжает сохранять предварительную проверку спецификации исходника. Неподдерживаемые исходники отклоняются при чтении и редактировании; инкрементальная синхронизация очищает их устаревший локальный индекс без перезаписи байтов исходника.

При запуске выполняется идемпотентная очистка локальных `conf/document-addressing.json` и `conf/document-addressing-recovery/`; отсутствие каталога считается успехом, ошибка удаления лишь логирует предупреждение и не должна блокировать монтирование; в режиме «только чтение» очистка пропускается. Файл `.siyuan/document-addressing.json` внутри блокнота больше не читается и не создаётся заново, а существующие файлы остаются как есть во избежание удаления при синхронизации. Ключи восстановления шифрования и задачи восстановления исходников не входят в область этой очистки.

Запись документа одновременно проверяет записываемое содержимое и текущий исходный файл на диске. Зашифрованный исходник сначала аутентифицируется, затем интерпретируется; проверка текущего исходника и запись на диск выполняются под одной файловой блокировкой, чтобы старый кэш не перезаписал позже появившийся несовместимый исходник. Автоисправление также требует совпадения текущего исходника с первоначально проверенными байтами; при сбое проверки нельзя продолжать откатывающую запись или усекать файл. Обычные документы сохраняют постраничную запись, а зашифрованные — атомарную замену шифротекста.

Пути ID блокнота и документа в интерфейсе сырых файлов также защищены проверкой формата исходника и не могут быть обойдены через загрузку, копирование или перемещение файлов. Предварительная проверка всего пакета завершается до создания целевого каталога и первого копирования; фактическое копирование документа использует уже проверенные прочитанные байты и перепроверяет целевой исходник под файловой блокировкой; конкурентные изменения после проверки или ошибки ввода-вывода всё равно могут оставить завершённые копии без обещания отката всего пакета. Обычные вложения и файлы `.sy` в каталогах плагинов сохраняют семантику сырых файлов, а зашифрованные блокноты по-прежнему запрещено читать и записывать через интерфейс сырых файлов.

При новой записи, копировании и переименовании сырых документов обычный корневой заголовок с `/` требует `Spec >= 6`, а форматированный исходник `DocumentTitle` требует `Spec >= 7`. При слишком низкой метке версии запрос отклоняется до записи в цель; интерфейс сырых файлов не выполняет автоматическое обновление версии или повторную сериализацию запроса. Существующие поддерживаемые старые данные продолжают поддерживать аутентифицированное чтение, историю, резервное копирование, синхронизацию и восстановление; неизвестный форматированный формат или некорректный исходник сохраняют исходные данные и отклоняются без деградации в текст IAL.

### Восстановление индекса и задач

`document_metadata` использует независимую версию производного индекса и статусы блокнота `missing`, `building`, `ready`, `error`. После создания таблицы она строится из исходных документов и позиций ID, без угадывания границ сегментов из старого `hPath`. Во время построения фиксируются инкрементальные изменения, которые догоняются перед переключением; только после завершения полного сканирования и инкрементальной проверки соответствующее поколение помечается как `ready`.

Когда метаданные, необходимые для структурированных и старых интерфейсов путей, не готовы, возвращается `indexUnavailable`. Восстановление обязано аутентифицировать реальный исходник и не может досоздавать несуществующие родительские исходные файлы или перезаписывать повреждённый исходник производным индексом.

Порядок обновления: запись исходного документа на диск, обновление метаданных документа и соответствующей строки документа в одной транзакции БД дерева блоков, отправка последующих пакетов `hpath`. Атомарная транзакция между исходным файлом и базой данных, а также между БД дерева блоков и базой содержимого не заявляется. Прерывание на любом шаге сохраняет маркер восстановления; после перезапуска или разблокировки сначала проверяются версия исходника и текущая позиция ID, а затем продолжается производное обновление. Версия снимка, обнаружение перемещения или удаления делают недействительным старое дерево в очереди и не позволяют восстановить старый заголовок.

Существующий `temp/queue/hpath-refresh.queue` хранит только ID блокнота, ID документа и путь данных ID. Миграция не должна записывать сегменты заголовков, форматированные заголовки или основной текст в эту глобальную открытую очередь. Конкурентное переименование, перемещение, удаление, синхронизация и обычное перестроение индекса по-прежнему должны проверять, не устарела ли задача, и не очищать по ошибке незавершённые задачи восстановления зашифрованных блокнотов.

Чтобы предотвратить сбой в окне между записью исходного файла и регистрацией задачи восстановления, перед изменением предварительно сохраняется на диск маркер ожидания сверки, содержащий только идентичность, либо используется существующая постоянная запись транзакции, покрывающая это окно; соответствующая реализация обязана доказать восстанавливаемость с помощью инъекции сбоев. Маркер очищается после завершения задачи, а повторное восстановление должно давать тот же производный результат. Пока зашифрованный блокнот не разблокирован, задача сохраняется — нельзя пропускать аутентификацию ради очистки очереди.

### Совместимость с шифрованием

Существующие зашифрованные данные являются базовой линией совместимости и следуют требованиям аутентифицированного чтения, изоляции и восстановления из [Зашифрованный блокнот](ENCRYPTED-NOTEBOOK.zh-CN.md). Содержимое исходника заголовка, текстовый заголовок и цепочка предков относятся к защищённому содержимому документа; чтение, кэширование и ответы обязаны находиться в пределах области авторизации и аренды операции соответствующего блокнота и очищаться после блокировки согласно существующему жизненному циклу.

`docCreateTarget`, `refCreateTarget` и `dailyNoteTarget` в зашифрованных блокнотах хранятся как защищённая конфигурация и не могут попадать напрямую в `BoxConf` в виде открытых полей. Текущая зашифрованная полезная нагрузка `BoxCrypt.Metadata` содержит только иконку и сортировку; новое решение определяет для этой нагрузки независимую `version: 2`, сохраняя `icon`, `sort`, `sortMode` и храня три необязательных целевых объекта в `documentTargets`. Существующая нагрузка без `version` аутентифицированно читается как версия `1`, а обычное сохранение конфигурации продолжает быть совместимым со старой нагрузкой; версия `2` генерируется только при записи новых объектов, и последующее удаление объектов не откатывает версию нагрузки обратно. Эта версия интерпретируется раздельно от `BoxCrypt.Spec`, `version` целевого объекта и версии `.sy`.

После разблокировки читатель конфигурации в пределах аренды проецирует целевые объекты в авторизованный интерфейс управления; перед записью на диск эти объекты должны быть очищены из открытой копии конфигурации, сохраняя только аутентифицированный шифротекст. После блокировки соответствующий открытый кэш очищается, ответы статуса и конфигурации не возвращают эти объекты; не-администраторы также не могут их читать. Пропущенные или отфильтрованные поля не являются запросом на удаление; обычное сохранение конфигурации при блокировке оставляет существующий шифротекст без изменений, а добавление или изменение целевых объектов требует предварительной разблокировки. Чтение новой нагрузки, переупаковка при смене пароля, импорт/экспорт, история конфигурации и восстановление резервных копий покрывают образцы старой версии; неизвестная версия нагрузки и ошибка аутентификации отклоняют интерпретацию или перезапись, не допуская потери новой конфигурации из-за незнакомых структуре полей.

Перед перестроением производного индекса необходимо аутентифицировать исходный шифротекст и проверить формат документа. Неизвестный формат, повреждение и ошибка аутентификации обязаны сохранять исходные данные и возвращать ошибку без отката к открытому тексту, межблокнотному запросу или неаутентифицированному старому индексу. Перестроение обычного индекса не означает, что зашифрованные исходные данные прошли аутентификацию.

Версионированное расширение полезной нагрузки конфигурации продолжает использовать существующий контейнер аутентифицированного шифрования, назначение подключа `siyuan/box-metadata` и привязанный к блокноту AAD без изменения конверта шифрования, семантики AAD или вывода ключей. Если в будущем эти форматы будут затронуты, потребуется отдельное проектирование с явной версией, аутентифицированной миграцией и восстановлением после прерывания, с сохранением соответствующих ключей и материалов резервного копирования. Запрещено перегенерировать `MasterSalt`, отбрасывать ключи или требовать от пользователя пересоздания существующих зашифрованных блокнотов для обхода проблем совместимости. Поддерживаемые форматы в документах, истории, резервных копиях и снимках синхронизации должны оставаться восстанавливаемыми.

| A: Защита совместимости | Распознавание конфликтов цепочки предков кандидатов, защита версии исходника и исторические образцы | Синхронизация передаёт непрозрачные байты исходника, восстановление снимков проверяет спецификацию исходника; соответствующие входы чтения, записи и исправления отклоняют неподдерживаемые форматы или спецификации исходников; отдельный выпуск защитной версии не требуется |
| B: Внутренняя декомпозиция | Единое чтение заголовков, метаданные документов, вычисление иерархии по ID, обновление путей и восстановление | Поведение обычных заголовков неизменно; структура больше не выводится из отображаемой строки, зашифрованный индекс может аутентифицированно перестраиваться |
| C: Интерфейсы и вызывающие стороны | Новые интерфейсы чтения, разрешения, условного создания, шаблоны версии `2` и зашифрованная нагрузка, миграция встроенных операций и платформ | Проверены условия конкурентности имён и конфигурации, старые и новые контракты, восстанавливаемость частичных сбоев и отмены, сохранено поведение ежедневных заметок и других операций |
| D: Открытие нового символа | Единые структурированные правила и восстановление индекса, правила отказа старых интерфейсов, инструкции миграции плагинов, межблокнотные операции и проверка импорта/экспорта | Обычные сборки по умолчанию поддерживают `/`; внешняя приёмка релиза завершается только после прохождения полной предпроверки поддерева, восстановления индекса и всех условий релиза |
| E: Строчные заголовки | Исходник Spec `7`, редактирование полного исходника, обратные ссылки заголовков, преобразование и экспорт | Сохранение интерфейсов идентичности и ограничений обычного создания, проверка сохранения нативных строчных элементов, условной записи, отмены, шифрования и защиты старой записи |

Этапы A–E являются группировкой реализации и приёмки и не требуют выпуска отдельных переходных версий. Текущая разработка уже включает строчные заголовки при неизменном базовом протоколе идентичности и создания. Соответствующие условия релиза и требования совместимости, проверяемые по спецификации исходника документа, по-прежнему должны выполняться; завершение реализации исходника и таргетированных регрессий не означает полного завершения приёмки релизных сборок, платформ, производительности и сторонних плагинов.

Условия открытия включают: все встроенные потребители мигрированы; заменяющие интерфейсы и документация по адаптации плагинов опубликованы; проверки Spec и отклонения до записи в текущей реализации прошли верификацию; миграция обычных и зашифрованных индексов прерываема и восстанавливаема; импорт и экспорт не перезаписывают файлы из-за конфликтов отображаемых путей; поведение десктопа, браузера и мобильного приложения согласовано; руководства пользователя на четырёх языках согласованы с реализованным поведением по умолчанию, влиянием на плагины и доступными функциями. Регрессии на старых данных и старых протоколах не являются обязательством по поддержке смешанного использования со старыми клиентами.

Реализация использует `.sy` Spec `6` для заголовков с литеральным слешем и Spec `7` для форматированных исходников; при выпуске версии с этой функцией прилагаются имеющиеся замеры производительности и результаты тестов совместимости с честным указанием ограничений проверки. Предварительный выпуск защитной версии или регистрация её номера больше не являются предварительным условием приёмки данной задачи. Это доказательства релиза, а не решения, позволяющие заново отложить идентичность, шаблоны, границы плагинов или семантику сбоев. Нельзя заменять полную функциональную приёмку завершением документации, прохождением изолированных тестов или однократным перестроением индекса.

### Ключевые регрессионные сценарии

Сохраняются `TestCreateDocsByHPathUsesParentIDForDuplicateHPath` и `TestCreateDocsByHPathKeepsHPathFallbackForDifferentParent`, доказывая, что старый вход совместимости не был незаметно заменён новыми правилами. Отдельно для нового входа покрываются сохранение исходного ID после изменения заголовка родителя, отказ после межблокнотного перемещения родителя, отсутствие ошибочного выбора одноимённого родительского документа и возврат `planChanged` при фиксации с версией.

Одновременно создаются корневой документ `A/B`, корневой документ `A` с дочерним `B`, корневой документ `A／B` и корневой документ `A%2FB`. Первые два допускают одинаковый отображаемый путь, но их ID, `segments`, `depth`, область поддерева и ссылки экспорта должны быть корректны для каждого; последние два не должны преобразовываться в первые два. Добавляются образцы с повторяющимися слешами, сегментами-точками, пустыми заголовками, различиями регистра и одинаковым обычным текстом при разных форматах заголовка.

Два запроса одновременно разрешают отсутствующего предка и отправляют одно и то же условие отсутствия — проверяется, что успешен только один, а второй возвращает `planChanged`; обычные одноимённые итоговые документы по-прежнему могут создаваться раздельно. При появлении второго одноимённого документа для уже сопоставленного предка условие уникальной идентичности завершается ошибкой. Изменение целевого блокнота, наследуемой конфигурации или пути шаблона основного текста после предпросмотра конфигурации должно отклоняться даже при неизменной версии пути родителя; гонка между переименованием/обновлением конфигурации и финальной проверкой/фиксацией также должна быть покрыта.

Конструируется поддерево с обычным корневым заголовком, но с потомками, содержащими `/` или неизвестное представление заголовка; проверяется, что перемещение, копирование, импорт и восстановление перед записью исходника проверяют всех потомков, спецификацию исходника и аутентификацию; изменения после предпроверки по-прежнему должны обнаруживаться без понижения спецификации или обхода границ шифрования.

Проверяются восстановление старой конфигурации и исторических снимков, отсутствующая конфигурация, игнорирование отменённых записей и очистка при запуске; при неготовности индекса позиционирование по пути и создание должны отклоняться. С использованием поддерживаемых обычных и зашифрованных исторических образцов проверяются защита неизвестного формата исходника, ошибка аутентификации, отсутствие открытого текста целевой конфигурации на диске и очистка кэша после блокировки, с сохранением покрытия резервного копирования и восстановления при смене пароля.

`TestDocumentAddressingCheckoutSourcePreflight` использует реальные снимки репозитория для покрытия будущих спецификаций, неизвестных представлений заголовков, несовместимых текущих исходников и выведенных из эксплуатации записей. Восстановление снимка отклоняет неподдерживаемые исходники до применения пакета, сохраняя байты и временные метки; синхронизация, напротив, не интерпретирует содержимое и передаёт эти исходники как есть. `TestDocumentAddressingCheckoutSourceRemoval` раздельно покрывает частичное удаление и удаление всего блокнота при синхронизации и восстановлении снимка. `TestSyncDocumentOpaqueRoundTrip` покрывает локальную загрузку из облака, совместимые документы в том же пакете, удаление, сохранение байтов и отсутствие новых расхождений при последовательной синхронизации. `TestSyncDocumentUnsupportedSourceClearsOldIndexes` проверяет очистку устаревших индексов, а также отказ чтения и записи старого кэша редактирования. `TestDocumentAddressingCheckoutPreservesOpaqueEncryptedSource` использует образцы исторического шифротекста для проверки передачи сырых байтов без разблокировки и проверяет неизменность конфигурации и материалов восстановления. Регрессии путей покрывают обратные слеши, дублирующиеся цели, а также завершающие точки, завершающие пробелы и псевдонимы потоков данных по умолчанию в Windows, не позволяя фактической цели записи на диск обойти проверку источника. Также сохраняются регрессии для BOM, легальных заголовков со слешем, обычного восстановления повреждённых исходников и `.sy` вложения, чтобы защита источника не превратилась в несовместимое ограничение файловых операций.

Прежние тесты преобразования с сохранением основного текста синхронизированы как `TestHeadingDocTitle` и `TestHeadingDocTitleTextMarks` — изображения, ссылки, экранирование и текстовые маркеры теперь сохраняются в исходнике заголовка. `TestHeadingDocumentRichTitleRoundTrip` и тесты сбоя преобразования проверяют двустороннее преобразование полного исходника, сохранение ID основного текста и условную компенсацию; интеграционные тесты обратных ссылок заголовков, форматированной замены, экспорта и шифрования проверяют принадлежность источника, преобразования с сохранением полного исходника и конкурентные изменения. Дерево документов шаблона по-прежнему покрывает групповую отмену/повтор, частичную фиксацию, конфликты имён или ID при повторе и последующие правки пользователя.

Реальные HTTP-регрессии проверяют строгие типы запросов, различие между обязательным полем и `null`, порядок возврата, усечение кандидатов, данные ошибок, защиту администратора и доступности для записи, аренду шифрованного ответа и отказ доступа к публикации. Регрессии совместимости старых интерфейсов и регрессии новых интерфейсов проверяются раздельно, чтобы не перезаписывать старое поведение новыми ожиданиями. Фронтенд проверяет round-trip старой конфигурации шаблонов, поуровневое вычисление новых шаблонов, единый снимок времени, подсказки частичного успеха и мобильные точки входа.

Инъекция сбоев покрывает как минимум этапы до и после записи исходного документа на диск, до и после транзакции метаданных, прерывание пакета индекса содержимого, потерю успешного ответа и блокировку во время вывода ответа. На реальных образцах поддерживаемых исторических форматов проверяются чтение, экспорт, история, резервное копирование и восстановление, а также проверяется, что читатель с ограниченными возможностями отклоняет неподдерживаемые режимы и форматы; тестирование только файлов, сгенерированных текущей версией, не доказывает обратную совместимость. Регрессия ограниченного читателя используется для проверки границ проверок и не требует выпуска этого читателя или обещания аналогичной защиты у произвольных исторических клиентов.

### Производительность и ресурсы

В одной и той же среде сравниваются базовая линия и реализация на 1 000 и 10 000 документов, широких поддеревьях и иерархии глубиной 7, с дополнительным покрытием случая включения пользователем большей глубины; тестируются раздельно обычные и разблокированные зашифрованные блокноты. Фиксируются задержка переднего плана, фоновое время выполнения, память, размер БД и число чтений `.sy` для пакетного чтения путей, переименования родительского документа, перемещения, первого перестроения и инкрементального восстановления, с отчётом по медиане и высоким перцентилям.

Создание и чтение на переднем плане не должны сканировать весь блокнот из-за добавления метаданных; переименование родителя при готовом индексе не должно читать основной текст каждого потомка. Построение индекса может сканировать исходные данные по числу документов, но должно иметь прогресс и точки восстановления. Кэш имеет чёткий верхний предел, а при блокировке соответствующие заголовки очищаются; полная цепочка предков каждого блока содержимого не хранится постоянно в памяти. Затраты на фоновое обновление `hpath` для блоков содержимого учитываются отдельно — общее время с учётом ожидания планировщика не выдаётся за время БД, и не утверждается, что декомпозиция устраняет все обновления поддерева.

Отчёт о производительности обязан объяснять изменения относительно базовой линии и их причины; конкретное время зависит от устройства, размера текста и накладных расходов шифрования — данный черновик не содержит неизмеренных выигрышей или фиксированных обещаний в миллисекундах. При явной регрессии сначала анализируются число запросов, пакеты транзакций и повторные чтения исходников, и только затем принимается решение об оптимизации кэша, без изменения семантики заголовков ради производительности.

### Проверки на этапе реализации

Поведенческие тесты входят в существующую область обнаружения тестов фронтенда и ядра; новые Go-тесты контрактов сохраняют `Contract` в имени. После внесения изменений в API выполните в `app/` команды `pnpm run api:generate --petal ../../petal`, `pnpm run api:check --petal ../../petal`, `pnpm run lint` и соответствующие тесты фронтенда; в `kernel/` выполните `go test ./apicontract/...` и регрессионные тесты, покрывающие затронутые API, модели, файловую систему, дерево блоков и SQL. Выполните тесты соответствующих пакетов с тегами `fts5 sqlcipher`, сохраняя покрытие Spec 6, исторических обычных и зашифрованных образцов, неизвестных форматов исходников, синхронизации и восстановления; заглушки для сборки режима 1 или удалённых механизмов не сохраняются. В документации дополнительно проверяются двуязычная согласованность, примеры, ссылки и различия.
