# Зашифрованный блокнот

[English](ENCRYPTED-NOTEBOOK.md)

## Область функциональности

### Цели проектирования

Зашифрованный блокнот шифрует при хранении документы `.sy`, файлы ресурсов и их исходные имена, определения баз данных и индексные базы данных SQLite. После ввода мастер-пароля пользователь независимо разблокирует блокноты и получает доступ к их содержимому. Обычные блокноты не требуют миграции.

Зашифрованный блокнот поддерживается как выпущенная функция.

### Ключевые ограничения

| Аспект | Проектное решение |
|---|---|
| Область шифрования | `.sy` + assets (включая имена файлов) + файлы баз данных + базы данных SQLite (content + blocktree) шифруются полностью |
| Идентичность блокнота | Динамический boxID + флаг `BoxConf.Encrypted: true` |
| Количество | Поддерживается несколько зашифрованных блокнотов |
| Пароль | Общий мастер-пароль (обёртка KEK, независимый DEK для каждого блокнота) |
| Гранулярность разблокировки | Строго раздельная разблокировка каждого блокнота (KEK используется однократно и удаляется, каждый раз выполняется Argon2id ~1 сек) |
| Схема базы данных SQLite | Физически независимая база данных SQLCipher SQLite для каждого зашифрованного блокнота, изолированная от глобальной siyuan.db |
| Принцип изоляции | Каждый зашифрованный блокнот — независимый остров: изолирован от обычных блокнотов и друг от друга. Данные, ссылки на блоки, зеркала баз данных и перемещения не пересекают границы зашифрованного блокнота. Разблокировка одного зашифрованного блокнота не влияет на состояние блокировки других. |
| Глобальные функции | Зашифрованный блокнот полностью не участвует (глобальный поиск / граф связей / ссылки на блоки его не видят) |
| Ссылки на блоки | Обычные ссылки внутри блокнота; запрещены ссылки через границу шифрования (в обе стороны: обычный ↔ зашифрованный, зашифрованный A ↔ зашифрованный B) |
| AI / LLM | Изоляция на уровне функций не делается — после разблокировки можно напрямую читать содержимое и использовать поиск внутри блокнота; после блокировки нет доступного дескриптора DEK, и специализированные точки входа отклоняют доступ. Глобальный поиск, семантический поиск и векторные эмбеддинги не участвуют (подробнее см. «Доступность для AI / LLM») |
| Публикация | Не поддерживается — читатели и анонимные посетители сервиса публикации не могут перечислять или читать зашифрованные блокноты независимо от того, разблокирован ли блокнот, настроен ли пароль публикации или видимость |
| Перемещение через границу | Запрещено — нарушает согласованность данных и приводит к утечке |
| Базы данных | Хранение на уровне блокнота — файлы баз данных зашифрованного блокнота следуют за каталогом блокнота, шифруются DEK; запрещено зеркалирование через границу |
| Карточки / интервальное повторение | Не поддерживается (ограничение функции) |
| Закладки | Не поддерживается (ограничение функции) |
| Теги | Не поддерживается (ограничение функции) |
| Импорт | Поддерживается — импортированные .sy.zip и Markdown шифруются DEK перед записью на диск, как и созданные вручную документы |
| Включение / отключение | Для включения требуется задать мастер-пароль; для отключения нужно обработать все активные блокноты и зависимости восстановления либо сохранить исходный шифротекст и ключевые материалы в полностью проверенном архиве |
| Поведение при перезапуске | При запуске все зашифрованные блокноты принудительно закрываются (управляемые дескрипторы DEK существуют только в памяти процесса и после перезапуска требуют повторного вывода), пользователю нужно разблокировать их заново |
| Существующие обычные блокноты | Полностью не затрагиваются, нулевая миграция |
| Существующие зашифрованные данные | После обновления остаются читаемыми и восстанавливаемыми; при изменении формата сохраняется аутентифицированное чтение старой версии либо предоставляется восстанавливаемая миграция, не требующая удаления или пересоздания пользовательских данных |

### Сравнение с обычным блокнотом

| Аспект | Обычный блокнот | Зашифрованный блокнот |
|---|---|---|
| Создание | Создаётся в любое время без ограничений | Требуется сначала включить шифрование (задать мастер-пароль), при создании проверяется мастер-пароль |
| Открытие (Mount) | Открывается напрямую | Требуется сначала ввести мастер-пароль для разблокировки (каждый раз ~1 сек Argon2id), приложение получает управляемый дескриптор DEK |
| Закрытие (Unmount) | При закрытии становится невидимым | Закрытие = блокировка (остановка нового доступа + ожидание или отмена текущих задач + удаление DEK из кэша управляемых ключей + удаление зашифрованной базы SQLite + максимально возможная очистка управляемых ядром кэшей открытого текста и временных файлов) |
| После перезапуска | Сохраняет последнее открытое состояние | Принудительно закрывается, требуется повторный ввод мастер-пароля для разблокировки |
| Файлы .sy | Открытый JSON на диске | Шифротекст AES-256-GCM на диске, прозрачная расшифровка при чтении |
| Файлы assets | Открытый бинарный файл, исходное имя | Шифротекст AES-256-GCM, обезличенное имя файла, исходное имя хранится зашифрованным |
| Файлы баз данных | Глобальный `storage/av/<avID>.json` (открытый текст) | Уровень блокнота `<boxID>/storage/av/<avID>.json` (шифрование DEK) |
| База SQLite content | Запись в глобальную siyuan.db (открытый текст) | Запись в отдельную siyuan-encrypted-`<boxID>`.db (шифрование SQLCipher) |
| База SQLite blocktree | Запись в глобальную blocktree.db (открытый текст) | Запись в отдельную siyuan-encrypted-`<boxID>`-blocktree.db (шифрование SQLCipher) |
| Глобальный поиск | Участвует (попадания FTS) | Не участвует (данных нет в глобальной базе SQLite) |
| Граф связей | Участвует | Не участвует |
| Ссылки на блоки | Могут ссылаться любые блокноты | Обычные ссылки внутри блокнота; запрещены ссылки через границу шифрования (в обе стороны) |
| Перемещение документа (между блокнотами) | Поддерживается | Запрещено через границу шифрования |
| Документ в заголовок (Doc2Heading) | Поддерживается | Запрещено через границу шифрования |
| Зеркало базы данных (между блокнотами) | Поддерживается | Запрещено через границу шифрования |
| Переименование файла ресурса | Поддерживается | Не поддерживается (переименование обезличенного имени нарушит сопоставление) |
| Распознавание текста на ресурсах (OCR) | Поддерживается | Не поддерживается, независимо от состояния разблокировки |
| Импорт | Поддерживается | Поддерживается (.sy.zip и Markdown, автоматическое шифрование DEK перед записью на диск) |
| Поиск внутри блокнота | Использует глобальную базу SQLite | Использует зашифрованную базу SQLite |
| Панель обратных ссылок | Использует глобальную базу SQLite | Использует зашифрованную базу SQLite (включая подзапрос mention) |
| Открытие документа / структура / хлебные крошки / информация о блоке / всплывающий предпросмотр | Использует глобальную базу SQLite | Использует зашифрованную базу SQLite |
| Базы данных | Глобальное хранилище + глобальная база SQLite | Хранилище уровня блокнота (шифрование DEK) + зашифрованная база SQLite |
| История файлов | Поддерживается | Поддерживается (шифротекст .sy сохраняется в каталоге истории как есть; запись истории сохраняет boxID, тип объекта и стабильное базовое имя файла на момент снимка, а просмотр/откат расшифровываются с использованием этих трёх параметров как контекста AAD) |
| История удалённых блокнотов | Поддерживается | Поддерживается (перед удалением весь каталог копируется в зашифрованном виде, при восстановлении копируется обратно как есть; для восстановления также требуются совпадающая глобальная резервная копия ключей и мастер-пароль) |
| Векторные эмбеддинги / семантический поиск | Участвует | Не участвует (зашифрованные данные не попадают в глобальную таблицу block_embeddings, конвейер эмбеддингов читает только глобальную базу; независимо от состояния разблокировки) |
| Агент / AI-чат / MCP | Можно читать содержимое, искать | Доступно после разблокировки (можно читать содержимое блоков, перечислять документы, искать внутри блокнота); недоступно после блокировки (подробнее см. «Доступность для AI / LLM»). Глобальный и семантический поиск не участвуют |
| Публикация | Поддерживает настройку видимости, пароля и запрета доступа через `publishAccess.json` | Не поддерживается; читатели и анонимные посетители сервиса публикации никогда не могут перечислять или читать, `publishAccess.json` не может переопределить это правило |
| CLI ядра | Может работать с данными рабочего пространства | Независимо от блокировки или разблокировки не поддерживает зашифрованные блокноты и их файлы |
| Карточки / интервальное повторение | Участвует | Не поддерживается (ограничение функции) |
| Закладки | Участвует (глобальная агрегация) | Не поддерживается (ограничение функции) |
| Теги | Участвует (глобальная агрегация) | Не поддерживается (ограничение функции) |
| Иконка в списке | Пользовательский emoji | В закрытом состоянии отображается иконка замка, после открытия восстанавливается emoji |
| Экспорт (.sy.zip) | Поддерживается | Поддерживается (экспорт открытого текста в разблокированном состоянии, отказ в заблокированном состоянии; подробнее см. предпосылки безопасности в разделе «Границы безопасности») |
| Синхронизация данных | dejavu синхронизирует открытый текст | Без изменений (шифротекст входит и выходит, сохраняя форму шифротекста) |
| Удаление блокнота | Удаление каталога | Удаление каталога + удаление зашифрованных файлов баз данных SQLite + удаление хранилища баз данных уровня блокнота |
| Перестроение индекса | Полное | Пропускается при запуске (закрыт); при открытии полное перестроение в зашифрованную базу SQLite |
| /api/file/\* | Можно читать, писать, копировать, переименовывать, удалять или перечислять файлы рабочего пространства | Доступ к любым файлам в постоянном каталоге зашифрованного блокнота запрещён (не только .sy), чтобы предотвратить утечку шифротекста или запись в обход слоя шифрования; `temp/` по-прежнему доступен через API файлов администратора и доверенные плагины |

Зашифрованный блокнот — это «остров»: физическая изоляция данных, специализированные точки входа для операций, полное неучастие в глобальных функциях (глобальный поиск / граф связей), отсутствие поддержки публикации, документы и файлы баз данных не пересекают границу. Функции внутри блокнота (редактирование, ссылки на блоки, обратные ссылки, поиск, базы данных, структура, история и т. д.) работают как обычно; после разблокировки AI/LLM может напрямую читать содержимое и использовать поиск внутри блокнота. Зашифрованные блокноты также изолированы друг от друга. Обычные блокноты полностью не затрагиваются.

При вставке содержимого обычного блокнота в разблокированный зашифрованный блокнот для содержащихся в нём локальных вложений создаются отдельные зашифрованные копии, а ссылки во вставляемом содержимом переписываются. Исходные вложения остаются без изменений, а вложения, уже имеющиеся в целевом блокноте, используются повторно. При сбое пакета вставка прерывается, а созданные в этот раз копии очищаются. Это не позволяет совместно использовать вложения между блокнотами или копировать вложения из других зашифрованных блокнотов и не изменяет формат шифрования. «Открыть расположение файла» для зашифрованных вложений продолжает использовать расшифрованную временную копию.

### Ограничения функциональности

Зашифрованный блокнот является островом, поэтому часть функций не поддерживается из-за их межблокнотного характера или зависимости от глобальной агрегации, что составляет чёткую границу функциональности.

- Карточки / интервальное повторение: колоды и расписание пересекают границы блокнотов и зависят от глобальной базы SQLite, не поддерживается

- Публикация: сервис публикации ориентирован на доступ только для чтения или анонимных посетителей; зашифрованный блокнот не участвует в публикации независимо от блокировки или разблокировки и не может быть включён через пароль публикации или настройки видимости

- Закладки: глобальное агрегированное представление (сканирует глобальную siyuan.db), зашифрованный блокнот не поддерживается

- Теги: глобальное агрегированное представление (сканирует глобальную таблицу spans), зашифрованный блокнот не поддерживается

- Переименование файлов ресурсов: имена файлов asset в зашифрованном блокноте обезличены как `uuid-blockID.ext`, имя файла на диске участвует в AAD, поэтому переименование требует повторной упаковки всего ресурса

- Очистка неиспользуемых ресурсов: ресурсы зашифрованного блокнота по-прежнему не участвуют в глобальной очистке. Для разблокированного блокнота предусмотрена отдельная точка входа: Панель документов — Блокнот — Ещё — Очистить неиспользуемые ресурсы; сканирование и удаление строго ограничены текущим блокнотом

- Очистка неиспользуемых баз данных: определения баз данных зашифрованного блокнота не участвуют в глобальной очистке неиспользуемых, чтобы избежать ошибочного удаления из-за невозможности подтвердить связи ссылок при блокировке

## Взаимодействие с пользователем

Настольные клиенты Windows и macOS предоставляют в Настройки — Аутентификация — Зашифрованный блокнот переключатель «Следовать за блокировкой экрана системы», по умолчанию выключенный. После включения блокировка экрана системы блокирует все разблокированные зашифрованные блокноты в каждом ядре рабочего пространства, запущенном самим настольным клиентом, независимо от времени автоматической блокировки по бездействию, и действует даже при нулевом времени бездействия. Удалённые подключения, браузер, Linux и мобильные клиенты не запускают эту операцию блокировки экрана настольной системы. Однако разблокировка системы не разблокирует блокноты автоматически.

Главный процесс настольного клиента ожидает не более одной секунды, чтобы нормально отвечающие окна редактора отправили ожидающий сохранения ввод, а затем вызывает аутентифицированный интерфейс блокировки ядра. Ядро ожидает завершения выполняющихся разблокировок, затем собирает разблокированные блокноты и повторно использует обычный процесс размонтирования для завершения транзакций, сохранения истории, отзыва доступа и очистки управляемых ключей и кэшей. Неотвечающие окна не могут бесконечно блокировать блокировку, а сохранение ввода, ещё не доставленного ядру, не гарантируется. При сбое запроса выполняется повтор после разблокировки или пробуждения системы. Это асинхронная операция блокировки, и не гарантируется, что операционная система будет ждать её завершения перед переходом в спящий режим.

Переключатель сохраняется в `system.encryptedNotebookFollowSystemLock`, вне `NotebookCrypto`. Изменение переключателя не меняет резервную копию ключей, полезную нагрузку аутентификации, формат шифротекста или материалы восстановления. Блокировка влияет на все клиенты, подключённые к соответствующему локальному ядру.

### Проектирование взаимодействия

| Сценарий | Взаимодействие |
|---|---|
| Включение | Настройки — Аутентификация — Зашифрованный блокнот, включить переключатель и задать мастер-пароль (двойной ввод + подтверждение риска) |
| Отключение | Отклоняется при наличии зашифрованных блокнотов или связанной истории в активных данных; снимки локального репозитория должны иметь полностью проверенный архив для завершения настройки ключей. Явное постоянное удаление остаётся отдельной операцией |
| Создание | Панель файлов — меню «Ещё» — «Создать зашифрованный блокнот», после ввода имени и мастер-пароля автоматически разблокируется и открывается |
| Иконка | В закрытом (заблокированном) состоянии отображается иконка замка; после открытия (разблокировки) восстанавливается пользовательский emoji |
| Разблокировка | Нажать на закрытый зашифрованный блокнот, ввести пароль в поле мастер-пароля (🔓 Разблокировать xxx) и подождать ~1 секунду до открытия |
| Блокировка | Эквивалентна закрытию: сначала блокируются новые операции, ожидаются или отменяются текущие задачи, затем удаляется управляемый дескриптор DEK, удаляется зашифрованная база SQLite и по возможности очищаются управляемые ядром кэши открытого текста, временные файлы и токены доступа. Перед закрытием автоматически сохраняются незаписанные правки и история файлов |
| Автоматическая блокировка | Каждый разблокированный блокнот независимо хранит время последней активности; при реальном взаимодействии аутентифицированного пользователя с интерфейсом в текущем рабочем пространстве время активности всех текущих разблокированных зашифрованных блокнотов обновляется единообразно. Клиенты без интерфейса также могут выполнять такое же обновление через явный интерфейс поддержания активности, требующий аутентификации и прав администратора; фоновое чтение, синхронизация, индексация и другая непользовательская активность не поддерживают активность автоматически |
| Смена пароля | Настройки — Аутентификация — Зашифрованный блокнот — «Изменить мастер-пароль» |
| Перемещение документа | Внутри зашифрованного блокнота при изменении только родительского каталога шифротекст перемещается как есть и обновляется индекс; при изменении базового имени файла выполняется повторная упаковка; между обычными блокнотами перемещение работает как обычно; через границу шифрования (обычный ↔ зашифрованный) отклоняется с подсказкой |
| Документ в заголовок | Через границу шифрования отклоняется с подсказкой |
| Ссылки на блоки | Внутри зашифрованного блокнота ссылки работают обычно (поиск `((` ищет только в этом блокноте, панель обратных ссылок отображается нормально); через границу шифрования (обычный ↔ зашифрованный, зашифрованный A ↔ зашифрованный B) блокируются |
| Зеркало базы данных | Внутри зашифрованного блокнота зеркалирование работает обычно; через границу шифрования запрещено |
| Переименование файла ресурса | Не поддерживается (переименование обезличенного имени нарушит сопоставление) |
| Импорт | Поддерживается: импортированные файлы .sy.zip или Markdown автоматически шифруются DEK перед записью на диск |
| История файлов | Поддерживается (для просмотра требуется предварительно разблокировать соответствующий зашифрованный блокнот; индекс истории не хранит открытый текст) |
| Удалённые блокноты | Поддерживается (резервная копия шифротекста, для восстановления требуются совпадающая глобальная резервная копия ключей и мастер-пароль; пока эта история сохраняется, нельзя напрямую удалять зависимую резервную копию ключей) |
| Публикация | Не поддерживается; интерфейс редактирования прав публикации не предоставляет точек настройки для зашифрованных блокнотов и их документов, сервис публикации не видит их независимо от статуса аутентификации |
| Экспорт | Поддерживается (как у обычного блокнота; требуется предварительная разблокировка, экспортируется открытый текст. В заблокированном состоянии экспорт отклоняется) |
| Синхронизация | Без изменений (шифротекст входит и выходит, сохраняя форму шифротекста) |

### Руководство по использованию

#### Первое включение

1. Перейдите в Настройки — Аутентификация — Зашифрованный блокнот и включите переключатель

2. Задайте мастер-пароль (двойной ввод для подтверждения + подтверждение риска). Мастер-пароль — это единый ключ для всех зашифрованных блокнотов, его необходимо запомнить — лазейки для восстановления нет

3. После включения можно в меню «Ещё» панели файлов выбрать «Создать зашифрованный блокнот», ввести имя и мастер-пароль, после чего он автоматически разблокируется и откроется

> Рекомендация по надёжности: более 12 символов, смесь заглавных и строчных букв + цифры + символы. Чем сильнее мастер-пароль, тем выше устойчивость к перебору (лазейка для восстановления пароля не предоставляется).

#### Повседневное использование: разблокировка и блокировка

- Разблокировка: нажмите на закрытый зашифрованный блокнот, введите мастер-пароль и подождите ~1 секунду (вывод Argon2id) до открытия. Разблокировка действует только на этот блокнот, остальные зашифрованные блокноты остаются заблокированными

- Блокировка: закрытие блокнота равносильно блокировке. Ядро останавливает новый доступ, ожидает или отменяет текущие задачи, отзывает управляемый дескриптор DEK и подключения к базам данных и по возможности очищает управляемые ядром кэши открытого текста, временные файлы и токены. Блокировка сразу после использования — важнейшая привычка безопасности, максимально сокращающая время экспозиции ключей и открытого текста

- После перезапуска: все зашифрованные блокноты принудительно закрываются, требуется повторный ввод мастер-пароля для разблокировки (управляемые дескрипторы DEK существуют только в памяти процесса и после перезапуска требуют повторного вывода)

> Важно: в заблокированном состоянии зашифрованный блокнот обеспечивает максимальную защиту на уровне приложения, но блокировка лишь по возможности очищает контролируемые приложением память и временные данные и не гарантирует стирание всех мгновенных копий в операционной системе или нижележащих носителях. Во время разблокировки вызывающие стороны, получившие авторизацию главного приложения (API, плагины, AI/LLM, включая MCP), могут читать открытый текст так же, как из обычного блокнота; читатели и анонимные посетители сервиса публикации, а также CLI ядра всегда отклоняются (подробнее см. предпосылки безопасности в разделе «Границы безопасности»).

#### Изменение мастер-пароля
Перейдите в Настройки — Аутентификация — Зашифрованный блокнот — Изменить мастер-пароль. Смена пароля повторно оборачивает WrappedDEK каждого блокнота и защищает ключи восстановления истории новым паролем без повторного шифрования данных документов. После смены пароля резервная копия ключей автоматически обновляется и синхронизируется; с помощью текущей резервной копии и текущего пароля по-прежнему можно восстановить историю удалённых блокнотов, созданную до смены пароля.

> Важная семантика: смена пароля использует режим обёртки KEK — сам DEK не меняется, лишь WrappedDEK повторно оборачивается новым KEK, выведенным из нового мастер-пароля. Это означает, что смена пароля не отзывает способность старого мастер-пароля к расшифровке: если старый мастер-пароль и старый WrappedDEK (например, сохранённые на стороне синхронизации, в резервных копиях или исторических снимках) утекут одновременно, из них всё равно можно будет извлечь тот же DEK и расшифровать текущие данные. Если есть подозрение, что старый мастер-пароль скомпрометирован, следует экспортировать содержимое в открытом виде, импортировать его во вновь созданный зашифрованный блокнот (новый DEK) и после подтверждения успешной миграции безопасно удалить файлы открытого текста, а не ограничиваться сменой пароля.

#### Синхронизация между устройствами
Шифротекст `.sy`/assets/файлов баз данных зашифрованного блокнота синхронизируется вместе с данными (шифротекст входит и выходит, сохраняя форму шифротекста); глобальные ключевые материалы (MasterSalt и др.) также автоматически резервируются в каталог синхронизации. После синхронизации на новом устройстве не нужно вручную «включать» функцию:

Открытое состояние зашифрованного блокнота не может наследоваться между устройствами. Даже если синхронизированный на локальное устройство файл `conf.json` фиксирует открытое состояние на другом устройстве, пока в локальной памяти нет DEK этого блокнота, и интерфейс, и ядро должны считать его закрытым и пропускать индексацию; после ввода мастер-пароля локальное устройство выполняет разблокировку и монтирование.

При синхронном удалении зашифрованного блокнота, смонтированного на локальном устройстве, ядро должно завершить локальный переход удаления до выполнения полного перестроения индекса, раннего возврата при выходе или обновления интерфейса: закрыть допуск новых операций, дождаться завершения текущих аренд, очистить DEK и состояние монтирования, удалить выделенные индексные базы данных и завершить очистку глобального индекса. Конфигурация на диске после удаления больше не служит основанием для определения необходимости очистки.

1. Настройте ту же учётную запись синхронизации на новом устройстве и завершите синхронизацию

2. Синхронизация загрузит резервную копию ключей локально, и ядро автоматически восстановит состояние «Включено»

3. Нажмите прямо на зашифрованный блокнот и введите мастер-пароль для разблокировки и использования

Если после синхронизации на новом устройстве блокнот всё ещё отображается заблокированным, это нормально — нажмите на него и введите мастер-пароль.

Восстановление при синхронизации может проверить целостность резервной копии, но не может доказать, что это новейшая версия. Пожалуйста, дополнительно храните версионированные резервные копии ключей; при появлении нескольких исторических копий система не может автоматически определить свежесть, и перед восстановлением пользователь должен подтвердить версию по доверенному источнику и информации о времени.

#### Импорт и экспорт

- Импорт: поддерживается импорт `.sy.zip` и Markdown, содержимое автоматически шифруется DEK перед записью на диск, как и созданные вручную документы

- Экспорт: как у обычного блокнота (требуется предварительная разблокировка, экспортируется открытый текст). Поддерживаются `.sy.zip`, HTML, Word, PDF, Markdown и другие форматы; в заблокированном состоянии экспорт отклоняется

- Публикация: не поддерживается. Зашифрованные блокноты и их документы не появляются в сервисе публикации, и разблокировка или установка пароля публикации также не могут включить её

Настольный и мобильный клиенты могут обновлять текущее рабочее пространство через импорт Data.zip. Импорт сначала выполняет анализ, а затем записывает в активные данные. При конфликте зашифрованного блокнота с существующим блокнотом диалог по умолчанию пропускает конфликт и предлагает перезапись и отмену. Пропуск сохраняет каталог блокнота и его ключевые материалы, а результат перед перезагрузкой интерфейса перечисляет пропущенные ID блокнотов. Перезапись следует семантике перезаписи по пути: совпадающие пути заменяются, уникальные файлы цели сохраняются; это не зеркальное восстановление и не распространяет удаления.

Перед импортом отклоняются неканонические псевдонимы путей блокнота. До фиксации можно отменить; во время фиксации нельзя отменить или закрыть диалог, Esc и действие «Назад» на мобильных устройствах также не могут закрыть его. Незафиксированная предварительная проверка истекает через 30 минут и очищается при запуске или следующем импорте, после истечения её всё ещё можно отменить; файлы восстановления зафиксированных пакетов сохраняются.

Импорт зашифрованного содержимого требует ввода мастер-пароля и аутентификации совместимой конфигурации ключей, обёртки блокнота, метаданных, документов, ресурсов и определений баз данных. Резервные копии, созданные до смены пароля, могут считываться с помощью аутентифицированных исторических ключей без отката текущего пароля и без отбрасывания ключей восстановления. Совместимость нельзя определять только по совпадению ID блокнота или строки пароля; блокноты с разным состоянием шифрования или разными ключами данных нельзя объединять напрямую. При неполной локальной конфигурации ключей следует сначала завершить восстановление, а затем импортировать зашифрованное содержимое. Записи транзакций смены пароля из исходного архива не устанавливаются как активные операции. Существующий формат шифротекста, AAD и вывод ключей остаются неизменными.

Затронутые блокноты сначала прекращают приём новых операций и ожидают завершения текущих, затем выполняется замена, а после импорта они остаются заблокированными. Всё выбранное содержимое проходит подготовку и проверку перед фиксацией. Загруженный оригинал, перезаписанные файлы и ключевые материалы сохраняются в `<рабочее пространство>/conf/data-imports/<ID операции>/`, а постоянный журнал восстанавливает незавершённые пакеты перед монтированием и синхронизацией. Эти файлы восстановления следует сохранять до проверки импортированных данных и необходимой истории. Устаревший `/api/import/importData`, CLI и вызовы MCP не перезаписывают тихо конфликты шифрования; интерактивный процесс использует типизированные контракты интерфейсов предварительной проверки, фиксации и отмены.

Если сам откат завершается сбоем, запись, новые операции с блокнотом, принятие конфигурации ключей и синхронизация остаются заблокированными. При повторной инициации импорта сначала выполняется повторная попытка восстановления при монопольном доступе, затем предварительная проверка архива; пропуск возобновляется только после успешного восстановления. Восстановление также выполняется при запуске перед монтированием блокнотов и синхронизацией.

#### Что делать, если забыли пароль
Восстановление невозможно — так задумано (лазейки нет). Даже если шифротекст синхронизирован с облаком, без мастер-пароля его не расшифровать. Обязательно запомните мастер-пароль, рекомендуется хранить его в менеджере паролей.

#### Восстановление при потере резервной копии ключей
Если одновременно потеряны `conf/conf.json` и резервная копия ключей в каталоге синхронизации (крайний случай), повторное включение зашифрованного блокнота будет отклонено с предложением восстановить файл резервной копии. Если удастся вернуть `data-crypto-backup.json` с другого синхронизированного устройства или из ранее экспортированного файла ключей, его можно импортировать через кнопку «Импортировать ключи», отображаемую в состоянии `Disabled` или `RecoveryRequired`, либо вручную восстановить в `<рабочее пространство>/data/.siyuan/` и повторно включить функцию, после чего разблокировать соответствующим этому ключу мастер-паролем.

Восстановление истории удалённого зашифрованного блокнота также требует глобальной резервной копии ключей, совпадающей с его WrappedDEK, и мастер-пароля. Пока необходимо сохранять такую возможность локального восстановления, нельзя окончательно удалять эту историю или совпадающую резервную копию ключей; процесс отключения должен отклонять продолжение при обнаружении такой зависимости.

#### Сценарии, подходящие для зашифрованного блокнота

- Личные дневники, финансовые записи, медицинская информация

- Рабочие секреты, коммерческие предложения, договоры

- Опасение потери или кражи устройства — после шифрования, даже если данные диска будут восстановлены, без мастер-пароля это всего лишь шифротекст

#### Сценарии, не подходящие для зашифрованного блокнота

- Повседневные заметки, учебные конспекты (дополнительные накладные расходы шифрования не оправданы)

- Содержимое, требующее глобального поиска (зашифрованный блокнот не участвует)

- Содержимое, которое нужно предоставлять вовне через сервис публикации (зашифрованный блокнот не поддерживает публикацию)

- Сеть знаний, требующая ссылок на блоки между блокнотами (запрещено через границу)

- Документы, требующие перемещения и упорядочивания между блокнотами (запрещено через границу)

- Сценарии, требующие зеркалирования баз данных между блокнотами (запрещено через границу)

- Содержимое, требующее повторения по карточкам (не поддерживается)

- Содержимое, требующее управления закладками/тегами (не поддерживается)

- Содержимое, к которому нежелателен доступ AI/LLM (после разблокировки AI может читать; если это нежелательно, необходимо держать заблокированным)

- Большое количество крупных файлов (assets расшифровываются полностью при каждом просмотре)

#### Рекомендации по повседневному использованию

1. Мастер-пароль необходимо помнить: забытый пароль = данные необратимо потеряны (лазейки нет)

2. Блокируйте сразу после использования: сокращайте время экспозиции DEK в памяти

3. Не храните все заметки в зашифрованном блокноте: храните только действительно конфиденциальные

4. Надёжность мастер-пароля: рекомендуется более 12 символов, смесь заглавных и строчных букв + цифры + символы

5. Резервное копирование: раздельно храните версионированные резервные копии шифротекста и совпадающие резервные копии ключей; при потере мастер-пароля или всех совпадающих резервных копий ключей шифротекст невозможно восстановить

### Архитектура ключей

```
Мастер-пароль пользователя
    │ Argon2id(глобальный MasterSalt, 64MB/3 итерации/4 потока)
    ▼
   KEK (ключ шифрования ключа, только в памяти, одноразовый)
    │ обёртка AES-256-GCM
    ├─→ расшифровка BoxConf.WrappedDEK → DEK₁ → .sy/assets/файлы БД/базы SQLite зашифрованного блокнота 1
    ├─→ расшифровка BoxConf.WrappedDEK → DEK₂ → зашифрованный блокнот 2
    └─→ расшифровка BoxConf.WrappedDEK → DEK₃ → зашифрованный блокнот 3
```

- Argon2id: используется трудоёмкий по памяти вывод ключа с параметрами 64 MB, 3 итерации, 4 потока

- DEK: независимый 32-байтовый случайный ключ для каждого блокнота, используемый для шифрования данных

- Обёртка KEK: при смене пароля требуется только повторно обернуть DEK без повторного шифрования данных

- KEK не кэшируется: выводится при каждой разблокировке, поддерживая строгую изоляцию между блокнотами

#### Резервное копирование MasterSalt и межустройственное восстановление

MasterSalt — глобальная основа вывода KEK: мастер-пароль + MasterSalt через Argon2id выводят KEK, а KEK затем раскрывает WrappedDEK каждого блокнота. Потеря MasterSalt означает вечную блокировку данных: даже при вводе того же мастер-пароля из-за изменения salt выведенный KEK будет другим, и старый WrappedDEK не удастся раскрыть. Для этого внедрён механизм резервного копирования и восстановления.

Резервная копия: `<DataDir>/.siyuan/data-crypto-backup.json`, хранит весь набор NotebookCrypto (MasterSalt/KEKVerifier/KDFParams/HistoryKEKs). Находится внутри DataDir, поэтому входит в область синхронизации dejavu. Обновляется при включении зашифрованного блокнота и смене мастер-пароля. Отключение сначала проверяет активные блокноты и исторические зависимости, а также полноту архивного покрытия локальных снимков восстановления, затем отдельно сохраняет версионированные ключевые материалы и в конце удаляет активную резервную копию. Файл резервной копии хранится в виде открытого JSON, где verifier и исторические KEK являются шифротекстом, что соответствует способу хранения `conf/conf.json`.

Каждый зашифрованный блокнот отдельно сохраняет `<DataDir>/<boxID>/.siyuan/notebook-crypto-backup.json`, содержащий обёртку ключа BoxEncryption этого блокнота (WrappedDEK/WrapNonce и метаданные аутентификации). Глобальный `data-crypto-backup.json` предоставляет идентичность вывода KEK, а отдельный `notebook-crypto-backup.json` блокнота предоставляет инкапсулированный DEK, поэтому они не могут заменять друг друга.

Точки запуска восстановления (охватывают сценарии потери conf.json / синхронизации на новое устройство / импорта Data.zip и др.):

| Сценарий запуска | Функция | Нужен мастер-пароль? | Описание |
|---|---|---|---|
| После завершения синхронизации (получен файл резервной копии) | `restoreNotebookCryptoConfigFromBackup` | Нет | Записывает конфигурацию обратно в локальный conf.json и ставит `Enabled=true`, UI показывает «Включено, заблокировано» |
| После импорта Data.zip по старому процессу | `restoreNotebookCryptoConfigFromBackup` | Нет | То же самое, покрывает случай «резервная копия прибыла на локальное устройство с Data.zip, но локально не включено» |
| Интерактивный импорт Data.zip | `CommitDataImport` | Нужен при выборе зашифрованного содержимого | Перед фиксацией аутентифицирует совместимые ключи и выбранный шифротекст, сохраняя текущий пароль и исторические ключи восстановления |
| Ввод пользователем мастер-пароля для разблокировки (последняя гарантия) | `tryRestoreNotebookCryptoFromBackup` | Да | `deriveKEK` пытается восстановиться при локальном `Enabled=false`, проверяет мастер-пароль и возвращает KEK |
| Ручное включение пользователем (защита восстановления) | `tryRestoreNotebookCryptoFromBackup` | Да | При наличии существующих зашифрованных блокнотов отклоняет генерацию нового salt, вместо этого восстанавливается из резервной копии и проверяет мастер-пароль |

Разделение восстановления конфигурации и восстановления ключей: восстановлению конфигурации достаточно прочитать файл резервной копии и записать обратно salt/verifier (мастер-пароль не нужен, так как salt не секретен и без мастер-пароля данные всё равно не расшифровать); восстановлению ключей требуется мастер-пароль для вывода KEK и проверки verifier. Это позволяет после синхронизации/импорта автоматически перейти в состояние «Включено», а пользователю достаточно ввести мастер-пароль для разблокировки.

Ручной экспорт и импорт ключей: помимо автоматической синхронизации пользователь может в Настройки — Аутентификация — Зашифрованный блокнот вручную экспортировать и импортировать резервную копию ключей как независимый от синхронизации путь восстановления (например, недоступность синхронизации, перенос между учётными записями, физический автономный перенос).

| Операция | Точка входа | Описание |
|---|---|---|
| Экспорт ключей | Отображается в состоянии «Включено» | Копирует `data-crypto-backup.json` в каталог export для скачивания, пользователь хранит его самостоятельно (API: `/api/notebook/exportNotebookCryptoBackup`) |
| Импорт ключей | Отображается в состоянии `Disabled` или `RecoveryRequired` | Выбор локального файла резервной копии для загрузки, после проверки корректности записывается обратно в `<DataDir>/.siyuan/` и восстанавливает локальную конфигурацию (`Enabled=true`). В дальнейшем разблокируется соответствующим этому ключу мастер-паролем (API: `/api/notebook/importNotebookCryptoBackup`) |

Защита при импорте и восстановлении: полная конфигурация `Enabled` отклоняет импорт во избежание перезаписи существующего salt и осиротения WrappedDEK; `RecoveryRequired` разрешает импорт только тогда, когда ключ-кандидат проходит аутентификацию и может раскрыть все существующие зашифрованные блокноты и перечислимые ядром зависимости истории удалённых блокнотов. Сам файл резервной копии не содержит мастер-пароля (salt не секретен, verifier зашифрован), экспорт и импорт не связаны с утечкой открытых данных, а для разблокировки по-прежнему требуется мастер-пароль.

Защитный механизм восстановления: при наличии зашифрованных блокнотов или зашифрованной истории в активных данных `EnableEncryptedNotebook` восстанавливает существующие ключевые материалы и не генерирует повторно MasterSalt, который сделал бы старые WrappedDEK сиротами; при отсутствии или невозможности аутентификации материалов требуется восстановление. `DisableEncryptedNotebook` проверяет существующие блокноты, связанную историю и локальные снимки восстановления; активные каталоги должны быть явно архивированы и вынесены или удалены, а сохранённые зашифрованные снимки должны иметь полное архивное покрытие. Исходный шифротекст и ключи остаются в архиве, а перед сбросом дополнительно сохраняются отдельные копии текущей конфигурации ключей. Сторону синхронизации, автономные носители и внешние снимки невозможно надёжно перечислить, поэтому если пользователь хочет восстановить эти копии позже, он должен отдельно сохранить экспортированную совпадающую резервную копию ключей до отключения.

Предусловие: `restoreNotebookCryptoConfigFromBackup` срабатывает только при локальном `Enabled=false` и не перезаписывает используемую локальную конфигурацию.

### Структура зашифрованных файлов

```
<workspace>/
├── conf/conf.json                          ← Глобальная конфигурация шифрования (MasterSalt/KEKVerifier)
├── storage/av/                             ← Файлы баз данных обычных блокнотов (открытый текст)
├── data/
│   ├── .siyuan/
│   │   └── data-crypto-backup.json         ← Резервная копия NotebookCrypto (MasterSalt/KEKVerifier, входит в область синхронизации, см. Резервное копирование MasterSalt и межустройственное восстановление)
│   ├── <boxID>/                            ← Каталог зашифрованного блокнота
│   │   ├── .siyuan/
│   │   │   ├── conf.json                   ← BoxConf (Encrypted=true + WrappedDEK)
│   │   │   └── notebook-crypto-backup.json ← Резервная копия BoxEncryption одного блокнота
│   │   ├── *.sy                            ← Шифротекст AES-256-GCM
│   │   ├── assets/
│   │   │   └── <uuid>-<blockID>.ext        ← Зашифрованный контейнер одного файла, имя файла обезличено
│   │   └── storage/av/
│   │       └── <avID>.json                 ← Файл базы данных (шифрование DEK)
│   └── <normalNotebookID>/                  ← Обычный блокнот (открытый текст, не трогается)
├── history/                                ← Каталог истории (шифротекст хранится как есть)
│   └── <timestamp>-update/
│       └── <boxID>/                        ← История зашифрованного блокнота (шифротекст .sy + зашифрованные файлы баз данных)
└── temp/
    ├── siyuan.db                           ← Глобальная SQLite (открытый текст, не содержит данных зашифрованных блокнотов)
    ├── blocktree.db                        ← Глобальная blocktree (открытый текст, не содержит данных зашифрованных блокнотов)
    ├── siyuan-encrypted-<boxID>.db         ← База SQLite content зашифрованного блокнота (SQLCipher)
    └── siyuan-encrypted-<boxID>-blocktree.db ← База SQLite blocktree зашифрованного блокнота (SQLCipher)
```

### Шифрование и расшифровка .sy / assets / файлов баз данных

Прозрачное шифрование и расшифровка `.sy` (уровень filesys):

- Внедрение обратного вызова `DEKProvider` (во избежание циклических зависимостей)

- Расшифровка после чтения с диска, шифрование перед записью на диск, в кэше хранится открытый текст

- Чтение заголовка зашифрованного блокнота требует полного чтения + расшифровки с последующим разбором

- AAD для `.sy` привязывает boxID, тип объекта и стабильное базовое имя файла `<rootID>.sy`, без включения родительского каталога; базовое имя файла должно совпадать с ID корневого блока после расшифровки и быть глобально уникальным внутри блокнота

- Родительский каталог не входит в AAD, приложение по-прежнему строит иерархию документов по существующей структуре каталогов; при загрузке проверяется совпадение базового имени файла с ID корневого блока после расшифровки, а также отклоняются дублирующиеся ID объектов, недопустимые пути и циклические иерархии внутри одного блокнота, но криптографическая целостность отношений родительского каталога не обеспечивается

Шифрование assets:

- При загрузке полностью считывается в память + шифруется + записывается на диск (потоковое шифрование невозможно)

- Обезличивание имени файла: имя файла asset в зашифрованном блокноте имеет вид `<uuid>-<blockID>.<ext>`, а исходное имя, размер открытого текста и количество фрагментов сохраняются в том же контейнере ресурса как аутентифицированные зашифрованные метаданные

- Вновь записываемые контейнеры начинаются с идентификатора `SYAE`, аутентифицированные зашифрованные метаданные включают `spec=2`, 32-байтный `containerID`, генерируемый CSPRNG операционной системы при каждой записи, исходное имя, размер открытого текста и количество фрагментов; AAD фрагментов содержимого имеет вид `siyuan:asset:<boxID>:assets/<diskName>:content:v2:<containerID в нижнем регистре hex>:<индекс фрагмента с нуля>`, а метаданные имени аутентифицируются с тем же префиксом и суффиксом `:metadata`. Фрагменты или метаданные разных версий записи не могут взаимозаменяться; откат всего старого контейнера по-прежнему не входит в область защиты

- При чтении сначала аутентифицируются и расшифровываются метаданные имени, затем пофрагментно аутентифицируется и расшифровывается содержимое; при скачивании используется исходное имя из контейнера

- Поддерживается совместимость со старыми ресурсами `SYAE`, в метаданных которых одновременно отсутствуют `spec` и `containerID`; их фрагменты аутентифицируются с помощью `siyuan:asset:<boxID>:assets/<diskName>:content:<индекс фрагмента>`; чтение имени, чтение содержимого, экспорт и исторические снимки поддерживают этот формат. Явно пустая версия, отсутствие обязательных полей новой версии, неизвестная версия и сбой аутентификации отклоняются без попытки использовать AAD других версий

- Новые или повторно сохранённые ресурсы единообразно записываются в версии 2; простое открытие, предпросмотр, скачивание или экспорт не перезаписывают исходный файл и не требуют от пользователя пересоздания ресурсов. Старый формат имеет только прежнюю пофрагментную аутентификацию и не может постфактум проверить, не были ли сшиты фрагменты разных версий записи; повторно сохранённый контейнер версии 2 обладает привязкой фрагментов, но это не доказывает, что старое содержимое ранее не было сшито. Совместимое чтение не предоставляет гарантий защиты от понижения версии или отката, и данные, заменённые на старый формат, по-прежнему проверяются по старому формату

- Для зашифрованного блокнота отключён откат к глобальным assets, принудительно используется уровень блокнота

- Переименование файлов ресурсов запрещено (обезличенное имя файла на диске участвует в AAD, переименование требует повторной упаковки всего ресурса)

- Исходное имя и содержимое ресурса находятся в одном зашифрованном контейнере, межфайловой транзакции сопоставления имён не существует; при сбое записи вызывающей стороне должна возвращаться ошибка

Шифрование файлов баз данных:

- Откат пути (fallback): файлы баз данных зашифрованного блокнота хранятся в `<boxID>/storage/av/<avID>.json`, обычные блокноты по-прежнему хранят их в глобальном `storage/av/`

- Чтение: сначала проверяется глобальный путь, если не найдено — выполняется обход открытых зашифрованных блокнотов; после нахождения выполняется расшифровка DEK и затем разбор JSON

- Сохранение: после сериализации JSON маршрутизируется по пути (глобальный открытый текст / зашифрованный блокнот с шифрованием DEK)

- Первое создание: `RenderAttributeView` определяет boxID по blockID и заранее задаёт принадлежность

- Зеркало: зашифрованным блокнотам запрещено участвовать в зеркалировании через границу; внутренние зеркала зашифрованного блокнота хранятся в `blocks.msgpack` уровня блокнота

## Реализация и интерфейсы

### Проектирование изоляции баз данных SQLite

```
Операция с обычным блокнотом:
  Фронтенд → API → исходная функция → глобальная blocktree.db → глобальная siyuan.db

Операция с зашифрованным блокнотом (выделенный путь чтения с boxID):
  Фронтенд (с notebook) → маршрутизация API handler → функция InBox
    → зашифрованная база SQLite blocktree → зашифрованная база SQLite content
```

Путь записи: сосредоточен в единой точке входа, выбирает базу SQLite по блокноту. Очередь индексации, функции записи blocktree и исправление индекса полностью маршрутизируются по блокноту.

Путь чтения: трёхуровневый fall-through — уровень handler маршрутизирует по параметру `notebook`; исходная функция перенаправляет в версию InBox (обычный путь передаёт пустой boxID); нижележащая обёртка определяет маршрут в зависимости от того, открыта ли зашифрованная база SQLite, а пустой boxID обязательно использует глобальную базу SQLite.

Принцип глубокой полной маршрутизации: каждый вызов sql, через который проходит операция чтения зашифрованного блокнота (включая глубокие helper-функции: подсчёт ссылок, имена/псевдонимы блоков, рекурсия дочерних блоков, подсчёт FTS, подсветка, поиск mention, запросы определений refs и т. д.), маршрутизируется в зашифрованную базу SQLite и никогда не утекает в глобальную базу SQLite.

Откат общих точек входа: основные функции, такие как `GetBlockTree` / `ExistBlockTree` / `GetBlockTrees` / `LoadTreeByBlockID`, если не находят в глобальной базе, автоматически обходят открытые зашифрованные блокноты.

### Защита ссылок на блоки через границу шифрования

Ссылки на блоки зашифрованного блокнота: внутри блокнота работают обычно, через границу шифрования запрещены. Трёхуровневая защита:

1. Маршрутизация поиска на фронтенде: при вводе `((` или `{{` внутри зашифрованного блокнота для запуска поиска запрос содержит параметр `notebook`, ядро ищет только в собственной зашифрованной базе SQLite этого блокнота, результаты не содержат блоков других блокнотов

2. Маршрутизация на уровне handler: зашифрованный блокнот вызывает выделенную версию поиска

3. Итоговая проверка перед записью в базу: перед фиксацией транзакции в базу выполняется обход дерева, для каждого узла ссылки на блок определяется, пересекает ли он границу, и при пересечении он понижается до обычного текста (очищается атрибут ссылки, сохраняется текст якоря). Это защищает от ручного ввода ID блока, перетаскивания, вставки и прямых вызовов API

### Правила перемещения через границу

В зашифрованном блокноте запрещено перемещение документов через границу шифрования (обычный ↔ зашифрованный, в обе стороны).

Риск повреждения данных: перемещение между блокнотами использует Rename файловой системы для прямого перемещения потока байтов `.sy` без преобразования шифрования/расшифровки. Поэтому шифротекст, перемещённый в обычный каталог, нечитаем, и открытый текст, перемещённый в зашифрованный каталог, нечитаем. Индекс также невозможно перенести между базами.

Перемещение внутри одного зашифрованного блокнота: AAD шифротекста `.sy` привязывает только стабильное базовое имя файла и не привязывает родительский каталог. Перемещение без изменения базового имени файла выполняется по семантике перемещения внутри одного ящика обычного блокнота — прямым Rename шифротекста без повторной упаковки корневого документа или дочерних документов; только при изменении самого базового имени файла выполняется проверка и расшифровка по старому базовому имени и повторная упаковка по новому базовому имени. После завершения перемещения обновляется индекс, обработка сбоев совпадает с обычным блокнотом без добавления дополнительных метаданных иерархии шифрования.

Риск утечки безопасности: при перемещении из зашифрованного блокнота в обычный — текст документа теряет защиту шифрования; связанные resources должны быть вынесены и расшифрованы вместе; сеть ссылок, связывающая блоки и дочерние документы, разрывается или приводит к сопутствующей утечке; перенос метаданных индекса между базами нарушает изоляцию.

Проектная позиция: зашифрованный блокнот — это остров, содержимое не входит и не выходит (вынос из зашифрованного блокнота в обычный приведёт к утечке открытого текста; обратное приведёт к повреждению шифротекста).

### Доступность для AI / LLM

Видимость зашифрованного блокнота для AI/LLM через поддерживаемые специализированные точки входа определяется состоянием разблокировки; отдельный переключатель на уровне функций «скрыть от AI» не предусмотрен. Глобальный поиск, семантический поиск и векторные эмбеддинги никогда не включают зашифрованное содержимое.

В заблокированном состоянии: AI/LLM (включая MCP и агентов) не могут получить доступный дескриптор DEK, все специализированные точки входа зашифрованного блокнота отклоняют доступ; отдельная база данных закрыта, содержимое на диске является шифротекстом, поэтому эти вызывающие стороны не могут прочитать зашифрованное содержимое.

В разблокированном состоянии: DEK находится в памяти, AI/LLM могут читать содержимое зашифрованного блокнота и искать по полному тексту внутри блокнота — инструменты MCP могут перечислять зашифрованные блокноты и их документы, читать содержимое блоков, выполнять поиск FTS внутри блокнота и т. д. Однако глобальный поиск, семантический поиск и векторные эмбеддинги по-прежнему не участвуют (зашифрованные данные не попадают в глобальные таблицы `block_embeddings`/`blocks` и физически недоступны), подробнее см. таблицу сравнения «Зашифрованный блокнот vs Обычный блокнот».

Проектная позиция: изоляция «скрыть от AI» на уровне функций не делается, так как такая изоляция и неполна, и усложняет модель безопасности для понимания. После блокировки поддерживаемые точки входа не могут получить доступ к содержимому, но блокировка не заменяет защиту на уровне процесса и операционной системы. Пользователю достаточно усвоить одно правило: блокировать конфиденциальное содержимое сразу после использования.

### Различия в производительности

| Операция | Обычный блокнот | Зашифрованный блокнот | Причина различия |
|---|---|---|---|
| Разблокировка (Mount) | Мгновенно | Задержка ~1 сек | Вывод ключа Argon2id (намеренно медленный для защиты от перебора) |
| Открытие документа | Чтение с диска + разбор JSON | Чтение с диска + расшифровка AES-GCM + разбор + запрос к зашифрованной базе SQLite | Дополнительная расшифровка + запрос к зашифрованной базе SQLite |
| Сохранение документа | Рендеринг JSON + запись на диск | Рендеринг JSON + шифрование AES-GCM + запись на диск | Дополнительное шифрование |
| Загрузка assets | Потоковая запись на диск | Полное чтение в память + шифрование + запись на диск | Потоковое шифрование невозможно; нагрузка на память при больших файлах |
| Просмотр assets | Прямой ServeFile | Чтение с диска + расшифровка + вывод | Расшифровка при каждом запросе, без кэша браузера |
| Рендеринг базы данных | Глобальная blocktree + открытый JSON | Зашифрованная blocktree + расшифровка JSON с помощью DEK | Дополнительная расшифровка JSON; пакетная загрузка IAL маршрутизируется по блокноту |
| Сохранение базы данных | Запись открытого JSON на диск | Шифрование DEK + запись на диск | Дополнительное шифрование |
| Поиск внутри блокнота | Поиск FTS в глобальной базе SQLite | Поиск FTS в отдельной зашифрованной базе SQLite | Постраничная расшифровка SQLCipher ~5–10% накладных расходов |
| Подключения к БД | 1 глобальное | 1 глобальное + 2 на каждый разблокированный зашифрованный блокнот | Пул ~20 подключений на каждую зашифрованную базу SQLite |
| При блокировке | Без дополнительных расходов | Отзыв управляемого дескриптора ключа и максимально возможная очистка кэшей и временных файлов | Задержка холодного старта при следующей операции |

Примечания по производительности:

- Повседневное редактирование: практически незаметно. Шифрование и расшифровка AES-GCM занимают микросекунды, узким местом чтения/записи документов является дисковый ввод-вывод

- Заметная задержка: разблокировка ~1 сек, просмотр больших assets (расшифровка каждый раз без кэша), первый доступ после блокировки (холодный старт)

- Нулевое влияние на обычные блокноты: логика шифрования/расшифровки и маршрутизации пропускается по короткому пути для незашифрованных блокнотов

### Конечный автомат и правила параллелизма

Глобальное состояние — `Disabled`, `Enabled` или `RecoveryRequired`. В нормальном установившемся состоянии при `Disabled` не должно существовать активных зашифрованных блокнотов или перечислимых ядром ключевых зависимостей; если при запуске глобальная конфигурация отсутствует или отключена, но обнаружены зашифрованный блокнот или данные восстановления, система должна перейти в `RecoveryRequired` и отказаться считать их обычными блокнотами до восстановления совпадающей резервной копии ключей. При `Enabled` каждый зашифрованный блокнот независимо находится в состоянии `Locked`, `Unlocking`, `Unlocked`, `Locking` или `Error`, и после запуска приложения все начинают с `Locked`.

Определение зашифрованной идентичности должно работать по принципу fail-closed. При отсутствии или повреждении `conf.json` с допустимым boxID или резервной копии ключей блокнота, если на диске присутствует текущий маркер формата шифротекста либо текущий процесс уже подтвердил зашифрованную идентичность этого блокнота, блокнот должен быть переведён в `Error` с отказом в чтении и записи как обычного блокнота, без автоматического создания конфигурации `Encrypted=false`. Удалить зашифрованную идентичность времени выполнения можно только в процессе удаления блокнота после завершения аренд жизненного цикла и очистки локального DEK, маркера монтирования, выделенной базы данных и кэшей.

| Переход | Предусловие | Инвариант после успеха | Обработка сбоя |
|---|---|---|---|
| `Locked → Unlocking → Unlocked` | Мастер-пароль успешно проверен и конфигурация шифротекста совпадает | Доступный дескриптор DEK существует только в управляемой памяти; выделенная база данных открыта; разрешены специализированные точки входа блокнота | Отозвать выведенные дескрипторы KEK/DEK, закрыть открытые ресурсы и вернуться в `Locked` |
| `Unlocked → Locking → Locked` | Атомарно закрыт допуск новых операций и завершены или отменены текущие операции | Нет доступного управляемого дескриптора DEK или подключения к базе данных; управляемые ядром кэши открытого текста, временные файлы и токены по возможности очищены | После завершения очистки ключей и базы данных всё равно перейти в `Locked`; при сбое очистки временных файлов записать только диагностику без открытого текста и повторить при выходе или следующем запуске |
| `Unlocked → Error` | Сбой аутентификации шифротекста, сбой открытия базы данных или нарушение инварианта | Немедленный отказ в чтении и записи, без отката к пути обычного блокнота | Закрыть ресурсы, диагностика не должна содержать открытый текст; пользователь может только заблокировать или повторно разблокировать |
| Смена мастер-пароля | Все зашифрованные блокноты находятся в `Locked` | Все WrappedDEK, глобальная конфигурация и резервная копия обновляются как одна восстанавливаемая транзакция | Сохранить старую конфигурацию и резервную копию работоспособными; не допускается ситуация, когда новым паролем можно разблокировать лишь часть блокнотов |

Каждый блокнот использует единый контроллер жизненного цикла для управления состоянием, допуском операций и счётчиком активных операций. Операции чтения, редактирования, экспорта, предпросмотра, синхронизации, индексации, просмотра или восстановления истории, доступа AI/MCP и т. д. могут получить аренду жизненного цикла только для чтения исключительно в состоянии `Unlocked` и удерживать её до завершения разбора, публикации кэша, HTTP-ответа или завершения скачивания, а также до завершения регистрации асинхронного результата. Разблокировка и открытие должны выполняться внутри одной блокировки перехода блокнота; сбой монтирования может откатить только вновь созданное состояние разблокировки и не может заблокировать DEK или монтирование, уже используемое другими параллельными запросами. Блокировка и удаление атомарно переводят состояние в `Locking` и закрывают допуск новых аренд, затем получают монопольную аренду, отменяют или ожидают все текущие операции и внутри монопольной аренды закрывают базу данных, отзывают управляемый дескриптор DEK и по возможности очищают кэши и временные артефакты. После завершения очистки дескриптора ключа и подключений к базе данных публикуется состояние `Locked`; сбой удаления временных файлов не препятствует блокировке, но должен фиксироваться в диагностике и повторяться при выходе или следующем запуске. Таким образом, после завершения блокировки не может появляться новых ответов с открытым текстом, повторного заполнения кэша или переподключения к базе данных, но на диске могут оставаться временные копии открытого текста, которые не удалось удалить.

Блокировка глобальной конфигурации должна захватываться раньше любой блокировки жизненного цикла блокнота; при одновременном затрагивании нескольких блокнотов блокировки жизненного цикла захватываются в лексикографическом порядке boxID; блокировки кэша DEK, баз данных, файлов и других подсистем могут захватываться только после блокировки жизненного цикла и должны освобождаться до освобождения блокировки жизненного цикла. Запрещено захватывать в обратном порядке, а также повторно захватывать блокировку глобальной конфигурации или другие блокировки более низкого уровня при удержании блокировки подсистемы. Автоматическая блокировка хранит время активности для каждого блокнота отдельно, но одно аутентифицированное взаимодействие пользователя с интерфейсом в текущем рабочем пространстве или явное поддержание активности единообразно обновляет все текущие разблокированные блокноты; отсчёт времени использует системные часы и проверяется периодической задачей, поэтому изменение системных часов может соответственно приблизить или отложить срабатывание — автоматическая блокировка является защитой удобства, а не точной границей безопасности по времени.

### Границы функциональности, временный открытый текст и правила интерфейсов

Файлы ресурсов в зашифрованном блокноте не поддерживают распознавание текста (OCR) независимо от состояния разблокировки. Ручное распознавание возвращает локализованное сообщение «Не поддерживается», автоматическое распознавание пропускает ресурсы зашифрованных блокнотов; для этих ресурсов нельзя генерировать текст OCR или записывать в глобальное хранилище OCR и поисковый индекс.

Неподдерживаемые публикация, карточки, закладки, теги, переименование ресурсов, глобальная очистка неиспользуемых ресурсов и очистка неиспользуемых баз данных должны единообразно обрабатываться во фронтенде, HTTP API, API плагинов, MCP и процессах импорта: для целей в зашифрованном блокноте возвращается явная ошибка «Не поддерживается», не создаются глобальные индексы, глобальные атрибуты или отложенные задачи; существующие устаревшие данные не должны загружаться, агрегироваться или записываться обратно. Определение доступа к публикации должно быть независимо от состояния блокировки и иметь приоритет над `publishAccess.json`, а существующая конфигурация публикации не должна снова делать зашифрованный блокнот видимым. Коды ошибок и локализованные тексты должны быть стабильными для распознавания вызывающими сторонами.

Специализированные интерфейсы `/api/asset/getUnusedEncryptedBoxAssets` и `/api/asset/removeUnusedEncryptedBoxAssets` должны явно указывать один разблокированный зашифрованный блокнот. Сканирование аутентифицирует все документы и определения баз данных этого блокнота, включая статические ссылки в сессиях агентов и вложениях инструментов, и защищает сопутствующие файлы `.sya` для ссылаемых PDF. Любой сбой чтения, аутентификации, разбора или обхода каталогов прерывает сканирование. При удалении повторно проверяются только подтверждённые пользователем кандидаты с одновременной координацией допуска блокнота, транзакций редактирования и синхронизации; при наличии других активных запросов требуется повтор. Удаление начинается только после аутентификации и пакетного резервного копирования шифротекста ресурсов. При сбое исходные файлы восстанавливаются; перед запуском синхронизации восстанавливаются незафиксированные журналы очистки в `.siyuan/asset-cleanup/` рабочего пространства. Исторический шифротекст сохраняет исходный формат и стабильное базовое имя. Существующий глобальный индекс истории может фиксировать обезличенное имя файла, путь и время, сохраняя эти метаданные и после блокировки, но не должен фиксировать исходное имя файла или содержимое открытого текста. Глобальный индекс содержимого ресурсов, данные OCR и кэш открытого текста не создаются.

При отказе в операции необходимо указывать конкретную причину и возможный способ решения, а не покрывать несвязанные причины одной общей фразой: например, при импорте `.sy.zip` с карточками следует указать документ или колоду с карточками и предложить удалить карточки в исходном блокноте и экспортировать заново либо импортировать в обычный блокнот; при отсутствии разблокировки следует предложить разблокировать; при перемещении или ссылке через границу шифрования следует объяснить, что зашифрованный блокнот является изолированным пространством, а не возвращать «Операция не поддерживается».

Все исходные точки входа, способные обойти специализированные пути чтения и записи, должны быть зарегистрированы, включая файловый API, CLI ядра, файловые инструменты MCP, WebDAV, файловые интерфейсы плагинов, URL скачивания экспорта, URL предпросмотра и фоновые задачи. Постоянный каталог зашифрованного блокнота всегда отклоняет прямой доступ через исходные точки входа во избежание утечки шифротекста или записи в обход слоя шифрования; `temp/` рабочего пространства является общим временным пространством, доступным API файлов администратора, API архивов и доверенным плагинам, и не относится к границе контроля доступа шифрования. WebDAV продолжает безусловно отклонять весь `temp/`, чтобы не раскрывать временные данные через удалённый файловый сервис. При добавлении новой точки входа необходимо отдельно проверять, затрагивает ли она постоянный каталог зашифрованного блокнота или временный открытый текст.

#### Жизненный цикл временного открытого текста

При выполнении на настольном клиенте внешнего открытия или открытия расположения файла для разблокированного зашифрованного ресурса `/api/asset/resolveAssetPath` после аутентификации содержимого ресурса возвращает путь к копии открытого текста в `temp/export/<boxID>/external/<exportID>/<исходное имя файла>`, сохраняя исходное расширение для распознавания системной ассоциированной программой. «Открыть расположение файла» указывает на эту копию, внешнее редактирование не записывается обратно в зашифрованное вложение. Запрос удерживает аренду жизненного цикла блокнота до завершения ответа; при блокировке и запуске копия по возможности очищается по правилам управляемого временного каталога. При блокировке или сбое аутентификации доступ по-прежнему отклоняется, а исходный шифротекст сохраняется.

Экспорт делится на два типа: внешнее место назначения, явно выбранное пользователем, допускает создание открытого текста, но перед началом необходимо предупредить о риске; управляемые ядром предпросмотр, преобразование, скачивание и промежуточные артефакты единообразно размещаются в `temp/export/<boxID>/<kind>/<exportID>/`. Первый уровень boxID является идентификатором принадлежности для очистки, а не правом доступа; обычный экспорт и временные файлы плагинов не должны использовать допустимый boxID в качестве имени первого уровня в `temp/export/`.

Находящийся в памяти токен экспорта `managedEncryptedExports` используется для управления сроком действия и жизненным циклом ссылок на скачивание и не является изоляцией безопасности для локальных файлов, API администратора или доверенных плагинов. При блокировке, удалении, отмене, сбое и нормальном выходе соответствующие токены должны быть отозваны, а `temp/export/<boxID>` по возможности удалён; при запуске приложения как минимум сканируются и удаляются остаточные каталоги, имя первого уровня которых является допустимым boxID, а общая инициализация временного каталога настольного клиента дополнительно очищает весь `temp/export`. Ни одна вызывающая сторона не должна полагаться на сохранение файлов в `temp/` между процессами. При сбое удаления фиксируется только диагностика без открытого текста, что не мешает блокноту перейти в `Locked`, а при последующем выходе или запуске попытка продолжается. Журналы, отчёты об ошибках, миниатюры, артефакты OCR/преобразования и буфер обмена также по умолчанию не должны содержать открытый текст, если пользователь явно не передал его внешней программе.

Мобильный нативный процесс сохранения должен через `AcquireExportFile` получить аренду экспорта, содержащую путь, имя, размер и ID аренды, а в ветке `finally` после завершения копирования и проверки вызвать `ReleaseExportFile`; для зашифрованного экспорта нельзя использовать старые интерфейсы, возвращающие только путь или имя, так как они не охватывают жизненный цикл этапа нативного копирования.

## Совместимость и восстановление

### Архив неразблокируемого блокнота

`keys/persisted-conf.json` хранит последнюю сгенерированную текущим процессом форму сохранения конфигурации шифрования блокнота и записывается перед синхронной записью в файл конфигурации. Создание архива считывает этот снимок в памяти, не открывая заново `conf/conf.json`; если форма сохранения ещё не сгенерирована, используется текущая конфигурация шифрования. Имена ключей и программа чтения восстановления сохраняют совместимость с существующим архивом версии 1; прежние резервные копии и материалы-кандидаты миграции смены пароля по-прежнему сохраняются и аутентифицируются при восстановлении.

Архив зашифрованного блокнота использует независимый контейнер `siyuan-encrypted-notebooks` версии 1 и не изменяет существующие форматы документов, ресурсов, определений баз данных, AAD или обёртки ключей. Архив содержит исходный каталог выбранного блокнота, связанную локальную историю, соответствующие файлы в снимке локального репозитория, а также существующую глобальную конфигурацию шифрования, резервную копию ключей и записи миграции смены пароля. Ресурсы по требованию и отсутствующие фрагменты локального снимка должны быть предварительно восполнены; при сбое вынос не фиксируется. Список файлов, размеры и дайджесты SHA-256 используются только для проверки целостности копирования и не означают, что шифротекст аутентифицирован или материалы обязательно восстанавливаемы.

Генерация архива и подтверждение выноса выполняются раздельно. Перед подтверждением повторно проверяются исходный каталог, история, ключевые материалы и всё ещё существующие связанные снимки; при изменении требуется повторное архивирование. Инициирование скачивания в браузере или старой версии мобильного клиента не равносильно завершению сохранения — пользователь должен явно подтвердить, что сохранил отдельно. Фиксация через постоянную запись перемещает выбранный исходный каталог в `<рабочее пространство>/conf/notebook-archives/<ID операции>/removed/`, сохраняя архив и исходные материалы восстановления; незафиксированное перемещение откатывается при запуске без создания новой истории удаления. Частичный вынос не изменяет глобальные ключи и распространяется при обычной синхронизации данных. Снимки репозитория автоматически не удаляются; перед завершением старой конфигурации ключей необходимо подтвердить, что её зависимости зашифрованного восстановления покрыты полным архивом, отдельно сохранить версионированные ключевые материалы и лишь затем очистить старые поля ключей, включая `HistoryKEKs`.

Первая версия восстановления ориентирована только на автономное рабочее пространство без ключей шифрования или зашифрованных данных и с отключённой синхронизацией. Пользователь предоставляет прежний мастер-пароль и может дополнить его позже найденной совпадающей резервной копией ключей. Восстановление сначала во временном изолированном каталоге проверяет версию архива, пути, список файлов, HMAC резервной копии ключей, исторические ключи, обёртку блокнота, метаданные и шифротексты документов, ресурсов и баз данных; после успешной аутентификации всего содержимого выполняется фиксация, а блокнот остаётся заблокированным. Существующая глобальная конфигурация шифрования и резервная копия сохраняются как материалы-кандидаты восстановления без перезаписи включённой конфигурации и без создания замещающих ключей для недействительных или отсутствующих материалов аутентификации. Снимки репозитория в архиве преобразуются в историю удаления блокнота для восстановления, а исходный архив сохраняет ID снимка и исходный путь. При сбое или прерывании загруженный оригинал сохраняется, а незафиксированный целевой каталог откатывается; старый шифротекст не отбрасывается, аутентификация не обходится, и восстановление данных при потерянном мастер-пароле или потере всех совпадающих ключевых материалов не обещается.

### Стратегия совместимости существующих данных

Текущие записанные зашифрованные данные служат базой совместимости. Изменения форматов и управления ключами должны сохранять читаемость и восстанавливаемость существующих данных, и нельзя требовать от пользователя удаления или пересоздания данных под предлогом этапа разработки. Область совместимости включает документы, ресурсы и их исходные имена, определения баз данных, обёртки ключей, резервные копии, историю и снимки синхронизации.

При конфликте транзакции источника документа сохраняется текущее состояние файла, включая последующее перемещение или удаление. Исходная запись восстановления версии 1 сначала архивируется в `conf/document-source-recovery/<ID транзакции>/record.json`, а активная запись затем завершается через восстановление индекса. Снимок шифротекста остаётся шифротекстом, а существующая глобальная конфигурация шифрования, резервная копия ключей, записи миграции смены пароля и обёртка ключей блокнота сохраняются вместе. Проверка архива проверяет только копирование и не означает, что шифротекст аутентифицирован. Индекс восстановления перестраивается из аутентифицированного снимка источника без перезаписи источника документа; закрытые или заблокированные блокноты обрабатываются при монтировании. Повреждённые или неподдерживаемые записи восстановления, а также сбои аутентификации источника по-прежнему должны вызывать ошибку с сохранением оригинала. Формат документа, AAD, вывод ключей или существующий путь аутентифицированного чтения не изменяются.

Привязки баз данных соблюдают те же границы изоляции. При импорте `.sy.zip` в зашифрованный блокнот привязки, указывающие на блоки текущего импорта, переназначаются на новые блоки; привязки, указывающие на блоки вне пакета, преобразуются в непривязанные записи с сохранением ID записи, сохранённого текста и значений других полей. Обратные привязки импортируемых документов сохраняют только базы данных внутри пакета. Импорт не должен записывать привязки баз данных обратно в документы за пределами целевой границы. Обычный импорт сохраняет привязки, указывающие на существующие обычные документы. При добавлении новой привязанной записи, перепривязке и редактировании привязанного первичного ключа необходимо проверять границу до изменения записи или документа.

При экспорте нельзя незаметно удалять существующие недействительные обратные привязки баз данных, а также нельзя разрешать их через границу шифрования. Ошибка экспорта должна указывать ID затронутой базы данных и сохранять исходные данные. При проверке затронутого документа следует поочерёдно сверить его `custom-avs` с базами данных в разрешённой области хранения и после сохранения резервной копии явно удалить только подтверждённо недействительные привязки. Отсутствие файла, повреждение данных и сбой аутентификации по-прежнему должны вызывать ошибку; разблокировка другого зашифрованного блокнота не включает его базы данных в область экспорта этого документа. Данное исправление привязок не изменяет формат шифротекста, AAD, ключи или путь аутентифицированного чтения старого формата.

Форматированный текст ячеек таблицы использует `Spec: "4"` документа и добавляет необязательную обёртку исходных данных `TableCellRich` в аутентифицированное синтаксическое дерево открытого текста. Существующие версии документов остаются читаемыми, ячейки автоматически не преобразуются. Обёртка шифрования документа, AAD, вывод подключей и ключи восстановления остаются неизменными. При чтении, экспорте, истории, снимках и восстановлении сначала аутентифицируется шифротекст, затем проверяются версии документа и форматированного текста; неизвестный формат или повреждённые исходные данные должны вызывать ошибку с сохранением исходных данных. Проекцию на уровне строк можно перестраивать только после успешной аутентификации и проверки исходных данных.

Устаревший форматированный текст первичного ключа базы данных использует спецификацию базы данных 15 и применяет тот же источник `inline-ast` версии 1, что и заголовок документа. Существующие версии баз данных (включая обычные первичные ключи спецификации 14) остаются читаемыми, а старый текст, похожий на Markdown, не переинтерпретируется как форматирование. Обёртка шифрования, AAD, ключи и материалы восстановления остаются неизменными. При повторном открытии, экспорте, истории, снимках и восстановлении сначала аутентифицируется источник базы данных, затем проверяется источник на уровне строк и перестраивается проекция. Неизвестная или повреждённая версия должна вызывать ошибку с сохранением исходного файла. Привязанные записи, строчные ссылки на блоки и ресурсы по-прежнему соблюдают границы изоляции блокнота, в котором находится база данных; редактирование привязанного первичного ключа изменяет статический текст якоря без перезаписи исходного документа или блока. Вновь редактируемый форматированный текст первичного ключа использует источник Kramdown той же формы, что и текстовое поле, и требует спецификации базы данных 16. Существующие источники inline-ast спецификации 15 остаются читаемыми, чтение или фиксация без изменений не преобразуют формат источника, и обновляются только базы данных, сохраняющие новый источник. Старые клиенты не могут открывать обновлённые базы данных, и для отката требуется восстановление полного снимка до обновления. Шифротекст, аутентифицированный до обновления, по-прежнему сохраняет возможность восстановления через существующие пути атомарной записи и снимков без изменения обёртки шифротекста, AAD или ключей.

Сохранение строчных изображений в текстовых полях базы данных требует спецификации базы данных 17. Изображения продолжают использовать существующий источник Kramdown и хранилище ресурсов блокнота. При сохранении обычных текстовых полей в базах данных спецификации 16 и более ранних версий сохраняется прежняя версия; восстановление снимка до обновления позволяет вернуть ранее аутентифицированную версию.

### Границы безопасности

Предпосылка безопасности: в закрытом (заблокированном) состоянии зашифрованный блокнот обеспечивает максимальную защиту на уровне приложения. После завершения блокировки новые операции отклоняются, управляемые дескрипторы DEK и подключения к базам данных удалены, а управляемые ядром кэши открытого текста, временные файлы и токены по возможности очищены; это не гарантирует стирания всех мгновенных копий в среде выполнения Go, области подкачки операционной системы, дампах сбоя или носителях информации. В открытом (разблокированном) состоянии приложение удерживает доступный дескриптор DEK, и в это время авторизованные главным приложением API, сторонние плагины, AI/LLM (включая MCP и агентов) могут читать открытое содержимое и использовать поиск внутри блокнота через поддерживаемые специализированные точки входа блокнота; глобальный поиск, семантический поиск и векторные эмбеддинги не участвуют. Сервис публикации является явным исключением: читатели публикации и анонимные посетители никогда не могут перечислять или читать зашифрованные блокноты независимо от того, разблокирован ли блокнот, и ни пароль публикации, ни настройки видимости, ни `publishAccess.json` не могут переопределить это правило. CLI ядра также отклоняет зашифрованные блокноты и их исходные файлы независимо от блокировки или разблокировки. Шифрование защищает «данные в покое» и «недостижимость через поддерживаемые точки входа после блокировки», но не защищает от «видимости для авторизованных главным приложением вызывающих сторон после разблокировки». Поэтому во время разблокировки его следует рассматривать как «обычный блокнот, используемый в главном приложении» и блокировать сразу после использования.

Защищено (шифротекст на диске):

- Текст документов `.sy` (зашифрован)

- Бинарные файлы assets (зашифрованы)

- Имена файлов assets (обезличены, исходное имя хранится зашифрованным)

- Иконка блокнота, вес сортировки в списке и способ сортировки (хранятся в аутентифицированном шифротексте `BoxCrypt.Metadata`)

- Файлы баз данных (столбцы/строки/значения cell/конфигурация представлений/снимки содержимого, зашифрованы)

- База SQLite content (blocks/FTS/attributes/refs, шифрование SQLCipher)

- База SQLite blocktree (метаданные дерева блоков: ID/путь/заголовок, шифрование SQLCipher)

- Файлы .sy и баз данных в каталоге истории (шифротекст хранится как есть)

Не защищено:

- MasterSalt/KEKVerifier в `conf.json` (по проекту могут быть в открытом виде: salt не секретен, verifier является шифротекстом)

- BoxConf.WrappedDEK (шифротекст, требует KEK для раскрытия)

- Выведенные значения DEK, мгновенные копии открытого текста, область подкачки, образ гибернации или дампы сбоя, которые могут создаваться процессом и операционной системой; блокировка гарантирует только отзыв управляемых дескрипторов ключей и максимально возможную очистку контролируемых приложением кэшей

- Ещё не очищенные экспорты открытого текста в `temp/`; к ним имеют доступ API файлов администратора, API архивов, доверенные плагины и локальные процессы

- Поле content индекса истории (остаётся пустым, не хранит ни открытый текст, ни шифротекст)

- Утечка метаданных (шифрование не скрывает следующую информацию): количество файлов, структура каталогов, размер файлов, время модификации (mtime), расширение файла asset, временная метка blockID. Хотя имя файла asset зашифрованного блокнота обезличено как `uuid-blockID.ext`, расширение видимо; старый шифротекст на стороне синхронизации / в исторических снимках также хранится каждой стороной хранения самостоятельно, поэтому зашифрованный блокнот не может отозвать их копии

Защита API:

- `/api/file/*`: запрещает доступ к любым файлам в постоянном каталоге зашифрованного блокнота (не только .sy), чтобы избежать утечки шифротекста или записи в обход слоя шифрования; `temp/` рабочего пространства остаётся доступным

- Сервис публикации: `RoleReader` и `RoleVisitor` никогда не имеют доступа к зашифрованным блокнотам и их документам, блокам, представлениям атрибутов и ресурсам; состояние разблокировки и конфигурация доступа к публикации не изменяют этот результат

- CLI ядра: отклоняет команды, нацеленные на зашифрованный блокнот или ID блока, а также прямые пути в `<рабочее пространство>/data/<ID зашифрованного блокнота>/`; не может использоваться для разблокировки, чтения, записи, экспорта или работы с данными зашифрованного блокнота

### Модель угроз и область безопасности

Данная функция защищает конфиденциальность данных в покое и недоступность блокнота через поддерживаемые точки входа после блокировки. Проект исходит из того, что злоумышленник может получить текущий или исторический шифротекст из рабочего пространства, стороны синхронизации или носителя резервного копирования, но не знает мастер-пароль и не может контролировать работающее приложение или операционную систему во время разблокировки пользователем. AES-GCM обеспечивает только конфиденциальность, целостность и аутентификацию контекста источника отдельного зашифрованного объекта и не обеспечивает доступность, свежесть версии, защиту от отката или удаление уже сохранённых копий шифротекста.

Следующие сценарии не входят в область защиты данной функции, о чём интерфейс и руководство пользователя должны чётко предупреждать:

- Во время разблокировки блокнота авторизованные главным приложением API, плагины, MCP, AI/LLM, а также локальные злоумышленники, способные читать память процесса приложения, могут получить открытый текст; читатели и анонимные посетители сервиса публикации к этой области не относятся и всегда отклоняются

- Локальные процессы, способные читать файлы рабочего пространства, API файлов администратора и доверенные плагины могут прочитать ещё не очищенные временные экспорты открытого текста; временный каталог не является границей контроля доступа

- Пользователь сам несёт ответственность за защиту файлов, экспортированных им явно, буфера обмена, скриншотов, распечаток, содержимого, переданного третьим лицам, а также файлов открытого текста, сохранённых вне рабочего пространства

- Раздел подкачки операционной системы, образы гибернации, дампы сбоя, снимки файловой системы и вредоносное ПО не получают абсолютной защиты за счёт «очистки памяти»; блокировка выполняет лишь максимально возможную очистку в пределах, контролируемых приложением

- Сервис синхронизации или владелец резервной копии могут сохранять, удалять, заменять или откатывать шифротекст; эти действия могут вызвать отказ в обслуживании или откат данных, но без знания мастер-пароля не позволяют расшифровать действительный шифротекст

- Родительский каталог не входит в AAD, поэтому злоумышленник, способный записывать шифротекст рабочего пространства, может переместить действительный шифротекст с неизменным базовым именем файла внутри одного блокнота, и приложение примет новый родительский каталог как текущую иерархию документа; содержимое, блокнот, тип объекта и стабильный ID объекта по-прежнему аутентифицируются, но сама иерархия родительских каталогов не обеспечена криптографической целостностью

«После блокировки остаётся только шифротекст» означает лишь то, что постоянные данные зашифрованного блокнота остаются зашифрованными, а управляемые временные файлы, кэши и дескрипторы ключей прошли максимально возможную очистку; это не гарантирует отсутствия в `temp/` рабочего пространства открытого текста, оставшегося из-за сбоя, блокировки файла или ошибки прав доступа, не включает файлы, явно экспортированные пользователем во внешние расположения, и не обещает стирания мгновенных или исторических копий, уже сохранённых процессом, операционной системой или нижележащими носителями информации.

### Формат шифротекста, ключей и баз данных

Формат постоянного хранения разделён на уровни, и нельзя смешивать глобальную конфигурацию KDF, обёртку ключей и инкапсуляцию каждого объекта данных:

1. Инкапсуляция объекта данных: каждый объект `.sy`, ресурса и определения базы данных содержит как минимум идентификатор или версию формата, идентификатор алгоритма, 96-битный nonce, сгенерированный CSPRNG операционной системы, шифротекст и тег аутентификации. AAD текущего формата детерминированно конструируется как `домен формата + boxID + тип объекта + стабильный ID объекта` и не включает родительский каталог или абсолютный путь; стабильным ID объекта `.sy` является каноническое базовое имя файла `<rootID>.sy`, для ресурса используется обезличенное базовое имя файла на диске, для определения базы данных — avID, для фиксированного одиночного файла — версионированный константный ID. Исходное имя ресурса сохраняется как аутентифицированные зашифрованные метаданные внутри того же контейнера ресурса. После расшифровки необходимо проверить совпадение внутреннего ID объекта с ID объекта AAD и отклонять дублирующиеся ID объектов внутри одного блокнота. Сбой источника случайности должен прерывать запись. Уникальность nonce опирается на вероятностную гарантию: текущая реализация не имеет постоянного счётчика вызовов ключа по назначению, разделяемого между перезапусками, устройствами и восстановлением резервных копий, и не может принудительно ограничивать масштаб вызовов за весь жизненный цикл ключа. Это текущее ограничение, которое не означает возможность неограниченного безопасного использования; последующее внедрение принудительного ограничения потребует версионированной межустройственной схемы жизненного цикла ключей и восстановления с сохранением доступа к существующим данным. Тег аутентификации не может постфактум выявить уже произошедшее повторное использование nonce, поэтому нельзя заявлять, что такое повторное использование будет автоматически обнаружено сбоем аутентификации

2. Глобальные ключи и метаданные обёртки: `NotebookCrypto` хранит алгоритм KDF, параметры, MasterSalt, формат verifier, версию обёртки KEK и версию HMAC резервной копии; `BoxConf.WrappedDEK` хранит обёртку DEK каждого блокнота. Они не сохраняются повторно с каждым объектом данных

3. Разделение по назначению: DEK каждого блокнота через фиксированные разделители доменов выводит подключи для содержимого файлов, ресурсов, определений баз данных, content SQLCipher и blocktree SQLCipher. Метаданные имени ресурса и фрагменты содержимого используют общий подключ ресурса и изолируются разными суффиксами AAD; не требуется выводить отдельный подключ для каждого типа объекта. KEK может напрямую использоваться для verifier, обёртки DEK и HMAC резервной копии, и эти назначения изолируются разными алгоритмами, версионированным AAD или форматом аутентифицируемых данных; нельзя ошибочно относить аутентификацию WrappedDEK к домену DEK

4. Информация о совместимости баз данных: версия SQLCipher, параметры cipher, тип индекса и версия schema хранятся в таблице encrypted_index_meta, аутентифицированной SQLCipher, и должны проверяться перед повторным использованием индекса. Индексы content и blocktree являются перестраиваемыми; при отсутствии информации о совместимости, несовместимости параметров или сбое открытия индекс закрывается, и после прохождения аутентификации ключей блокнота, метаданных и всех исходных документов оба индекса могут быть созданы заново и заполнены при монтировании. При сбое аутентификации исходных документов исходный шифротекст и остаточный индекс сохраняются с выдачей ошибки; перестроение не должно понижать параметры cipher или откатываться к открытому SQLite

5. Переименование и стабильность формата: текущий формат документов, конструирующий AAD из стабильного ID объекта, заморожен как база совместимости. Уже записанные ресурсы `SYAE` без поля версии продолжают считываться по старому формату, и нельзя требовать от пользователя удаления или пересоздания вложений из-за обновления до версии 2; запись единообразно использует версию 2, а чтение не принуждает к миграции на диске или исторических снимков. Изменение только родительского каталога не переупаковывает содержимое, и лишь при изменении стабильного базового имени файла выполняется аутентифицированная расшифровка по старому базовому имени и создание новой упаковки по новому базовому имени. Будущие изменения конверта, семантики AAD или способа вывода ключей должны использовать явную версию формата, сохранять старый путь аутентифицированного чтения либо предоставлять восстанавливаемую миграцию перед удалением чтения старой версии. Миграция должна сначала аутентифицировать исходные данные, сохранять исходные данные и совпадающие материалы восстановления и оставаться восстанавливаемой после сбоя или прерывания; нельзя решать несовместимость форматов путём сброса MasterSalt, отбрасывания ключей или удаления данных. Неизвестный формат, повреждение или сбой аутентификации должны сохранять исходный файл и сообщать об ошибке без отката к открытому тексту или обхода аутентификации. Каждое изменение формата должно проверяться на образцах поддерживаемых старых форматов по затронутым путям чтения, экспорта, истории, резервного копирования и восстановления

Spec `7` документа добавляет полный строчный источник `DocumentTitle` внутрь аутентифицированного открытого текста `.sy`, не изменяя инкапсуляцию шифротекста, AAD, вывод ключей, MasterSalt или резервную копию ключей. Читатель сначала аутентифицирует существующую инкапсуляцию, затем проверяет версию источника и узлы. Старые документы без этого поля сохраняют буквальный заголовок открытого текста и продолжают считываться без перезаписи текущего файла или исторических снимков. Неизвестный или искажённый источник заголовка должен вызывать ошибку с сохранением исходного шифротекста; нельзя заменять нечитаемый источник сводкой. Ресурсы заголовка, исходящие ссылки, обратные ссылки и производный кэш текста якоря по-прежнему соблюдают существующие границы доступа и индексации блокнота и не пересекают границу, даже если одновременно разблокированы другие зашифрованные блокноты. История, резервные копии, синхронизация и восстановление сохраняют полный источник и совпадающие материалы восстановления. Просмотр старой истории не принуждает к миграции; откат сначала аутентифицирует источник истории, затем сериализует восстановленное дерево по существующим правилам целевой инкапсуляции. Подробнее см. [Формат `.sy`](SY-FORMAT.zh-CN.md#11-完整文档标题源spec-7).

Основная база данных SQLCipher, WAL, SHM, журнал отката, временные файлы и резервные копии являются защищаемыми объектами, должны размещаться в контролируемых каталогах и использовать соответствующие ключи назначения. Блокировка, аварийное восстановление и исторические снимки должны перечислять эти сопутствующие файлы; незашифрованные страницы SQLite, результаты запросов или диагностические дампы не должны записываться в глобальный временный каталог.

### Стратегия резервного копирования, восстановления и метаданных

`data-crypto-backup.json` является материалом восстановления, а не секретом. Файл имеет версию формата, ID резервной копии, время создания, дайджест содержимого и HMAC на основе KEK; после вывода KEK из мастер-пароля отсутствие или несовпадение HMAC должно отклонять восстановление и не может пропускаться как путь совместимости. Восстановление не должно незаметно перезаписывать включённую конфигурацию. Резервная копия с недействительным форматом или не совпадающая с существующим зашифрованным блокнотом переходит в состояние ошибки вместо генерации нового MasterSalt.

При смене пароля WrappedDEK существующих блокнотов повторно оборачиваются новым KEK, а предыдущие KEK и текущий старый KEK после дедупликации по отдельности аутентифицированно шифруются новым KEK и версионированным AAD `siyuan:history-kek:v1` и записываются в `HistoryKEKs`. Это поле совместно защищается дайджестом и HMAC глобальной резервной копии и восстанавливается вместе со списком миграции смены пароля; даже удаление последнего мигрируемого блокнота не должно отбрасывать исторические ключи, для которых ещё не завершено переключение резервной копии. При восстановлении и разблокировке сначала пробуется текущий KEK, затем исторические KEK, развёрнутые из аутентифицированной конфигурации, после использования они обнуляются, а открытый KEK не кэшируется. Каталоги исторического шифротекста не требуют перезаписи, а текущая резервная копия и текущий пароль могут восстановить обёртки, оставшиеся от предыдущих смен пароля, включая каталоги, восстановленные позже с других устройств или из автономных снимков.

Весь цикл смены пароля выполняется последовательно с синхронизацией и чтением снимков репозитория. Пока миграция не завершена, запрещено ручное создание снимков и синхронизация с возможностью загрузки. Восстановление только с загрузкой сохраняет существующую локальную контрольную точку безопасности, исключает локальный список миграции из текущего индекса сравнения и не может заменять или удалять этот список. К загруженным обратно блокнотам сначала повторно применяются обёртки из списка, затем пользователь вводит новый пароль для аутентификации и завершения переключения глобальной резервной копии. Эти меры защиты не изменяют существующий шифротекст и формат восстановления.

Сохранение резервной копии следует существующей семантике записи файлов проекта: глобальный `data-crypto-backup.json` записывается через случайный временный файл в том же каталоге с последующей атомарной заменой, а `notebook-crypto-backup.json` каждого блокнота использует обычную запись конфигурации, защищённую блокировкой файла. Ни один из них не даёт дополнительной гарантии долговечности `fsync` файла или каталога при сбое питания; при запуске проверяются структура и дайджест, которые можно проверить без ключа, а при восстановлении после ввода мастер-пароля проверяются HMAC и соответствие обёртки ключей. При повреждении или несовпадении происходит безопасный отказ вместо генерации замещающих ключевых материалов.

HMAC может доказать только то, что содержимое резервной копии не было подделано стороной, не знающей KEK, но не может доказать, что это новейшая версия. В текущем объёме не вводится доверенный внешний монотонный счётчик, поэтому аутентифицированная действительная историческая резервная копия или исторический шифротекст могут пройти проверку; `BackupID` и `CreatedAt` являются лишь информацией для диагностики и ручного сравнения, а не якорем защиты от отката. Процессы синхронизации, истории или восстановления не должны описывать «успешную аутентификацию» как «новейшую» или «доверенный источник»; настоящая защита от отката требует независимого доверенного состояния и выходит за рамки данного проекта.

Сторона синхронизации и автономные резервные копии рассматриваются как хранилища, которые могут быть утеряны, скопированы, откачены, но не позволяют прочитать открытый текст. До ввода мастер-пароля невозможно установить доверенную аутентификацию на основе KEK; поэтому пользователь должен хранить как минимум одну независимую версионированную резервную копию ключей и понимать, что потеря мастер-пароля или всех совпадающих резервных копий MasterSalt необратима. Пока не обработаны зависимости активных блокнотов, истории или локальных снимков, отключение должно отклоняться. После явной проверки и выноса архива шифротекст и ключевые материалы остаются вне активных данных, затем завершается старая конфигурация ключей; окончательное удаление по-прежнему должно выполняться пользователем отдельно. Внешние и удалённые копии невозможно надёжно перечислить, и ответственность за сохранение совпадающей резервной копии ключей для них несёт пользователь.

| Текст документов, значения атрибутов, исходные имена ресурсов, ячейки баз данных, текст индекса | Нет |
| boxID, структура каталогов, количество файлов, размер шифротекста, время модификации, расширения ресурсов, временная информация ID блоков | Да |
| Название блокнота | Да. Список блокнотов и API состояния зашифрованного блокнота сохраняют название при блокировке, чтобы пользователь мог определить, какой блокнот разблокировать, поэтому название блокнота не относится к границе защиты конфиденциальности |
| Иконка, сортировка, заголовки и количество документов, количество связей, теги, закладки, названия истории и снимков | При блокировке по умолчанию не должны раскрываться; если совместимость требует раскрытия, это должно быть поочерёдно указано в данной таблице и в интерфейсе |

### Проектирование безопасности функции истории

```
История файлов:
  Редактирование запускает создание истории → шифротекст .sy копируется в каталог истории как есть
  Автоматическое создание истории перед закрытием/выходом → гарантирует, что история не потеряется, когда таймер не может сработать после блокировки
  Индекс истории → content остаётся пустым (шифротекст не попадает в поисковый индекс)
  Просмотр истории → чтение boxID снимка + типа объекта + стабильного базового имени файла, конструирование исходного AAD из этих трёх параметров для расшифровки (требуется, чтобы блокнот был разблокирован)
  Откат → расшифровка истории по AAD снимка → проверка совпадения ID корневого блока с базовым именем файла → загрузка tree → сериализация восстановленного содержимого через WriteTree и повторная упаковка по целевому базовому имени файла

История удалённых блокнотов:
  Перед удалением → весь каталог копируется в зашифрованном виде в каталог истории
  Восстановление → каталог шифротекста копируется обратно как есть и остаётся закрытым, при разблокировке для проверки WrappedDEK используются совпадающая глобальная резервная копия ключей и мастер-пароль
  Сохранение ключей: активная история блокирует очистку ключей; после проверки и выноса архива история и совпадающие ключи сохраняются вне активных данных, после чего зависимость снимается

История баз данных:
  Создание → файлы баз данных зашифрованного блокнота копируются из каталога уровня блокнота в каталог истории
  Просмотр → расшифровка по зафиксированным в снимке boxID и назначению/идентификатору объекта без использования абсолютного пути каталога истории в качестве AAD
  Откат → файлы баз данных / ресурсы зашифрованного блокнота откатываются в каталог уровня блокнота
```

Родительский путь файла истории в каталоге истории не является составной частью AAD. Каждая запись истории должна в однозначном каноническом формате сохранять `boxID`, тип объекта и стабильное базовое имя файла или идентификатор объекта на момент записи снимка; это может кодироваться фиксированной структурой каталога истории либо записываться метаданными, фиксируемыми вместе со снимком. При изменении только родительского каталога документа контекст AAD остаётся неизменным; при изменении базового имени файла существующая история по-прежнему аутентифицируется и расшифровывается по старому базовому имени. При откате сначала проверяется совпадение шифротекста, базового имени файла и расшифрованного ID объекта, затем выполняется восстановление в целевой родительский каталог; откат документа также нормализует структуру дерева и обрабатывает дублирующиеся ID блоков, поэтому даже при неизменном базовом имени файла восстановленное содержимое сериализуется через WriteTree и создаётся новая упаковка, а исходный шифротекст истории остаётся без изменений. Обратное копирование каталога удалённого блокнота относится к восстановлению в закрытом состоянии и не означает, что текущая резервная копия ключей уже совпала; аутентификация выполняется при разблокировке, а при отсутствии совпадающей резервной копии материалы восстановления можно добавить позже. При отсутствии контекста снимка, недопустимом формате или несовпадении с шифротекстом просмотр и откат должны отклоняться; нельзя разбирать шифротекст как открытый текст или подменять базовое имя снимка текущим базовым именем файла.

Ручная автоматизация баз данных использует формат автоматизации 9 без изменения конверта шифрования, AAD или вывода ключей. Форматы 1–8 по-прежнему аутентифицированно считываются через существующие пути экспорта, истории, резервного копирования и восстановления, а старые клиенты отклоняют формат 9 и не перезаписывают источник. Ручное выполнение удерживает аренду жизненного цикла блокнота во время чтения снимка, подтверждения прав HTTP и фиксации обычных значений полей, но не удерживает блокировку транзакции редактирования во время ожидания сети. При сбое, отмене, истечении снимка или сбое аутентификации исходные значения и шифротекст сохраняются, отмена и повтор используют сохранённый результат без выполнения HTTP-запросов, а кэш открытых HTTP-ответов не сохраняется на диск.

Формат автоматизации 10 сохраняет прежний аутентифицированный конверт хранения и читатели форматов 1–9. Событийные задачи HTTP не сохраняют снимки открытого текста на диск; ожидающие выполнения записи содержат только идентификатор и сводку, действительны в течение пяти минут и требуют активного главного окна, инициировавшего редактирование. Перед чтением или получением данных запрашивается аренда блокнота; заблокированные, повреждённые или не прошедшие аутентификацию источники не могут продолжать выполнение. Редактирование фиксируется до ожидания сети, а результат получения данных атомарно фиксируется как отдельная отменяемая транзакция только пока снимок ещё действителен. Сбой или отмена сохраняют уже сохранённую правку и исходный результат, а повторное воспроизведение не выполняет HTTP.

Ручная поочерёдная автоматизация фиксирует каждую исходную запись и все её межбазовые действия через существующие аутентифицированные транзакции и путь отмены; сбой одной записи сохраняет исходное значение этой записи, а предыдущие успешные результаты остаются сохранёнными. Прогресс в ожидании хранит только ID, сводку правил, счётчики и идентификатор разрешённой области, не удерживая расшифрованный снимок, тело ответа или аренду блокнота. Каждый последующий пакет повторно аутентифицирует текущий источник и проверяет фактическую сессию исходного главного окна; блокировка блокнота очищает прогресс и отменяет активные запросы. Повтор не удаляет существующих читателей, не изменяет ключевые материалы и не откатывается к открытому тексту, не изменяя формат документов, баз данных или конверта шифрования.
