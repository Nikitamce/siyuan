# Спецификация JSON-структуры файлов `.sy` в SiYuan: справочник по чтению и записи

[English](SY-FORMAT.md)

> Базовый уровень канонической записи: Spec `2` для обычных документов, Spec `3` для документов с вкладками, Spec `4` для документов с форматированным текстом в ячейках таблиц, Spec `5` для документов с узлами интеллект-карт, Spec `6` при наличии ASCII `/` в заголовке документа, Spec `7` при наличии полного строчного источника заголовка документа; совместимые средства чтения могут обновлять устаревшие данные или данные без поля `Spec`.
> Проверочные образцы: `20200825162036-4dx365o.sy` (элементы оформления), `20200905090211-2vixtlf.sy` (типы блоков содержимого).
> Все выводы в этом документе проверены на реальных образцах и актуальном исходном коде Lute / ядра SiYuan. Указанные образцы содержат небольшое количество известных устаревших данных; при расхождении между образцами и текущим исходным кодом приоритет имеют правила канонической записи из текущего исходного кода.
> Это руководство описывает открытый `.sy` JSON в обычных блокнотах или расшифрованное AST в разблокированных зашифрованных блокнотах. Однако файлы `.sy` на диске зашифрованных блокнотов представляют собой шифротекст и не могут редактироваться напрямую как JSON.
> Сопутствующий документ: [`WORKSPACE.zh-CN.md`](./WORKSPACE.zh-CN.md) описывает общую структуру рабочей области на диске (организацию блокнотов, родительских/дочерних документов и файлов ресурсов); данный документ посвящён **внутренней** JSON-структуре файла `.sy`.

## 0. Обзор

Открытый файл `.sy` представляет собой дерево Lute AST, сериализованное в JSON. Корневым узлом является `NodeDocument`, а основное содержимое — рекурсивно вложенный массив `Children`. Отдельно поддерживаемой JSON Schema не существует; поэтому источником истины для формата сериализации являются Go-структуры `ast.Node` и `ListData` из Lute. В дереве хранятся AST документа и его IAL, тогда как файлы ресурсов, определения представлений атрибутов и перестраиваемые индексы находятся вне дерева.

## 0.1 Каноническая запись и совместимое чтение

Данное руководство различает формат, который должны генерировать новые средства записи, и исторические данные, которые ядро может допускать и нормализовать:

| Термин | Значение |
|---|---|
| **Обязательно** | Должно присутствовать в новых канонических данных |
| **Опционально** | Может опускаться, если поле пустое или имеет тег `omitempty` |
| **Совместимый ввод** | Исторические или внешние данные, которые средство чтения может принимать, сохранять, исправлять или обновлять по явным правилам совместимости |

Если в конкретном разделе не указано иное, слово «обязательно» в этом документе относится к требованиям канонической записи для новых данных. `dataparser.ParseJSON` является совместимым средством чтения, а не строгим валидатором схемы; например, он может добавлять отсутствующие пустые абзацы, назначать ID блокам без ID и обновлять устаревшие `Spec`.

Каноническая запись открытого `.sy` использует UTF-8 JSON без метки порядка байтов (BOM). Средства чтения дерева блоков и свойств документа в файловой системе допускают наличие одного UTF-8 BOM (`EF BB BF`) в самом начале открытого текста и удаляют его перед проверкой и разбором JSON. В зашифрованных блокнотах такая нормализация выполняется только после успешной аутентифицированной расшифровки; добавлять BOM перед шифротекстом нельзя. При успешном исправлении или сохранении дерева блоков записывается JSON без BOM; снимки только для чтения и запросы свойств оставляют исходный файл без изменений. Повреждённый JSON, неподдерживаемая спецификация документа или ошибка аутентификации по-прежнему должны возвращать ошибку и сохранять исходный файл — совместимость с BOM не обходит эти проверки.

Только корневой узел файла может иметь тип `NodeDocument`. Для исторических файлов с вложенным `NodeDocument` внутри основного текста средство чтения дерева блоков файловой системы преобразует этот узел в вертикальный `NodeSuperBlock`, дополняя стандартными маркерами начала, компоновки (`row`) и конца. Исходный ID блока, свойства (включая исходный заголовок), существующие дочерние блоки и их порядок сохраняются; в пустой вложенный документ добавляется один пустой абзац. Исправление или сохранение файла сохраняет каноническую структуру через существующий аутентифицированный поток записи, снимки только для чтения нормализуют только дерево блоков в памяти, а запросы свойств, читающие только заголовок, оставляют исходный файл без изменений. При переиндексации заменяются соответствующие старые строки индекса вложенного документа из того же источника без удаления реальных документов или записей из других источников. Это исправление использует существующий формат суперблока и не изменяет версию спецификации документа или конверт шифрования.

## 0.5 Когда читать и писать `.sy` напрямую (приоритеты)

SiYuan предоставляет три официальных пути для изменения данных: **HTTP API, MCP, CLI**. **По умолчанию следует отдавать предпочтение им**, поскольку ядро берёт на себя сериализацию AST, назначение ID блоков и синхронизацию двух наборов индексов — индекса дерева блоков (`blocktree.db`, сопоставление ID блоков с путями файлов, от которого зависят ссылки на блоки и хлебные крошки) и индекса полнотекстового поиска (`siyuan.db` + FTS5). Прямое изменение файлов на диске обходит эту логику и поэтому легко приводит к рассинхронизации индексов.

**Читайте и записывайте `.sy` напрямую как JSON только тогда, когда официальные пути неудобны**. Подходящие сценарии:
- Массовая офлайн-миграция (холодная инициализация рабочей области, импорт внешних данных; структуру рабочей области на диске см. в [`WORKSPACE.zh-CN.md`](./WORKSPACE.zh-CN.md))
- Статистика содержимого только для чтения, анализ, пользовательский экспорт / конвертация форматов
- Исправление низкоуровневых структурных проблем (устаревшие файлы, некорректные узлы)
- Программная генерация шаблонов / каркасов

Распределение задач между четырьмя путями:

| Путь | Назначение | Возможности изменения |
|---|---|---|
| **HTTP API** | Онлайн-операции во время выполнения | Наиболее полные: CRUD документов/блоков (`filetree/*`, `block/*`, `transactions`) |
| **MCP** | Набор инструментов LLM | Подмножество онлайн-операций с документами для AI-агентов |
| **CLI** | Пакетная обработка / эксплуатация | Командные задачи импорта, экспорта, синхронизации, SQL и др. |
| **Прямое чтение/запись `.sy`** | Область действия данной спецификации | Офлайн, массовые и низкоуровневые структурные операции |

> ⚠️ После прямого изменения файлов на диске обычно требуется запустить «Перестроить индекс», чтобы заработали поиск и ссылки на блоки. Если SiYuan запущен, предпочтительнее использовать HTTP API, чтобы сериализацией и синхронизацией индексов занималось ядро.
> ⚠️ Не изменяйте напрямую файлы хранения зашифрованных блокнотов. После разблокировки блокнота используйте специализированные API для сохранения согласованности шифрования, аутентификации и изолированных индексов.

## 1. Общая структура

```json
{
  "ID": "20200825162036-4dx365o",
  "Spec": "2",
  "Type": "NodeDocument",
  "Properties": {
    "icon": "1f4f0",
    "id": "20200825162036-4dx365o",
    "title": "排版元素",
    "type": "doc",
    "updated": "20260616224229"
  },
  "Children": [ ... ]
}
```

| Ключ верхнего уровня | Обязателен | Описание |
|---|---|---|
| `ID` | ✅ | ID блока документа, **равен имени файла без `.sy`** |
| `Spec` | ✅ | `"2"` для обычного документа, `"3"` для вкладок, `"4"` для форматированного текста в ячейках таблиц, `"5"` для узлов интеллект-карт, `"6"` при наличии ASCII `/` в заголовке, `"7"` для полного строчного источника заголовка; используется как минимум максимальная версия, требуемая задействованными функциями, без понижения существующей версии |
| `Type` | ✅ | `"NodeDocument"` |
| `Properties` | ✅ | IAL уровня документа, см. §8 |
| `DocumentTitle` | Опционально | Авторитетный строчный источник заголовка, принадлежащий только корневому узлу, требует Spec `7`, см. ниже |
| `Children` | ✅ | Массив дочерних блоков основного содержимого; канонический файл содержит как минимум один блок |

Spec `6` сохраняет обычное строковое представление `Properties.title`; при наличии ASCII `/` в заголовке требуется структурированная адресация документа. Версия функции автоматически включает этот режим адресации, не перезаписывая исходные файлы старых документов ради записи миграции блокнота. Существующие `／`, `%2F`, текст в стиле Markdown и текст HTML-сущностей сохраняют буквальное значение; данная спецификация не включает строчное форматирование в заголовке. Зашифрованные блокноты сначала аутентифицируют существующую обёртку шифротекста, а затем интерпретируют тот же JSON; деривация ключей, AAD и материалы восстановления не изменяются. Требования к защите выпуска и миграции см. в [Заголовки и адресация документов](DOCUMENT-ADDRESSING.zh-CN.md).

### 1.1 Полный источник заголовка документа (Spec 7)

Заголовок с форматированным текстом принадлежит корневому узлу документа и не создаёт блоков основного текста или дополнительных ID блоков. Его авторитетным источником является версионированная обёртка:

```json
"DocumentTitle": {
  "spec": 1,
  "format": "inline-ast",
  "content": "[{\"Type\":\"NodeText\",\"Data\":\"标题 \"},{\"Type\":\"NodeTextMark\",\"TextMarkType\":\"strong\",\"TextMarkTextContent\":\"示例\"}]"
}
```

`content` — это UTF-8 JSON-строка, содержащая массив канонических строчных узлов `.sy`, а не Markdown и не узлы-обёртки абзацев. Нативные текстовые маркеры, изображения и их дочерние маркеры, экранирование, сущности, эмодзи и мягкие переносы строк сохраняют полный набор поддерживаемых атрибутов. Строчные узлы не имеют сохраняемого `ID`; блочные узлы, сырые HTML-узлы, а также неизвестные типы узлов или текстовых маркеров отклоняются. Этот формат не включает синтаксис, отключённый в обычном редакторе. Существующий пустой источник форматированного текста `[]` по-прежнему доступен для чтения. При записи заголовка содержимое, которое можно без потерь свести к обычному тексту (включая пустой заголовок), опускает `DocumentTitle` и сохраняет текст в `Properties.title`; стили, ресурсы, ссылки и встроенные переносы строк продолжают сохранять полный источник. Удаление полного источника не понижает версию спецификации документа, а доступ только для чтения не перезаписывает существующий источник. Редактор заголовка документа запрещает вставку мягких переносов строк и заменяет переносы строк во вставляемом тексте на пробелы. Существующие многострочные источники по-прежнему можно читать и восстанавливать; при экспорте заголовок документа заменяет переносы строк на пробелы без изменения исходных данных. Форматированный текст первичного ключа базы данных сохраняет переносы строк.

`Properties.title` — это производная текстовая сводка для компактного интерфейса, путей и индексов. Видимый текст, альтернативный текст изображений и формулы попадают в сводку, а текст строчных заметок и адреса ресурсов в сводку не попадают. Полный рендеринг и экспорт заголовка используют `DocumentTitle`; нельзя восстанавливать форматированный текст из сводки. Якорный текст динамических ссылок является производным кэшем и не изменяет редактируемую версию исходного содержимого. Ссылки в заголовке относятся к корневому ID документа в обратных ссылках и индексе связей, туда же относятся и ресурсы заголовка. Ни строчные узлы заголовка, ни его временные абзацы не становятся дочерними блоками основного текста.

Документ блокнота использует то же представление заголовка, при этом корневой ID равен ID блокнота. `Properties.custom-sy-notebook-title-source = "document"` означает, что заголовок документа является определяющим, и сохраняется даже после преобразования в обычный текст или пустой заголовок. Имя конфигурации блокнота выводится из текстовой сводки, а при пустой сводке используется текст-заполнитель «Без имени». Редактирование содержимого, экспорт и восстановление должны сохранять это свойство; существующие документы блокнотов, не имеющие ни этого свойства, ни источника форматированного заголовка, продолжают использовать имя блокнота из конфигурации.

Средство чтения проверяет исходную обёртку источника до отказоустойчивого исправления AST. Поля `spec`, `format`, `content` чувствительны к регистру, должны присутствовать и не могут быть null; неизвестные или дублирующиеся поля, невалидный UTF-8, NUL, неподдерживаемые версии, искажённые узлы и превышение лимитов вызывают ошибку. Лимит содержимого — 1 MiB, максимум 8192 узла, максимальная глубина вложенности — 64. Невалидный источник должен сохраняться, его нельзя заменять сводкой или молча исправлять. Документы без `DocumentTitle` продолжают трактовать `Properties.title` как буквальный обычный текст; при открытии Markdown не интерпретируется, а исходный файл не изменяется. Версия существующих документов не понижается. Экспорт `.sy`, история, резервное копирование и восстановление сохраняют полный источник; зашифрованное средство чтения сначала аутентифицирует существующую обёртку шифротекста, а затем выполняет эти проверки.

> ⚠️ Путь к файлу строго соответствует корневому ID: `data/<box>/<...>/<корневой_ID>.sy`. Изменение корневого ID равносильно переименованию файла — AI не должен произвольно менять корневой ID. Полную структуру файловой системы см. в [`WORKSPACE.zh-CN.md`](./WORKSPACE.zh-CN.md).
> Совместимое средство чтения вставит пустой абзац, если `Children` отсутствует или пуст, но новое средство записи должно записывать этот абзац самостоятельно.

## 2. Семантика общих полей (применима к каждому узлу)

| Поле | Тип | Условие наличия | Семантика |
|---|---|---|---|
| `Type` | string | **Обязательно у всех узлов** | Дискриминатор типа, например `"NodeParagraph"` |
| `ID` | string | Обязательно для канонических блочных узлов; может присутствовать у неблочных узлов при совместимом вводе | 22-символьный ID, используемый блоком; каноническое средство записи не добавляет это поле строчным или маркерным узлам |
| `Data` | string | Частично | Исходный текст / HTML / markdown; **может опускаться** (нельзя предполагать обязательное наличие) |
| `Properties` | object | Блоки и некоторые строчные узлы | IAL, `map[string]string`; строчные сценарии включают стилизованный текст, изображения и ячейки таблиц |
| `Children` | array | Контейнеры и составные структурные узлы | Массив дочерних узлов |
| Поля конкретного типа | - | По типу | Например, `HeadingLevel`, `ListData`, `TextMarkType`, `AttributeViewID` |

**Основное правило определения**: `Type` определяет, является ли узел блоком, авторитетной проверкой служит `ast.Node.IsBlock()`; поэтому нельзя судить по наличию `ID`. В канонических данных каждый блок имеет `ID` и соответствующий `Properties.id`, а вновь созданные строчные или маркерные узлы этих полей не имеют. Исторические файлы, созданные из-за старых дефектов, могут содержать ID у неблочных узлов, таких как `NodeCodeBlockCode`, `NodeMathBlockContent` и др. Совместимые средства чтения и редакторы могут очищать эти устаревшие поля `ID` / `Properties.id` в процессе нормализации, но обязаны определять тип узла по `Type` и не могут удалять сам узел только из-за несоответствия `ID` канону.

## 3. Правила ID и временных меток

- **Формат ID**: `YYYYMMDDHHMMSS-xxxxxxx` = 14-значная временная метка + `-` + 7 случайных символов `[a-z0-9]`. Пример: `20210104091228-ttcj9nm`.
- **Уникальность**: каждый вновь сгенерированный ID документа и блока должен быть уникальным во всей рабочей области, а не только в пределах одного файла.
- **Корневой ID** берётся из имени файла и **не** генерируется заново.
- **ID дочерних блоков** генерируются заново в указанном формате; ни в коем случае нельзя копировать буквальные ID из примеров или шаблонов.
- `Properties.updated` использует ту же 14-значную временную метку со значением «время последнего обновления».
- При изменении содержимого или структуры блока следует обновить `Properties.updated` у изменённого блока, его блочных предков, применимых предшествующих заголовков и корневого узла документа.
- При изменении `ID` любого блока необходимо **синхронизировать** `Properties.id`. Его `Properties.updated` не должен быть раньше времени создания, закодированного в новом ID.
- Совместимый исторический ввод может не содержать `updated`; новые данные при канонической записи должны предоставлять это поле для всех блочных узлов.

## 4. Каталог типов узлов

### Блочные узлы (в канонических данных имеют ID)

**Листовые блоки**: `NodeParagraph`, `NodeHeading`, `NodeThematicBreak`, `NodeHTMLBlock`, `NodeCodeBlock`, `NodeMathBlock`, `NodeTable`, `NodeBlockQueryEmbed`, `NodeAttributeView`, `NodeIFrame`, `NodeVideo`, `NodeAudio`, `NodeWidget`, `NodeCustomBlock`

**Контейнерные блоки**: `NodeList`, `NodeListItem`, `NodeBlockquote`, `NodeCallout`, `NodeSuperBlock`, `NodeTabs`, `NodeTabItem`, `NodeMindmap`, `NodeMindmapItem`

### Строчные или маркерные узлы (в канонических данных без ID)

`NodeText`, `NodeTextMark`, `NodeImage`, `NodeKramdownSpanIAL`, `NodeSoftBreak`, `NodeBr`, `NodeBackslash`, `NodeBackslashContent`, `NodeHeadingC8hMarker`, `NodeBlockquoteMarker`, `NodeTaskListItemMarker`, `NodeBang`, `NodeOpenBracket`, `NodeCloseBracket`, `NodeOpenParen`, `NodeCloseParen`, `NodeLinkText`, `NodeLinkDest`, `NodeLinkSpace`, `NodeLinkTitle`, `NodeCodeBlockCode`, `NodeCodeBlockFenceOpenMarker`, `NodeCodeBlockFenceInfoMarker`, `NodeCodeBlockFenceCloseMarker`, `NodeMathBlockContent`, `NodeMathBlockOpenMarker`, `NodeMathBlockCloseMarker`, `NodeSuperBlockOpenMarker`, `NodeSuperBlockLayoutMarker`, `NodeSuperBlockCloseMarker`, `NodeOpenBrace`, `NodeCloseBrace`, `NodeBlockQueryEmbedScript`, `NodeTableHead`, `NodeTableRow`, `NodeTableCell`

> «Листовой блок» означает, что узел не может содержать другие **блочные узлы**; однако он всё равно может иметь структурные строчные дочерние узлы, например в блоках кода, математических блоках и таблицах.
> Указанное выше «в канонических данных без ID» является правилом канонической записи. Явный процесс нормализации может очищать существующий `ID` у совместимых исторических неблочных узлов, но нельзя использовать это поле для определения, является ли узел блоком, и нельзя удалять сам узел на этом основании.
> Типы, запрещённые для канонической записи, включая синтаксис, отключённый в парсере, и семейство узлов `NodeGitConflict`, используемое только для обнаружения, перечислены в §11 и поэтому не включены в этот каталог.

## 5. Подробный разбор типов блоков и готовые примеры

### 5.1 Абзац

```json
{ "Type": "NodeParagraph", "ID": "...", "Properties": { "id": "...", "updated": "..." },
  "Children": [ { "Type": "NodeText", "Data": "Здесь находится пример абзаца." } ] }
```

### 5.2 Заголовок

```json
{ "Type": "NodeHeading", "ID": "...", "HeadingLevel": 2,
  "Properties": { "id": "...", "updated": "..." },
  "Children": [ { "Type": "NodeText", "Data": "Блок заголовка" } ] }
```

- `HeadingLevel` принимает значения `1`–`6`.
- `NodeHeadingC8hMarker` (`Data`, например `"## "`) **опционален**, его наличие или отсутствие одинаково допустимо. При генерации рекомендуется **опускать** его для краткости.
- SiYuan рекомендует **использовать заголовки второго уровня на верхнем уровне основного текста**, а не первого.

### 5.3 Список (ключевой момент: тип различается по `ListData.Typ`)

> **★ Каноническое структурное ограничение списка**: прямыми дочерними узлами `NodeList` могут быть **только** `NodeListItem`, то есть `CanContain` возвращает `NodeListItem == nodeType`. Абзацы, блоки кода, подсписки и любые другие блоки **не могут** быть прямыми дочерними узлами `NodeList` и должны быть предварительно обёрнуты в `NodeListItem`. `dataparser.ParseJSON` не выполняет эту проверку как строгий шаг валидации, поэтому прямые средства записи должны проверять структуру самостоятельно.

```
✅ Правильно                     ❌ Неправильно
NodeList                        NodeList
└─ NodeListItem                  ├─ NodeParagraph        ← Недопустимо
   └─ NodeParagraph              └─ NodeCodeBlock         ← Недопустимо
```

**Вложенный список** правильно записывается через ещё один слой `NodeList` (`NodeListItem` обрабатывается по ветке `CanContain` по умолчанию и не может напрямую содержать другой `NodeListItem`):

```
✅ Правильно                     ❌ Неправильно
NodeList                        NodeList
└─ NodeListItem                  └─ NodeListItem
   ├─ NodeParagraph                 ├─ NodeParagraph
   └─ NodeList  ← Подсписок          └─ NodeListItem  ← Недопустимо
      └─ NodeListItem
         └─ NodeParagraph
```

**Маркированный список** (`Typ` опущен):

```json
{ "Type": "NodeList", "ID": "...", "ListData": {},
  "Properties": { "id": "...", "updated": "..." },
  "Children": [
    { "Type": "NodeListItem", "ID": "...",
      "ListData": { "BulletChar": 42, "Marker": "Kg==" },
      "Properties": { "id": "...", "updated": "..." },
      "Children": [
        { "Type": "NodeParagraph", "ID": "...", "Properties": { "id": "...", "updated": "..." },
          "Children": [ { "Type": "NodeText", "Data": "Пункт списка 1" } ] }
      ] }
  ] }
```

**Нумерованный список** (`Typ: 1`):

```json
{ "Type": "NodeList", "ID": "...", "ListData": { "Typ": 1 },
  "Properties": { "id": "...", "updated": "..." },
  "Children": [
    { "Type": "NodeListItem", "ID": "...",
      "ListData": { "Typ": 1, "Tight": true, "Start": 1, "Delimiter": 46, "Padding": 3, "Marker": "MS4=", "Num": 1 },
      "Properties": { "id": "...", "updated": "..." },
      "Children": [
        { "Type": "NodeParagraph", "ID": "...", "Properties": { "id": "...", "updated": "..." },
          "Children": [ { "Type": "NodeText", "Data": "Пункт списка 1" } ] }
      ] }
  ] }
```

**Список задач** (`Typ: 3`); каждый `NodeListItem` начинается с `NodeTaskListItemMarker`:

```json
{ "Type": "NodeList", "ID": "...", "ListData": { "Typ": 3 },
  "Properties": { "id": "...", "updated": "..." },
  "Children": [
    { "Type": "NodeListItem", "ID": "...",
      "ListData": { "Typ": 3, "Tight": true, "BulletChar": 45, "Padding": 2, "Marker": "LQ==", "Num": -1 },
      "Properties": { "id": "...", "updated": "..." },
      "Children": [
        { "Type": "NodeTaskListItemMarker", "TaskListItemChecked": true, "TaskListItemMarker": 88 },
        { "Type": "NodeParagraph", "ID": "...", "Properties": { "id": "...", "updated": "..." },
          "Children": [ { "Type": "NodeText", "Data": "Задача 1" } ] }
      ] }
  ] }
```

### 5.4 Полный разбор полей `ListData`

| Поле | Тип (в коде) | Представление в JSON | Описание |
|---|---|---|---|
| `Typ` | int | Число | **Дискриминатор типа списка**: опущено — маркированный, `1` — нумерованный, `3` — список задач |
| `Tight` | bool | Булево | Компактный режим (без пустых строк); опционально |
| `BulletChar` | byte | Число | **ASCII-код** маркера маркированного списка / списка задач (`42`=`*`, `45`=`-`) |
| `Delimiter` | byte | Число | ASCII-код разделителя нумерованного списка (`46`=`.`) |
| `Start` | int | Число | Начальный номер нумерованного списка |
| `Num` | int | Число | Порядковый номер данного элемента; для маркированных и списков задач обычно опущен или `-1` |
| `Padding` | int | Число | Величина отступа; опционально |
| `MarkerOffset` | int | Число | Смещение отступа маркера; опционально |
| `Checked` | bool | Булево | Совместимые метаданные, выводимые при разборе маркера задачи; не является агрегированным значением всего списка, может опускаться |
| `Marker` | []byte | **Строка base64** | **base64** исходного текста маркера; может содержать разделитель (`"MS4="`=`1.`) или не содержать (`"MQ=="`=`1`) |

> Ключевое отличие: `BulletChar` / `Delimiter` в коде имеют тип `byte` и в JSON представлены числами ASCII-кодов; `Marker` в коде имеет тип `[]byte` и в JSON представлен строкой base64. Поля `Marker` / `BulletChar` / `Delimiter` имеют `omitempty` и могут опускаться.

### 5.5 Маркер задачи

Отметка с помощью `X`:

```json
{ "Type": "NodeTaskListItemMarker", "TaskListItemChecked": true, "TaskListItemMarker": 88 }
```

Пробел для неотмеченного состояния:

```json
{ "Type": "NodeTaskListItemMarker", "TaskListItemMarker": 32 }
```

Любой непробельный маркер, например `!`, также означает отмеченное состояние и сохраняет свой исходный байт:

```json
{ "Type": "NodeTaskListItemMarker", "TaskListItemChecked": true, "TaskListItemMarker": 33 }
```

`TaskListItemMarker` имеет тип Go `byte`, поэтому в JSON хранится число его ASCII-кода. Текущий рендеринг сначала читает это поле, а при совместимости со старыми данными откатывается к `TaskListItemChecked`. Когда AST разбирается напрямую из Markdown, поле `Data` может присутствовать, например `"[X]"`; но данные `.sy`, сгенерированные редактором, обычно его опускают, поэтому `Data` нельзя считать авторитетным источником состояния задачи.

### 5.6 Блок цитаты

```json
{ "Type": "NodeBlockquote", "ID": "...", "Properties": { "id": "...", "updated": "..." },
  "Children": [
    { "Type": "NodeBlockquoteMarker", "Data": "> " },
    { "Type": "NodeParagraph", "ID": "...", "Properties": { "id": "...", "updated": "..." },
      "Children": [ { "Type": "NodeText", "Data": "Текст цитаты" } ] }
  ] }
```

> `NodeBlockquoteMarker.Data` может быть `">"` или `"> "` — оба варианта допустимы.

### 5.7 Блок подсказки (Callout / GFM Alert)

```json
{ "Type": "NodeCallout", "ID": "...",
  "CalloutType": "NOTE", "CalloutTitle": "Note", "CalloutIcon": "✏️",
  "Properties": { "id": "...", "updated": "..." },
  "Children": [ { "Type": "NodeParagraph", "ID": "...", "Properties": { "id": "...", "updated": "..." },
    "Children": [ { "Type": "NodeText", "Data": "Текст подсказки" } ] } ] }
```

| `CalloutType` | `CalloutTitle` | `CalloutIcon` |
|---|---|---|
| `NOTE` | `Note` | `✏️` |
| `TIP` | `Tip` | `💡` |
| `IMPORTANT` | `Important` | `❗` |
| `WARNING` | `Warning` | `⚠️` |
| `CAUTION` | `Caution` | `🚨` |

В таблице выше перечислены пять встроенных типов и их значения по умолчанию; также поддерживаются пользовательские `CalloutType`, заголовок и иконка. `CalloutIconType: 0` означает, что `CalloutIcon` является прямым символом эмодзи; это значение по умолчанию, и оно опускается из-за `omitempty`. `CalloutIconType: 1` означает, что `CalloutIcon` является путём к пользовательской иконке.

### 5.8 Суперблок (вложенный, трёхмаркерная обёртка)

```json
{ "Type": "NodeSuperBlock", "ID": "...", "Properties": { "id": "...", "updated": "..." },
  "Children": [
    { "Type": "NodeSuperBlockOpenMarker" },
    { "Type": "NodeSuperBlockLayoutMarker", "Data": "col" },
    { "Type": "NodeSuperBlock", "ID": "...", "Properties": { "id": "...", "updated": "..." }, "Children": [ ... Вложенный суперблок с Data "row" ... ] },
    { "Type": "NodeSuperBlockCloseMarker" }
  ] }
```

> `NodeSuperBlockLayoutMarker.Data` может быть только `"row"` (вертикальный) или `"col"` (горизонтальный). Канонический суперблок содержит маркер начала, маркер компоновки, как минимум один блок содержимого и маркер конца, то есть минимум четыре дочерних узла. Он может содержать несколько блоков содержимого и быть вложенным, вмещая обычные блоки содержимого, включая сам себя, но не может напрямую содержать элементы вкладок.

### 5.9.1 Контейнер вкладок и элемент вкладки (Spec 3)

И `NodeTabs`, и `NodeTabItem` являются реальными контейнерными блоками с независимыми `ID`, `Properties.id` и `Properties.updated`. Контейнер вкладок вмещает только элементы вкладок; элемент вкладки вмещает обычные блоки содержимого и вложенные контейнеры вкладок, причём каждая вкладка содержит как минимум один блок основного текста (для пустого текста используется пустой абзац). Отдельный элемент вкладки служит только фрагментом редактирования и не может быть прямым дочерним узлом документа.

```json
{
  "Type": "NodeTabs",
  "ID": "20260905120000-tabs001",
  "Properties": {"id": "20260905120000-tabs001", "updated": "20260905120000", "tabs-active-id": "20260905120000-item001", "tabs-position": "left"},
  "Children": [{
    "Type": "NodeTabItem",
    "ID": "20260905120000-item001",
    "TabItemTitle": "**Пример**",
    "Properties": {"id": "20260905120000-item001", "updated": "20260905120000"},
    "Children": [{"Type": "NodeParagraph", "ID": "20260905120000-body001", "Properties": {"id": "20260905120000-body001", "updated": "20260905120000"}}]
  }]
}
```

`TabItemTitle` — опциональный строчный Markdown, использующий то же представление строчных текстовых маркеров, что и `CalloutTitle`, и не сохраняемый как отдельный дочерний блок. Допускаются пустые и повторяющиеся заголовки. Массив дочерних узлов определяет порядок. `tabs-active-id` указывает на ID прямого дочернего элемента вкладки; при отсутствии или недействительности откатывается к первой вкладке. `tabs-position` принимает только `top` (по умолчанию) и `left`. Оба свойства сохраняются и синхронизируются; простое переключение выбранной вкладки не изменяет время модификации основного текста. При пересоздании ID блоков необходимо также сопоставить ID выбранного элемента и внутренние ссылки в заголовке.

Документ, содержащий узлы вкладок, должен использовать как минимум `Spec: "3"`; форматированный текст в ячейках таблиц требует минимум Spec 4, узлы интеллект-карт — минимум Spec 5, наличие ASCII `/` в заголовке документа — минимум Spec 6, полный строчный источник заголовка — минимум Spec 7, обычные документы сохраняют Spec 2. После удаления функции версия не понижается. Перед передачей JSON в отказоустойчивый парсер сначала прочитайте исходный `Spec` корня, чтобы избежать очистки содержимого неизвестных узлов; нельзя исправлять и записывать обратно неподдерживаемые версии.

Внутренний Markdown использует `::: tabs` для начала группы вкладок, `@tab <строчный_заголовок>` для начала элемента вкладки и `@tab:active <строчный_заголовок>` для обозначения выбранного элемента. Открывающее ограждение содержит не менее трёх двоеточий, между двоеточиями и `tabs` требуется пробел или табуляция (канонический вывод использует один пробел). У элемента вкладки нет отдельного закрывающего маркера; вся группа закрывается отдельной строкой с закрывающим ограждением с тем же количеством двоеточий, что и у открывающего. Внешнее ограждение должно быть длиннее внутреннего, отступы опциональны; канонический вывод вычисляет длину ограждения по глубине вложенности без дополнительного отступа содержимого вкладок. Старый синтаксис `:::tabs`, `:::tab` больше не распознаётся, но существующая структура узлов вкладок `.sy` сохраняется.

IAL элемента вкладки располагается на следующей строке после маркера заголовка без пустой строки между ними, после чего отделяется от основного текста пустой строкой. IAL всего контейнера группы располагается после закрывающего ограждения, а IAL блоков основного текста — после соответствующих блоков. При импорте первый действительный маркер `@tab:active` определяет `tabs-active-id`, имея приоритет над значением в IAL группы; при отсутствии маркера выбора сохраняется действительный `tabs-active-id`, а при его отсутствии или недействительности происходит откат к первой вкладке. Вложенные группы сохраняют выбор независимо. Маркеры внутри блоков кода сохраняются буквально; буквальные маркеры в начале строки основного текста экранируются с помощью `\@tab` или `\@tab:active`. Стандартный Markdown экспортирует абзацы заголовков и основное содержимое всех вкладок; HTML может быть расширен до интерактивных вкладок, а печать, PDF и Word отображают все вкладки. Полную спецификацию см. в [Блок вкладок](TAB-BLOCK.zh-CN.md).

### 5.9.2 Контейнер и узел интеллект-карты (Spec 5)

`NodeMindmap` вмещает только `NodeMindmapItem`. Узел интеллект-карты может вмещать обычные блоки содержимого и вложенный `NodeMindmap`, но не может напрямую вмещать `NodeList`, `NodeListItem`, другой `NodeMindmapItem`, `NodeDocument` или `NodeFootnotesDef`. Оба новых типа имеют собственные независимые ID блоков и используют `ListData` для хранения нумерации и маркеров задач. Новые интеллект-карты используют отдельные типы узлов и не требуют `custom-sy-list-mindmap="1"`; при открытии редактируемого документа существующие списочные блоки с этим атрибутом обновляются с сохранением ID блоков и метаданных. Содержимое только для чтения и историческое содержимое по-прежнему может читаться в старом формате. Стандартный Markdown экспортирует как список, а `.sy` JSON сохраняет отдельные типы узлов.

### 5.10 Блок кода (четырёхсегментная структура, только с ограждением)

```json
{ "Type": "NodeCodeBlock", "ID": "...", "IsFencedCodeBlock": true,
  "CodeBlockFenceChar": 96, "CodeBlockFenceLen": 3,
  "CodeBlockOpenFence": "YGBg", "CodeBlockInfo": "Z28=", "CodeBlockCloseFence": "YGBg",
  "Properties": { "id": "...", "updated": "..." },
  "Children": [
    { "Type": "NodeCodeBlockFenceOpenMarker", "Data": "```", "CodeBlockFenceLen": 3 },
    { "Type": "NodeCodeBlockFenceInfoMarker", "CodeBlockInfo": "Z28=" },
    { "Type": "NodeCodeBlockCode", "Data": "package main\n...\n" },
    { "Type": "NodeCodeBlockFenceCloseMarker", "Data": "```", "CodeBlockFenceLen": 3 }
  ] }
```

Ключевые моменты:

- `NodeCodeBlockCode` хранит содержимое кода (записывается в `Data`, исходный текст, `\n` экранирован) и является строчным дочерним узлом `NodeCodeBlock`.
- Внешние маркеры ограждения (Open/Info/Close) также являются строчными дочерними узлами.
- `CodeBlockInfo` — это **имя языка в base64** (`"Z28="` = `go`). Шесть полей родительского узла (`IsFencedCodeBlock` / `CodeBlockFenceChar` / `CodeBlockFenceLen` / `CodeBlockOpenFence` / `CodeBlockInfo` / `CodeBlockCloseFence`) имеют тег `omitempty` и могут опускаться по мере необходимости; более новые файлы `.sy` обычно содержат только `"IsFencedCodeBlock": true`.
- Текущая конфигурация Markdown в SiYuan отключает блоки кода с отступом (`SetIndentCodeBlock(false)`); новые канонические блоки кода используют структуру с ограждением.

### 5.12 Блоки HTML / IFrame / Widget / Video / Audio (листья, содержимое в `Data` верхнего уровня)

```json
{ "Type": "NodeHTMLBlock", "ID": "...", "Data": "<div>\n<ruby>你<rt>nǐ</rt>...</div>", "Properties": { "id": "...", "updated": "..." } }
{ "Type": "NodeIFrame", "ID": "...", "Data": "<iframe src=\"...\"></iframe>", "Properties": { "id": "...", "updated": "..." } }
{ "Type": "NodeWidget", "ID": "...", "Data": "<iframe src=\"/widgets/example\" data-subtype=\"widget\"></iframe>", "Properties": { "id": "...", "updated": "..." } }
{ "Type": "NodeVideo", "ID": "...", "Data": "<video controls src=\"assets/x.mp4\"></video>", "Properties": { "id": "...", "updated": "..." } }
{ "Type": "NodeAudio", "ID": "...", "Data": "<audio controls src=\"assets/x.wav\"></audio>", "Properties": { "id": "...", "updated": "..." } }
```

> Эти пять типов узлов **не имеют `Children`**; содержимое HTML после экранирования JSON записывается напрямую в `Data` верхнего уровня.

### 5.13 Таблица

```json
{ "Type": "NodeTable", "ID": "...", "TableAligns": [0, 0, 0],
  "Properties": { "id": "...", "updated": "...", "colgroup": "||" },
  "Children": [
    { "Type": "NodeTableHead", "Data": "thead", "Children": [
      { "Type": "NodeTableRow", "Data": "tr", "Children": [
        { "Type": "NodeTableCell", "Data": "th", "Children": [ { "Type": "NodeText", "Data": "Заголовок" } ] }
      ] }
    ] },
    { "Type": "NodeTableRow", "Data": "tr", "Children": [
      { "Type": "NodeTableCell", "Data": "td", "Children": [ { "Type": "NodeText", "Data": "Ячейка" } ] }
    ] }
  ] }
```

- Фиксированная иерархия вложенности: `NodeTable > NodeTableHead/NodeTableRow > NodeTableCell > строчные узлы`.
- `TableAligns`: массив int выравнивания для каждого столбца, `0` — по умолчанию, `1` — по левому краю, `2` — по центру, `3` — по правому краю.
- `Data` (`thead`/`tr`/`th`/`td`) в компактных файлах **может опускаться**.
- `Properties.colgroup` использует `|` для разделения строк CSS-стилей каждого столбца; пустой сегмент означает отсутствие явного стиля у столбца.
- Опциональное свойство таблицы `Properties.caption` хранит HTML заголовка таблицы.
- `NodeTableCell` может использовать `Properties.colspan`, `Properties.rowspan` и `Properties.style` для хранения объединённых ячеек и состояния стилей ячейки.
- `NodeTableRow` может использовать `Properties.style` (например, `height: 80px;`) для задания минимальной высоты строки; при отсутствии высоты строка по-прежнему компонуется автоматически по содержимому. Внутренний Kramdown сохраняет стиль строки с помощью специального IAL `{: row-style="..."}` после последней вертикальной черты строки; экспорт обычных таблиц в стандартный Markdown опускает эту информацию о вёрстке. Старые документы без стилей строк сохраняют совместимость; при редактировании в старых клиентах новые стили строк могут быть отброшены.

Ячейки, содержащие форматированное блочное содержимое, дополнительно несут `"TableCellRich": {"spec": 1, "format": "kramdown", "content": "- first\n- second"}`. Это исходное содержимое является авторитетными данными; `Children` остаётся строчной проекцией, содержащей читаемые маркеры списков и переносы строк. Внутренние абзацы, списки, код и формулы не становятся блоками документа и не имеют сохраняемых ID блоков. Изображения, ссылки на существующие блоки и поддерживаемое строчное форматирование сохраняются в проекции для индексации и обработки ресурсов. Таблицы с форматированным текстом сохраняют `Properties.custom-sy-table-rich = "1"`; даже если во всех форматированных ячейках осталось только строчное содержимое или они пусты, обновления BlockDOM должны сохранять этот маркер, чтобы средства записи, пропускающие исходное содержимое, не заменили тихо таблицу с форматированным текстом.

Внутри фрагмента поддерживаются только абзацы, заголовки, списки, цитаты, обычный код и формулы. Вложенные таблицы, базы данных, суперблоки, вкладки, блоки подсказок, встроенные запросы, исполняемые диаграммы, медиа, виджеты и HTML-блоки не поддерживаются. BlockDOM упаковывает исходное содержимое в UTF-8 JSON с использованием URL-безопасного Base64 без заполнения и сохраняет в атрибуте `data-sy-table-cell-rich` ячейки. Внутренний Kramdown использует соответствующий IAL ячейки `table-cell-rich`; ни одно из этих представлений не является стандартным форматом обмена Markdown.

Средство чтения сначала проверяет версию и содержимое исходных данных, а затем перестраивает проекцию. При отсутствии, значении null, неизвестном поле или ошибке формата в обёртке должна выдаваться ошибка, а неподдерживаемый ввод должен оставаться без изменений. Сохранённые обычные ячейки не имеют этой обёртки, поэтому текст в них нельзя повторно интерпретировать как Markdown. При простом открытии ячейки или редактировании обычного строчного содержимого существующее представление сохраняется. При первом добавлении блочного содержимого создаётся обёртка форматированного текста, а `Spec` документа повышается до `4`. Существующая обёртка форматированного текста сохраняется даже после того, как содержимое становится чисто строчным или пустым, версия документа не понижается. Стандартный Markdown представляет форматированную ячейку с помощью HTML, сохраняющего блочную структуру внутри одной физической строки, кодируя вертикальные черты и переносы строк в коде в виде символьных ссылок без внутренней обёртки исходного содержимого. При импорте и вставке внешнего Markdown поддерживаемые HTML-структуры блоков и явные маркеры списков задач в начале восстанавливаются в существующую обёртку форматированного текста. Экранированные маркеры, строчный код, а также неподдерживаемый или некорректный HTML остаются обычным содержимым ячейки. Экспорт в HTML, PDF и Word разворачивает фрагмент только во временном дереве экспорта. Зашифрованные блокноты перед разбором того же JSON сначала аутентифицируют существующую обёртку шифрования документа; деривация ключей, AAD и материалы восстановления не изменяются.

### 5.14 Блок базы данных (AttributeView, лист)

```json
{ "Type": "NodeAttributeView", "ID": "...",
  "Properties": { "custom-sy-av-view": "20251230141609-lcme2fh", "id": "...", "updated": "..." },
  "AttributeViewID": "20251230141609-2kvghrg",
  "AttributeViewType": "table" }
```

- **Без Children**.
- `AttributeViewID` указывает на данные таблицы AV, которые хранятся в отдельном файле `.json`; **не** конструируйте этот ID на пустом месте.
- `AttributeViewType`: `table` / `kanban` / `gallery` и т.д. Это значение выводится из компоновки привязанного к носителю представления и не является независимым селектором представления.
- Опциональный `custom-sy-av-view` фиксирует ID текущего представления. При его отсутствии или если он не указывает на представление в указанном AttributeView, происходит откат к текущему представлению AttributeView или к первому доступному представлению.

> Рекомендуется, чтобы AI **не создавал новые блоки AttributeView**, поскольку данные таблицы находятся не в `.sy` и требуют сопутствующих файлов.

### 5.16 Пользовательский блок

```json
{ "Type": "NodeCustomBlock", "ID": "...", "Data": "Пользовательское исходное содержимое", "CustomBlockInfo": "info", "Properties": { "id": "...", "updated": "..." } }
```

`NodeCustomBlock` — листовой узел без `Children`. `Data` хранит исходное содержимое, `CustomBlockInfo` хранит строку информации ограждения.

Соответствующий исходный код Markdown использует три точки с запятой как в открывающем, так и в закрывающем ограждении:

```markdown
;;;закодированное_имя_пакета_плагина/закодированный_тип_блока
Пользовательское исходное содержимое
;;;
```

Имя пакета плагина и тип блока кодируются по отдельности как URI-компоненты, а затем соединяются через `/`. Строка, равная `;;;` после удаления маркера курсора редактора и обрезки начальных и конечных пробелов, завершает пользовательский блок и поэтому не может встречаться в `Data`. DOM, отрендеренный плагином, является временным содержимым и не может записываться как `Children`; источником постоянных данных могут быть только `Data`, атрибуты блока или внешнее хранилище, управляемое самим плагином. Вложенный редактор Protyle внутри точки монтирования рендеринга пока не поддерживается.

## 6. Подробный разбор строчных узлов

### 6.1 `NodeText` (обычный текст)

```json
{ "Type": "NodeText", "Data": "Обычный текст" }
```

Когда `Data` является пустой строкой, оно **опускается** из-за `omitempty`; поэтому `{ "Type": "NodeText" }` означает пустой текст, а не U+200B. Фактический пробел нулевой ширины должен быть явно записан в `Data`, например с помощью JSON-экранирования `"\u200b"`.

### 6.2 `NodeTextMark` (единый носитель современного строчного форматирования)

В `.sy` для жирного текста, курсива, ссылок, строчного кода, ссылок на блоки и т.д. **почти всегда** используется `NodeTextMark`, а **не** `NodeStrong`/`NodeEmphasis`/`NodeLink`. Тип определяется полем `TextMarkType`.

| `TextMarkType` | Значение | Обязательные поля |
|---|---|---|
| `text` | Обычный текст | `TextMarkTextContent` |
| `strong` | Жирный | `TextMarkTextContent` |
| `em` | Курсив | `TextMarkTextContent` |
| `u` | Подчёркивание | `TextMarkTextContent` |
| `s` | Зачёркивание (двойная тильда `~~`) | `TextMarkTextContent` |
| `mark` | Выделение цветом | `TextMarkTextContent` |
| `sup` / `sub` | Надстрочный / подстрочный | `TextMarkTextContent` |
| `kbd` | Клавиша клавиатуры | `TextMarkTextContent` |
| `code` | Строчный код | `TextMarkTextContent` |
| `tag` | Тег `#tag#` | `TextMarkTextContent` |
| `a` | Гиперссылка | `TextMarkAHref`, `TextMarkTextContent` (опционально `TextMarkATitle`) |
| `block-ref` | Ссылка на блок | `TextMarkBlockRefID`, `TextMarkBlockRefSubtype`, `TextMarkTextContent` |
| `inline-math` | Строчная формула | `TextMarkInlineMathContent` (**без** `TextMarkTextContent`) |
| `inline-memo` | Строчная заметка | `TextMarkInlineMemoContent`, `TextMarkTextContent` |
| `file-annotation-ref` | Ссылка на аннотацию файла | `TextMarkFileAnnotationRefID`, `TextMarkTextContent` |

Примеры:

```json
{ "Type": "NodeTextMark", "TextMarkType": "a", "TextMarkAHref": "https://ld246.com", "TextMarkTextContent": "Гиперссылка" }
{ "Type": "NodeTextMark", "TextMarkType": "block-ref", "TextMarkBlockRefID": "20200812220555-lj3enxa", "TextMarkBlockRefSubtype": "s", "TextMarkTextContent": "Ссылка на блок" }
{ "Type": "NodeTextMark", "TextMarkType": "inline-math", "TextMarkInlineMathContent": "a^2 + b^2 = c^2" }
{ "Type": "NodeTextMark", "TextMarkType": "inline-memo", "TextMarkInlineMemoContent": "Это строчная заметка", "TextMarkTextContent": "Заметка" }
```

- `TextMarkBlockRefSubtype`: `"s"` = статический якорный текст, `"d"` = динамический якорный текст (якорный текст следует за изменением содержимого целевого блока; обратите внимание, что «встроенный блок» — это другой узел `NodeBlockQueryEmbed`, не связанный с этим).
- `TextMarkType` может комбинировать несколько маркеров через пробел, например `"strong em"`.
- `TextMarkTextContent` есть не у всех типов (у `inline-math` его нет).
- Зачёркивание **поддерживает только двойную тильду `~~x~~`** и не поддерживает одинарную тильду `~x~` (`SetGFMStrikethrough1(false)`).
- Экранирование обратной косой чертой не является подтипом `NodeTextMark`: ему соответствует отдельный узел `NodeBackslash`, и оно не встречается среди значений `TextMarkType`.

### 6.3 Стилизованный строчный текст: правило парности

После `NodeTextMark` с цветом/эффектами (имеющего `Properties.style`) **обязательно должен сразу следовать** `NodeKramdownSpanIAL` с идентичным текстом style:

```json
{ "Type": "NodeTextMark", "Properties": { "style": "color: var(--b3-font-color1); background-color: var(--b3-font-background1);" },
  "TextMarkType": "strong", "TextMarkTextContent": "Цвет 1" },
{ "Type": "NodeKramdownSpanIAL", "Data": "{: style=\"color: var(--b3-font-color1); background-color: var(--b3-font-background1);\"}" }
```

> При генерации стилизованного строчного текста AI эти два узла должны идти парой, иначе при обратном преобразовании kramdown стили будут потеряны.

### 6.4 `NodeImage` (семисегментная базовая структура; опциональный заголовок добавляет два узла)

```json
{ "Type": "NodeImage", "Data": "span", "Children": [
  { "Type": "NodeBang" },
  { "Type": "NodeOpenBracket" },
  { "Type": "NodeLinkText", "Data": "текст alt" },
  { "Type": "NodeCloseBracket" },
  { "Type": "NodeOpenParen" },
  { "Type": "NodeLinkDest", "Data": "assets/image-2021.png" },
  { "Type": "NodeLinkSpace" },
  { "Type": "NodeLinkTitle", "Data": "Заголовок изображения" },
  { "Type": "NodeCloseParen" }
] }
```

- Узлы изображений, сгенерированные редактором, обычно имеют `Data: "span"`; совместимые компактные данные могут опускать пустое `Data`.
- Поле `Data` маркерных узлов `NodeBang` / `NodeOpenBracket` / `NodeCloseBracket` / `NodeOpenParen` / `NodeCloseParen` **может опускаться**.
- `NodeLinkText` и `NodeLinkDest` хранят соответственно альтернативный текст и целевой адрес. При наличии заголовка перед `NodeCloseParen` последовательно вставляются `NodeLinkSpace` и `NodeLinkTitle`; семиузловая форма без этих двух узлов также действительна.

### 6.5 Переносы строк и экранирование обратной косой чертой

```json
{ "Type": "NodeSoftBreak", "Data": "\n" }
{ "Type": "NodeBr" }
{ "Type": "NodeBackslash",
  "Children": [ { "Type": "NodeBackslashContent", "Data": "|" } ] }
```

- `NodeSoftBreak` обозначает мягкий перенос строки.
- `NodeBr` обозначает явный `<br>`.
- `NodeBackslash` оборачивает экранированный символ в строчный дочерний узел; он не является подтипом `NodeTextMark`.

## 7. Соглашения о кодировании base64

| Поле | Кодировка | Пример |
|---|---|---|
| `ListData.Marker` | base64 | `Kg==` = `*`, `MS4=` = `1.`, `MQ==` = `1` |
| `CodeBlockInfo` | base64 | `Z28=` = `go`, `amF2YQ==` = `java` |
| `CodeBlockOpenFence`/`CloseFence` | base64 | `YGBg` = ` ``` ` |
| `ListData.BulletChar`/`Delimiter` | **int ASCII-код** (**не** base64) | `42` = `*`, `46` = `.` |
| `TaskListItemMarker` | **int ASCII-код** (**не** base64) | `32` = пробел, `88` = `X`, `33` = `!` |
| `Data` (текст абзаца, содержимое кода, ссылки, SQL и др.) | **Исходный текст** (без кодирования) | `"package main\n..."` |

> Правило определения: поля Go `[]byte` (например, `Marker` / `Fence` / `Info`) становятся строками base64; поля Go `byte` (например, `BulletChar` / `Delimiter` / `TaskListItemMarker`) становятся числами JSON; строковые поля содержимого, такие как `Data`, `TextMarkTextContent`, `TextMarkInlineMathContent`, сохраняют исходный текст.

## 8. Properties (IAL)

Плоский `map[string]string`.

**Уровень документа (обязательно при канонической записи)**: `id`, `title`, `type` (всегда `"doc"`), `updated`. Опционально: `icon` (шестнадцатеричный код точки emoji, например `"1f4f0"`; имя файла пользовательской иконки; или HTTP(S) URL изображения), `title-img` (стиль обложки заголовка, строка CSS-объявления, например `background-image:url("assets/example.jpg")`).

**Уровень блока (обязательно при канонической записи)**: `id` (равен `ID` узла), `updated`. Совместимые исторические данные могут не содержать `updated`, но новые средства записи должны его предоставлять. Распространённые опциональные атрибуты включают `style`, `fold: "1"`, `name`, `alias`, `memo`, `bookmark`, `colgroup` / `caption` для таблиц, `custom-sy-av-view` для представлений атрибутов и любые атрибуты `custom-*`.

**Строчный уровень (опционально)**: некоторые строчные или структурные узлы также используют `Properties`, включая стилизованный `NodeTextMark`, позиционированный или масштабированный `NodeImage`, а также объединённый или стилизованный `NodeTableCell`. Наличие `Properties` у строчного узла не делает его блоком.

> Каноническим авторитетным ключом является `id` в **нижнем регистре**. Некоторые старые импортированные файлы также содержат устаревший `ID` в верхнем регистре; явный процесс нормализации может очищать это устаревшее поле совместимости.

## 9. Краткий справочник правил вложенности контейнеров

| Контейнер | Может содержать | Не может содержать |
|---|---|---|
| `NodeList` | **Только** `NodeListItem` | Любые другие блоки (абзацы/блоки кода/подсписки должны быть предварительно обёрнуты в `NodeListItem`) |
| `NodeListItem` | Обычные блоки содержимого и вложенные `NodeList`, `NodeMindmap` | Голый `NodeListItem`, голый `NodeMindmapItem` |
| `NodeBlockquote` | Обычные блоки содержимого и один `NodeBlockquoteMarker` | Голый `NodeListItem`, голый `NodeMindmapItem` |
| `NodeCallout` | Обычные блоки содержимого | Голый `NodeListItem`, голый `NodeMindmapItem` |
| `NodeSuperBlock` | Блоки содержимого (включая вложенные суперблоки) внутри обёртки из маркеров начала, компоновки и конца | `NodeDocument`, голый `NodeListItem`, голый `NodeTabItem`, голый `NodeMindmapItem` |
| `NodeDocument` | Обычные блоки содержимого | Голый `NodeListItem`, голый `NodeMindmapItem` |
| `NodeTabs` | Только `NodeTabItem`, минимум один | Другие блоки содержимого |
| `NodeTabItem` | Обычные блоки содержимого и вложенные `NodeTabs`, минимум один | `NodeDocument`, `NodeListItem`, `NodeTabItem` |
| `NodeMindmap` | Только `NodeMindmapItem` | Другие блоки содержимого |
| `NodeMindmapItem` | Обычные блоки содержимого и вложенные `NodeMindmap` | `NodeDocument`, `NodeList`, `NodeListItem`, `NodeMindmapItem`, `NodeFootnotesDef` |

> `NodeTabItem` должен принадлежать непосредственно `NodeTabs`; ни один из остальных перечисленных выше контейнеров не может напрямую вмещать элементы вкладок.

> Это ограничения канонической записи, выведенные из `CanContain` в Lute. Парсер Markdown применяет их при построении дерева, но `dataparser.ParseJSON` не является строгим валидатором отношений вложенности и не отклонит все нарушающие структуры. Прямые средства записи должны проверять эти отношения самостоятельно; некорректное дерево может привести к ошибкам разбора или рендеринга.

## 10. Обработка пробела нулевой ширины

Совместимые данные AST могут содержать `​` (U+200B) в `NodeText` для границ курсора рядом со строчными элементами. При редактировании следует сохранять существующие U+200B, но не следует синтезировать `NodeText` с U+200B по обе стороны от каждого изображения, строчного кода, тега, kbd или аналогичного узла; Protyle сам вставляет эти заполнители курсора в зависимости от контекста при рендеринге DOM редактора. Опущенное `Data` означает пустую строку, а не U+200B.

## 11. Типы, запрещённые для канонической записи (не генерировать)

Канонические средства записи не должны генерировать следующие виды синтаксиса или семейства узлов. Большинство из них отключены через `SetXxx(false)` в `NewLute()` в `kernel/util/lute.go`, поэтому текущая конфигурация парсера Markdown не генерирует соответствующие узлы. `NodeGitConflict` — особый случай: `NewLute()` включает `SetGitConflict(true)` только для распознавания исходных маркеров конфликта Git, уже присутствующих во вводе, но это семейство узлов по-прежнему относится к типам, запрещённым для канонической записи `.sy`. Совместимые средства чтения могут встретить любой из следующих типов в историческом или внешне сгенерированном JSON.

| Правило | Соответствующие типы узлов | Описание |
|---|---|---|
| Запрещено для канонической записи; `SetGitConflict(true)` используется для распознавания существующего ввода | `NodeGitConflict`/`NodeGitConflictOpenMarker`/`NodeGitConflictContent`/`NodeGitConflictCloseMarker` | Блок исходных маркеров конфликта Git; генерировать запрещено |
| `SetFootnotes(false)` | `NodeFootnotesDefBlock`/`NodeFootnotesDef`/`NodeFootnotesRef` | Сноски, полностью запрещены |
| `SetToC(false)` | `NodeToC` | Оглавление `[toc]` |
| `SetIndentCodeBlock(false)` | Блоки кода с отступом | Поддерживаются только блоки кода с ограждением |
| `SetHeadingID(false)` | `NodeHeadingID` | Пользовательский ID заголовка `{#id}` |
| `SetSetext(false)` | Заголовки Setext (подчёркивание `===`/`---`) | Поддерживается только стиль ATX `#` |
| `SetYamlFrontMatter(false)` | `NodeYamlFrontMatter` | Метаданные YAML Front Matter |
| `SetLinkRef(false)` | `NodeLinkRefDef`/`NodeLinkRefDefBlock` | Определение ссылки-сноски |
| `SetGFMStrikethrough1(false)` | Зачёркивание одинарной тильдой `~x~` | Поддерживается только двойная тильда `~~x~~` |

> Примечание: в `NewLute()` также есть несинтаксические переключатели, такие как `SetAutoSpace(false)`, `SetCodeSyntaxHighlight(false)`, `SetExportNormalizeTaskListMarker(false)` и др., которые влияют только на поведение рендеринга/экспорта и не приводят к исчезновению каких-либо типов узлов, поэтому они не включены в таблицу выше.

## 12. Контрольный список для AI при записи

При генерации или совместимом редактировании `.sy`, который должен корректно загружаться SiYuan, проверяйте каждый пункт:

1. ☐ Корневой `Type` = `"NodeDocument"`, `Spec` = `"2"`, `"3"` (вкладки), `"4"` (форматированный текст в ячейках таблиц), `"5"` (узлы интеллект-карт), `"6"` (ASCII `/` в заголовке документа) или `"7"` (полный строчный источник заголовка) без понижения существующей версии; корневой `ID` равен имени файла без `.sy` и равен `Properties.id`
2. ☐ Корневой `Properties` содержит `id` / `title` / `type:"doc"` / `updated`
3. ☐ Каждый вновь сгенерированный ID является новым значением и уникален во всей рабочей области; каждый канонический блок имеет 22-символьный `ID`, совпадающий `Properties.id` и корректную 14-значную `Properties.updated`
4. ☐ Блок определяется по `Type`, а не по `ID`; не добавляйте ID новым строчным или маркерным узлам, очищайте исторические неблочные ID только как нормализацию поля, не удаляя сам узел
5. ☐ При изменении содержимого или структуры обновляйте `updated` у изменённого блока, его блочных предков, применимых предшествующих заголовков и корневого узла документа
6. ☐ Списки различаются по `ListData.Typ` (`0` или опущено — маркированный, `1` — нумерованный, `3` — список задач), и `NodeList`, и каждый `NodeListItem` используют соответствующий `Typ`
7. ☐ Прямыми дочерними узлами `NodeList` могут быть **только** `NodeListItem`; для вложенного списка создайте ещё один `NodeList` внутри элемента списка
8. ☐ Поля Go `byte` (`BulletChar`, `Delimiter`, `TaskListItemMarker`) являются числами JSON; поля Go `[]byte` (`Marker`, ограждение, информация) являются строками base64
9. ☐ Маркер задачи использует `TaskListItemMarker` для хранения исходного байта маркера (`32` — пробел, `88` — `X`, другие непробельные байты означают отмеченное состояние); `TaskListItemChecked` — совместимый откат, `Data` не является авторитетным состоянием
10. ☐ Блок кода имеет четыре структурных дочерних узла, математический блок — три, встроенный блок запроса — пять, суперблок оборачивает минимум один блок содержимого маркерами начала, компоновки и конца
11. ☐ `NodeCodeBlockCode` и `NodeMathBlockContent` являются структурными строчными дочерними узлами; их исторические ID можно очищать, но нельзя удалять сами узлы
12. ☐ Строки содержимого сохраняются в исходном виде; base64 используется только для полей `[]byte`
13. ☐ Для современного строчного форматирования предпочтительно использовать `NodeTextMark`, а не устаревшие `NodeStrong` / `NodeEmphasis` / `NodeLink`
14. ☐ За стилизованным `NodeTextMark` сразу следует парный `NodeKramdownSpanIAL`
15. ☐ Узлы HTML / IFrame / Widget / Video / Audio / AttributeView / CustomBlock являются листьями без `Children`; содержимое записывается в `Data` или поля конкретного типа
16. ☐ Не конструируйте `AttributeViewID` или целевые ID ссылок на блоки на пустом месте; они должны указывать на реально существующее представление атрибутов или блок
17. ☐ Не генерируйте запрещённые типы, такие как `NodeGitConflict`, сноски, ToC, YAML, LinkRef, HeadingID и др.; при совместимом чтении исторических или внешних данных допускайте их наличие
18. ☐ При редактировании сохраняйте существующий текст U+200B, но не синтезируйте повсеместно узлы пробела нулевой ширины вокруг строчных элементов
19. ☐ Трактуйте файлы на диске зашифрованных блокнотов как шифротекст, а не как JSON; изменяйте их только через API разблокированного блокнота

## 13. Запреты и частые ошибки

| ❌ Неправильно | ✅ Правильно |
|---|---|
| Предполагать, что у всех узлов есть `Data` | `Data` может опускаться; у маркерных узлов `Data` обычно отсутствует |
| Считать узел блоком из-за наличия `ID` или удалять весь узел как аномальные данные | Тип блока определяется по `Type`; совместимые редакторы могут очищать поле `ID` у исторических неблочных узлов, но не могут удалять сам узел |
| Использовать устаревшие узлы вроде `NodeStrong`/`NodeLink` | Использовать `NodeTextMark` + `TextMarkType` |
| Считать, что `ListData.Typ` принимает только `1` | `0` или опущено — маркированный, `1` — нумерованный, `3` — список задач |
| Считать `BulletChar` строкой base64 | Это `byte`, в JSON представлен как int-код (`42` = `*`) |
| Считать `"Data":"[X]"` авторитетным состоянием задачи | Использовать число `TaskListItemMarker` для хранения исходного байта маркера; `TaskListItemChecked` — совместимый откат |
| Стилизованный `TextMark` без парного IAL | Обязательно в паре с `NodeKramdownSpanIAL` |
| Добавлять `Children` узлам AttributeView, Widget или CustomBlock | Они являются листьями и должны использовать `Data` или поля конкретного типа |
| Изменять `ID` без синхронизации `Properties.id` | Они должны совпадать |
| Обновлять временную метку только у непосредственно редактируемого блока | Нужно также обновлять его блочных предков, применимые предшествующие заголовки и корневой узел документа |
| Добавлять `TextMarkTextContent` к `inline-math` | У него есть только `TextMarkInlineMathContent` |
| Конструировать целевые ID ссылок на блоки или представлений атрибутов на пустом месте | Цель должна реально существовать |
| Делать абзац прямым дочерним узлом `NodeList` | `NodeList` может содержать только `NodeListItem`, нужно предварительно обернуть |
| Добавлять текстовый узел U+200B по обе стороны от каждого строчного элемента | Сохранять существующие U+200B; заполнители курсора DOM редактора добавляются Protyle по контексту |
| Генерировать узлы `NodeGitConflict`, сносок, ToC, YAML и т.д. | Они относятся к типам, запрещённым для канонической записи; совместимые средства чтения всё ещё могут встречать исторические или внешние узлы |
